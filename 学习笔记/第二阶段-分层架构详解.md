## 〇、分层架构总览

本项目采用经典的**四层架构**（Controller → Service → Mapper → Database），外加 DTO/VO 作为数据传输对象。一次 HTTP 请求的完整流转路径：

```
前端请求 (JSON)
    │
    ▼
Controller 层  ← 接收请求、参数校验(@Valid)、权限判断、调用 Service、封装 Result 返回
    │  入参：DTO    出参：VO（包装在 Result<T> 中）
    ▼
Service 层     ← 业务逻辑、事务控制(@Transactional)、DTO↔Entity 转换、调用 Mapper
    │  入参：DTO/基本类型    出参：VO/Entity
    ▼
Mapper 层      ← 数据访问，继承 BaseMapper<T> 获得 CRUD，可自定义 SQL
    │  入参：Entity/条件    出参：Entity/基本类型
    ▼
MySQL 数据库   ← 实际存储
```

各层职责一句话总结：

| 层 | 包路径 | 职责 | 关键注解/类 |
|----|--------|------|-------------|
| Controller | `controller/` | 接收 HTTP 请求，参数校验，调用 Service，统一返回 | `@RestController`、`@RequestMapping`、`@Valid` |
| Service | `service/` + `service/impl/` | 业务逻辑、事务、数据转换 | `@Service`、`@Transactional`、`IService`/`ServiceImpl` |
| Mapper | `mapper/` | 数据库 CRUD，自定义 SQL | `@Mapper`、`BaseMapper<T>`、`@Select`/`@Update` |
| Entity | `entity/` | 数据库表的 Java 对象映射 | `@TableName`、`@TableId`、`@TableField`、`@TableLogic` |
| DTO | `dto/` | 接收前端请求参数（入站） | `@NotBlank`、`@Size`、`@Email` 等校验注解 |
| VO | `vo/` | 返回给前端的视图对象（出站） | 通常带 `@Builder`，不含敏感字段 |

> **核心理解**：分层的本质是**关注点分离**。Controller 不管业务怎么实现，Service 不管数据怎么存，Mapper 不管业务规则。每一层只依赖下一层的接口，不跨层调用（如 Controller 不直接调 Mapper）。

## 一、Entity 层 —— 数据库表的 Java 映射

### 1.1 Entity 是什么

Entity（实体类）是**数据库表在 Java 中的对象映射**，一张表对应一个类，一行记录对应一个对象。本项目有 4 个实体类：

| 实体类 | 对应表 | 业务含义 |
|--------|--------|----------|
| `User` | `sys_user` | 系统用户（管理员/普通用户） |
| `Book` | `book` | 图书 |
| `BookCategory` | `book_category` | 图书分类 |
| `BorrowRecord` | `borrow_record` | 借阅记录 |

所有实体类的共同特征：
- 标注 `@Data`（Lombok，自动生成 getter/setter/toString/equals/hashCode）
- 标注 `@TableName("表名")`（MyBatis-Plus，指定映射的表名）
- 实现 `Serializable` 接口（可序列化，用于缓存、RPC 传输等场景）
- 包含 `serialVersionUID`（序列化版本号）

#### 补充：`@Data` 自动生成的五个方法分别干什么

`@Data` 是 Lombok 的组合注解，等价于同时加了 `@Getter` + `@Setter` + `@ToString` + `@EqualsAndHashCode` + `@RequiredArgsConstructor`。自动生成的五个方法作用：

| 方法 | 作用 | 本项目中的使用场景 |
|------|------|-------------------|
| **getter** | 读取字段值，如 `book.getTitle()` | 到处都在用，取对象的字段值 |
| **setter** | 修改字段值，如 `book.setStock(5)` | 构建 Entity、更新字段时用 |
| **toString** | 把对象转成可读字符串，如 `Book(id=1, title=Java核心技术, ...)` | `log.info("book={}", book)` 打日志时自动调用 |
| **equals** | 比较两个对象的**内容**是否相同（不是比内存地址） | `List.contains()`、`List.remove()` 底层靠它判断 |
| **hashCode** | 给对象算一个 int 哈希值（"数字指纹"） | `HashMap`/`HashSet` 存取时快速定位 |

> **为什么需要 equals 和 hashCode？** Java 里 `==` 比的是内存地址（是不是同一个对象），`equals` 比的是内容（字段值是否都相同）。两个不同的 Book 对象，只要 id 和字段都一样，`equals` 就返回 true。而 `hashCode` 约定：`equals` 相同的两个对象，`hashCode` 必须相同——所以两者总是一起生成。HashMap/HashSet 先按 hashCode 快速定位桶，再用 equals 确认是不是同一个对象。

> **为什么不直接把字段设为 public？** 封装原则：外部必须通过 getter/setter 访问字段，未来可以在 setter 里加校验（如 `setStock` 时判断不能为负），调用方代码不用改。

### 1.2 MyBatis-Plus 核心注解详解

以 `Book.java` 为典型样本，逐个注解拆解：

```java
@Data
@TableName("book")
public class Book implements Serializable {

    @TableId(type = IdType.AUTO)
    private Long id;

    private String isbn;
    private String title;
    // ... 其他普通字段

    @TableField(fill = FieldFill.INSERT)
    private LocalDateTime createTime;

    @TableField(fill = FieldFill.INSERT_UPDATE)
    private LocalDateTime updateTime;

    @TableLogic
    private Integer deleted;
}
```

| 注解 | 作用 | 本项目用法 |
|------|------|-----------|
| `@TableName("表名")` | 指定实体类映射的数据库表名。类名与表名不一致时必须显式指定（如 `User` → `sys_user`） | 4 个实体都显式指定了表名 |
| `@TableId(type = IdType.AUTO)` | 标记主键字段。`AUTO` 表示数据库自增（配合 `application.yml` 中 `id-type: auto` 全局配置） | 所有实体主键都是 `Long id`，自增 |
| `@TableField(fill = ...)` | 字段填充策略。`INSERT` = 插入时自动填充；`INSERT_UPDATE` = 插入和更新时都填充 | `createTime` 用 INSERT，`updateTime` 用 INSERT_UPDATE |
| `@TableLogic` | 逻辑删除字段。标注后，MyBatis-Plus 的查询/更新/删除会自动追加 `deleted = 0` 条件，删除操作实际变为 `UPDATE ... SET deleted = 1` | 所有实体都有 `deleted` 字段 |
| （无注解的普通字段） | 默认映射到同名列。配合 `map-underscore-to-camel-case: true`，数据库 `create_time` 自动映射到 Java `createTime` | 如 `isbn`、`title`、`categoryId` 等 |

> ⚠️ **`@TableId(type = IdType.AUTO)` 与全局配置的关系**：`application.yml` 中 `global-config.db-config.id-type: auto` 是全局默认，实体上不写 `@TableId` 也会生效。但本项目每个实体都显式写了 `@TableId(type = IdType.AUTO)`，属于"显式优于隐式"的写法，可读性更好。

### 1.3 四个实体类的字段对比

| 字段类别 | User | Book | BookCategory | BorrowRecord |
|----------|------|------|--------------|--------------|
| 主键 | `id` | `id` | `id` | `id` |
| 业务字段 | username, password, nickname, email, phone, role, status | isbn, title, author, publisher, publishDate, categoryId, price, stock, totalStock, description, coverUrl | name, description, sort | userId, bookId, borrowDate, dueDate, returnDate, status, fine |
| 自动填充 | createTime, updateTime | createTime, updateTime | createTime, updateTime | createTime, updateTime |
| 逻辑删除 | deleted | deleted | deleted | deleted |

几个值得注意的设计：

1. **`User.password` 存 BCrypt 加密后的密文**，不是明文。注册时 `BCrypt.hashpw()` 加密，登录时 `BCrypt.checkpw()` 校验。
2. **`Book.stock` 与 `Book.totalStock` 分离**：`stock` 是当前可借库存（借还时变动），`totalStock` 是总藏书量（新增时 = stock，更新库存时按差值调整）。
3. **`BorrowRecord.status` 用字符串枚举值**：`BORROWED`（借阅中）、`RETURNED`（已归还）、`OVERDUE`（已逾期），而不是数字编码，可读性更好。
4. **`BorrowRecord.fine` 用 `BigDecimal`**：涉及金额必须用 `BigDecimal`，不能用 `double`/`float`（浮点精度丢失问题）。

#### 补充：四个设计细节为什么这么做

**① 密码存 BCrypt 密文，不存明文**

如果数据库被拖库，明文密码直接暴露。BCrypt 是**单向加密**：只能从明文→密文，不能从密文反推明文。而且每次加密结果不同（带随机盐），两个用户密码都是"123456"，存进去的密文也不一样。

```java
// 注册时加密
String hashed = BCrypt.hashpw("123456", BCrypt.gensalt());
// 存进去的是：$2a$10$N9qo8uLOickgx2ZMRZoMyeIjZAgcfl7p92ldGxad68LJZdL17lhWy

// 登录时校验（不是查密码是否相等，是用 BCrypt 校验输入是否匹配密文）
BCrypt.checkpw("123456", hashed);  // true
```

**② stock 和 totalStock 分离**

```
totalStock = 这本书一共有多少本（只在采购/报废时变）
stock      = 现在还能借几本（借还时频繁变动）
```

一本书买了 5 本，totalStock=5。有人借走 1 本，stock=4，totalStock 还是 5。如果只有一个字段，就不知道"原来有多少本"，也无法统计"被借走了几本"（totalStock - stock）。

**③ status 用字符串不用数字**

```java
status = "BORROWED"   // 一看就懂：借阅中
// 对比：status = 0  // 啥意思？得查注释
```

用字符串的好处：查数据库、看日志时直接能看懂，不用回忆数字编码。代价是占的空间稍大，对这种小项目可以忽略，可读性优先。

**④ 金额用 BigDecimal，不用 double**

```java
double a = 0.1 + 0.2;
System.out.println(a);  // 输出 0.30000000000000004，不是 0.3！
```

浮点数在计算机里是二进制近似存储，算钱时差一分钱都是 bug。BigDecimal 能精确表示十进制小数：

```java
BigDecimal daily = new BigDecimal("0.50");   // 每天罚 5 毛
BigDecimal fine = daily.multiply(BigDecimal.valueOf(3));  // 逾期3天 = 1.50，精确
```

所以 `BorrowRecord.fine` 和 `Book.price` 都用 `BigDecimal`。

### 1.4 自动填充机制 —— `MyMetaObjectHandler`

实体类上 `@TableField(fill = FieldFill.INSERT)` 只是"声明需要填充"，**真正填充值的逻辑在 `MyMetaObjectHandler.java`**：

```java
@Component
public class MyMetaObjectHandler implements MetaObjectHandler {

    @Override
    public void insertFill(MetaObject metaObject) {
        this.strictInsertFill(metaObject, "createTime", LocalDateTime.class, LocalDateTime.now());
        this.strictInsertFill(metaObject, "updateTime", LocalDateTime.class, LocalDateTime.now());
    }

    @Override
    public void updateFill(MetaObject metaObject) {
        this.strictUpdateFill(metaObject, "updateTime", LocalDateTime.class, LocalDateTime.now());
    }
}
```

- 实现 `MetaObjectHandler` 接口并标注 `@Component`，MyBatis-Plus 自动识别。
- `insertFill`：执行 `insert` 时被调用，自动设置 `createTime` 和 `updateTime` 为当前时间。
- `updateFill`：执行 `updateById`/`update` 时被调用，自动刷新 `updateTime`。
- `strictInsertFill` / `strictUpdateFill`：严格填充模式——**只有字段为 null 时才填充**，如果业务代码手动设了值则不覆盖。

#### 补充：`@Component` 是什么

`@Component` 是 Spring 最基础的注解，作用是**把这个类交给 Spring 容器管理**（变成一个 Bean）。Spring 启动时自动创建这个类的实例，放进 IoC 容器里，需要用时直接注入，不用自己 `new`。

`@Service`、`@Controller`、`@RestController`、`@Repository` 本质上都是 `@Component` 的"马甲"——内部都标注了 `@Component`，功能完全一样，只是语义不同（让人一眼看出属于哪一层）。`MyMetaObjectHandler` 不属于 Controller/Service/Mapper 任何一层，所以直接用 `@Component`。

> 只有 Spring 管理的 Bean，MyBatis-Plus 才能自动发现并调用它的 `insertFill`/`updateFill`。如果不写 `@Component`，这个类就是个普通 Java 类，框架根本不知道它的存在。

#### 补充：`MetaObject` 是什么 + 具体调用链

`MetaObject` 是 **MyBatis 提供的对象包装器**，把任意 Java 对象包一层，提供统一的 `getValue("字段名")` / `setValue("字段名", 值)` 方法，底层用反射操作。为什么要包一层？因为填充器要处理所有实体类（User、Book、BorrowRecord...），不可能为每个类写一套。有了 `MetaObject`，不管你是什么类，统一用字符串属性名就能读写：

```java
metaObject.setValue("createTime", LocalDateTime.now());
// 等价于：book.setCreateTime(LocalDateTime.now());
// 但用反射实现，不需要知道对象的具体类型
```

所以 `insertFill(MetaObject metaObject)` 的参数，**就是你正在保存的那个实体对象的包装版**。

**具体调用链（以 `save(book)` 为例）：**

```
你在 Service 里调用：bookService.save(book)
    │
    ▼
ServiceImpl.save() 内部调用：baseMapper.insert(book)
    │
    ▼
MyBatis-Plus 拦截到 INSERT，检查 book 的字段：
    发现 createTime 上有 @TableField(fill = FieldFill.INSERT)
    发现 updateTime 上有 @TableField(fill = FieldFill.INSERT_UPDATE)
    → "有字段需要自动填充！"
    │
    ▼
从 Spring 容器中取出 MetaObjectHandler 的实现：
    → 就是 MyMetaObjectHandler（因为标了 @Component）
    │
    ▼
把 book 包装成 MetaObject：
    MetaObject metaObject = MetaObject.forObject(book, ...);
    │
    ▼
调用你的方法：myMetaObjectHandler.insertFill(metaObject)
    │
    ▼
insertFill 里执行 strictInsertFill(metaObject, "createTime", ...)：
    → 内部判断：metaObject.getValue("createTime") == null ?
    → 是 null → metaObject.setValue("createTime", 当前时间)  ← 反射调用 setCreateTime()
    → 不是 null → 跳过（严格模式，不覆盖手动设置的值）
    │
    ▼
填充完毕，book 现在有了 createTime 和 updateTime
    │
    ▼
MyBatis 才真正执行：INSERT INTO book (title, stock, create_time, update_time, ...)
```

更新时同理，`updateById(book)` 会触发 `updateFill(metaObject)`，只刷新 `updateTime`，不碰 `createTime`。

> 学习价值：这就是"约定优于配置"的体现。业务代码里 `save(book)` 时完全不用管 `createTime`/`updateTime`，框架自动填好。

### 1.5 逻辑删除机制

`@TableLogic` + `application.yml` 全局配置配合工作：

```yaml
mybatis-plus:
  global-config:
    db-config:
      logic-delete-field: deleted
      logic-delete-value: 1
      logic-not-delete-value: 0
```

效果：
- `selectById(1)` → 实际执行 `SELECT * FROM book WHERE id = 1 AND deleted = 0`
- `removeById(1)` → 实际执行 `UPDATE book SET deleted = 1 WHERE id = 1`（不是物理 DELETE）
- `updateById` → 自动追加 `AND deleted = 0`

> ⚠️ 注意：`BookMapper` 中自定义的 `@Update` SQL（如 `decreaseStock`）**没有自动追加逻辑删除条件**，所以手写 SQL 时必须自己加 `AND deleted = 0`，本项目的自定义 SQL 都做到了这一点。

## 二、Mapper 层 —— 数据访问接口

### 2.1 Mapper 是什么

Mapper 是**数据访问层接口**，负责与数据库交互。本项目的 Mapper 全部是**接口**，没有实现类——MyBatis 通过**动态代理**在运行时生成实现。

所有 Mapper 的共同模式：

```java
@Mapper
public interface XxxMapper extends BaseMapper<XxxEntity> {
    // 可自定义方法
}
```

- `extends BaseMapper<T>`：继承 MyBatis-Plus 提供的通用 CRUD 接口，**免费获得 17 个方法**，无需写 SQL。
- `@Mapper`：标记这是 MyBatis 的 Mapper 接口（配合启动类的 `@MapperScan`，二选一即可，本项目两者都写了，双重保险）。

### 2.2 `BaseMapper<T>` 提供的 CRUD 方法清单

继承 `BaseMapper<T>` 后自动获得以下方法（以 `BookMapper extends BaseMapper<Book>` 为例）：

| 分类 | 方法签名 | 作用 |
|------|----------|------|
| **插入** | `int insert(T entity)` | 插入一条记录 |
| **删除** | `int deleteById(Serializable id)` | 按 ID 逻辑删除 |
| | `int delete(Wrapper<T> wrapper)` | 按条件删除 |
| | `int deleteBatchIds(Collection ids)` | 批量删除 |
| **更新** | `int updateById(T entity)` | 按 ID 更新（非空字段） |
| | `int update(T entity, Wrapper<T> wrapper)` | 按条件更新 |
| **查询单条** | `T selectById(Serializable id)` | 按 ID 查询 |
| | `T selectOne(Wrapper<T> wrapper)` | 按条件查一条（多条报错） |
| **查询列表** | `List<T> selectList(Wrapper<T> wrapper)` | 按条件查列表 |
| | `List<T> selectBatchIds(Collection ids)` | 按 ID 批量查询 |
| | `List<Map<String,Object>> selectMaps(Wrapper<T>)` | 查 Map 列表 |
| **查询数量** | `Long selectCount(Wrapper<T> wrapper)` | 统计数量 |
| **分页** | `<P extends IPage<T>> P selectPage(P page, Wrapper<T>)` | 分页查询（需配置分页插件） |

> 本项目 Service 层中大量使用的 `getById()`、`save()`、`updateById()`、`removeById()`、`page()`、`list()`、`count()` 等方法，底层就是调用这些 BaseMapper 方法（通过 `ServiceImpl` 封装了一层）。

### 2.3 四个 Mapper 对比

| Mapper | 继承 | 自定义方法 | 说明 |
|--------|------|-----------|------|
| `UserMapper` | `BaseMapper<User>` | 无 | 纯通用 CRUD，空接口 |
| `BookCategoryMapper` | `BaseMapper<BookCategory>` | 无 | 纯通用 CRUD，空接口 |
| `BookMapper` | `BaseMapper<Book>` | `decreaseStock`、`increaseStock` | 自定义库存原子操作 |
| `BorrowRecordMapper` | `BaseMapper<BorrowRecord>` | `countBorrowingByUserId`、`countByUserAndBook` | 自定义计数查询 |

**空接口也是有意义的**：`UserMapper` 和 `BookCategoryMapper` 虽然没有自定义方法，但继承 `BaseMapper` 后就拥有了完整的 CRUD 能力，Service 层通过 `ServiceImpl<UserMapper, User>` 间接使用。

### 2.4 自定义 SQL：注解方式

当 BaseMapper 的通用方法不够用时（如复杂查询、原子操作），可以在 Mapper 接口方法上用 `@Select`/`@Update` 等注解直接写 SQL。

#### 示例 1：`BookMapper.decreaseStock` —— 原子扣减库存（防超卖）

```java
@Update("UPDATE book SET stock = stock - #{count} WHERE id = #{bookId} AND stock >= #{count} AND deleted = 0")
int decreaseStock(@Param("bookId") Long bookId, @Param("count") Integer count);
```

**为什么不用 `updateById`？**
- 如果先 `selectById` 查库存、再判断、再 `updateById`，在并发场景下会出现**超卖**（两个请求都查到 stock=1，都通过校验，都扣减，结果 stock=-1）。
- 这条 SQL 用 `WHERE stock >= #{count}` 把"判断 + 扣减"放在**一条原子 SQL** 中，数据库行锁保证并发安全。
- 返回值 `int` 是影响行数：返回 0 表示库存不足（WHERE 条件不满足），返回 1 表示扣减成功。
- `BorrowServiceImpl.borrowBook` 中就是靠 `affectedRows == 0` 判断库存不足并抛异常。

#### 示例 2：`BorrowRecordMapper.countByUserAndBook` —— 防重复借阅

```java
@Select("SELECT COUNT(*) FROM borrow_record WHERE user_id = #{userId} AND book_id = #{bookId} AND status = 'BORROWED' AND deleted = 0")
int countByUserAndBook(@Param("userId") Long userId, @Param("bookId") Long bookId);
```

- 用 `COUNT(*)` 判断用户是否已借阅某本书且未归还。
- 手写 SQL 时必须手动加 `AND deleted = 0`（自定义 SQL 不享受 `@TableLogic` 自动追加）。

> `@Param("bookId")` 的作用：给方法参数起名字，让 SQL 中的 `#{bookId}` 能对应上。如果只有一个参数且用 `#{}` 引用，可以省略；多个参数时必须写。

### 2.5 分页插件 —— `MyBatisPlusConfig`

BaseMapper 的 `selectPage` 方法**不会自动分页**，必须配置分页拦截器。`MyBatisPlusConfig.java` 做了这件事：

```java
@Configuration
public class MyBatisPlusConfig {

    @Bean
    public MybatisPlusInterceptor mybatisPlusInterceptor() {
        MybatisPlusInterceptor interceptor = new MybatisPlusInterceptor();

        // 分页插件
        PaginationInnerInterceptor paginationInterceptor = new PaginationInnerInterceptor(DbType.MYSQL);
        paginationInterceptor.setMaxLimit(500L);  // 单页最大 500 条，防恶意查询
        paginationInterceptor.setOverflow(false); // 页码溢出不返回空，而是查最后一页
        interceptor.addInnerInterceptor(paginationInterceptor);

        // 乐观锁插件（本项目实体未使用 @Version，但已预留）
        interceptor.addInnerInterceptor(new OptimisticLockerInnerInterceptor());

        return interceptor;
    }
}
```

分页插件的工作原理：拦截 `selectPage` 执行，先自动执行一条 `SELECT COUNT(*)` 查总数，再拼接 `LIMIT offset, size` 查当前页数据，封装成 `IPage<T>` 返回。

> Service 层 `BookServiceImpl.pageBooks` 中 `new Page<>(pageNum, pageSize)` + `page(page, wrapper)` 就是走的这个机制。

## 三、Service 层 —— 业务逻辑封装与事务管理

### 3.1 Service 的接口 + 实现分离模式

本项目每个业务域都有**接口**和**实现类**两部分：

| 接口 | 实现类 |
|------|--------|
| `UserService extends IService<User>` | `UserServiceImpl extends ServiceImpl<UserMapper, User> implements UserService` |
| `BookService extends IService<Book>` | `BookServiceImpl extends ServiceImpl<BookMapper, Book> implements BookService` |
| `BookCategoryService extends IService<BookCategory>` | `BookCategoryServiceImpl extends ServiceImpl<BookCategoryMapper, BookCategory> implements BookCategoryService` |
| `BorrowService extends IService<BorrowRecord>` | `BorrowServiceImpl extends ServiceImpl<BorrowRecordMapper, BorrowRecord> implements BorrowService` |

**为什么要接口 + 实现分离？**
1. **面向接口编程**：Controller 依赖 `UserService` 接口，不依赖具体实现，未来换实现类不影响调用方。
2. **MyBatis-Plus 的 `IService`/`ServiceImpl` 体系**：继承 `IService<T>` 获得通用 Service 方法（比 BaseMapper 更丰富，如 `saveBatch`、`getOne`、`page` 等），继承 `ServiceImpl<Mapper, Entity>` 获得这些方法的默认实现。
3. **AOP 代理**：Spring 的 `@Transactional`、日志切面等基于接口代理（JDK 动态代理），有接口更规范。

实现类的标准写法：

```java
@Slf4j
@Service
@RequiredArgsConstructor
public class UserServiceImpl extends ServiceImpl<UserMapper, User> implements UserService {

    private final JwtUtil jwtUtil;  // 构造器注入（Lombok @RequiredArgsConstructor 生成）

    // 业务方法...
}
```

- `@Service`：注册为 Spring Bean。
- `@RequiredArgsConstructor`：Lombok 注解，为所有 `final` 字段生成构造器，实现**构造器注入**（Spring 推荐的注入方式，替代 `@Autowired` 字段注入）。
- `extends ServiceImpl<UserMapper, User>`：继承后可直接用 `baseMapper` 调用 Mapper，也可用 `this.save()`/`this.getById()` 等通用方法。

### 3.2 `IService<T>` 提供的通用 Service 方法

`IService` 在 `BaseMapper` 基础上增加了更多便捷方法，本项目常用的：

| 方法 | 作用 | 本项目使用场景 |
|------|------|---------------|
| `save(T entity)` | 插入 | 注册用户、新增图书、创建借阅记录 |
| `getById(Serializable id)` | 按 ID 查询 | 校验图书/用户是否存在 |
| `getOne(Wrapper<T>)` | 按条件查一条 | `getByUsername` 查用户 |
| `updateById(T entity)` | 按 ID 更新 | 更新图书、更新借阅记录 |
| `removeById(Serializable id)` | 按 ID 逻辑删除 | 删除图书、删除分类 |
| `list(Wrapper<T>)` | 查列表 | 查询所有分类 |
| `page(IPage<T>, Wrapper<T>)` | 分页查询 | 图书分页、借阅记录分页 |
| `count(Wrapper<T>)` | 统计数量 | 校验 ISBN 是否存在、分类下图书数 |

> 注意：`ServiceImpl` 内部持有 `baseMapper`（即对应的 Mapper 接口代理对象），需要调用 Mapper 自定义方法时用 `baseMapper.xxx()`，如 `BorrowServiceImpl` 中 `baseMapper.countByUserAndBook(userId, bookId)`。

### 3.3 四个 Service 的业务方法清单

| Service | 自定义业务方法 | 核心业务 |
|---------|---------------|----------|
| `UserService` | `login(LoginDTO)`、`register(RegisterDTO)`、`getByUsername(String)`、`toVO(User)` | 登录验证 + JWT 签发、注册（BCrypt 加密） |
| `BookService` | `pageBooks(BookQueryDTO)`、`getBookById(Long)`、`addBook(BookAddDTO)`、`updateBook(Long, BookUpdateDTO)`、`deleteBook(Long)`、`toVO(Book)` | 图书 CRUD + 分页搜索 + Redis 缓存 |
| `BookCategoryService` | `listAllCategories()`、`addCategory(BookCategory)`、`updateCategory(BookCategory)`、`deleteCategory(Long)`、`toVO(BookCategory)` | 分类 CRUD + 删除前校验（分类下无图书才能删） |
| `BorrowService` | `borrowBook(Long, Long)`、`returnBook(Long)`、`pageUserBorrowRecords(...)`、`pageAllBorrowRecords(...)`、`toVO(BorrowRecord)` | 借阅（分布式锁+原子扣库存+事务+MQ）、归还（逾期罚款计算） |

### 3.4 事务管理 —— `@Transactional`

所有写操作（新增、更新、删除）都标注了 `@Transactional(rollbackFor = Exception.class)`：

```java
@Override
@Transactional(rollbackFor = Exception.class)
public UserVO register(RegisterDTO registerDTO) {
    // ... 多个数据库操作，要么全部成功，要么全部回滚
}
```

**关键点：**

1. **`rollbackFor = Exception.class`**：Spring 默认只对 `RuntimeException` 和 `Error` 回滚，对受检异常（`Exception` 子类）不回滚。显式指定 `rollbackFor = Exception.class` 表示**任何异常都回滚**，这是企业项目的标准写法。

2. **事务的边界**：`@Transactional` 标注的方法内，所有数据库操作在同一个事务中。以 `borrowBook` 为例（实际事务在 `doBorrowBook` 的调用链中）：
   - 扣减库存（`decreaseStock`）
   - 创建借阅记录（`save`）
   - 两步必须同时成功或同时失败。如果扣库存成功但创建记录失败，事务回滚，库存恢复。

3. **事务失效的常见坑**（本项目都避开了）：
   - 方法不是 `public` → 本项目都是 public
   - 同类内部调用（`this.方法()`）→ 本项目事务方法都由 Controller 或其他 Bean 调用
   - 异常被 catch 吞掉 → 本项目 catch 只用于 MQ 发送失败等非主流程操作，主流程异常直接抛出

### 3.5 典型业务流程剖析

#### 流程 A：借阅图书（`BorrowServiceImpl.borrowBook`）

这是本项目最复杂的业务方法，融合了**分布式锁 + 多层校验 + 原子操作 + 事务 + 异步消息**：

```
borrowBook(userId, bookId)
│
├─ ① 分布式锁（Redis）
│   lockKey = "library:lock:borrow:{userId}:{bookId}"
│   尝试加锁，10秒过期 → 防止同一用户并发重复借阅同一本书
│
├─ ② doBorrowBook（核心逻辑，在锁保护下执行）
│   ├─ 校验用户存在且未禁用
│   ├─ 校验图书存在且有库存
│   ├─ 校验用户未借阅此书（countByUserAndBook == 0）
│   ├─ 校验用户借阅数未达上限（countBorrowingByUserId < maxCount）
│   ├─ 原子扣减库存（decreaseStock，返回 0 则库存不足）
│   ├─ 创建借阅记录（borrowDate=今天, dueDate=今天+maxDays, status=BORROWED）
│   ├─ 异步发送借阅成功通知（RabbitMQ，失败不影响主流程）
│   └─ 异步发送延迟到期提醒（延迟队列，60秒后触发）
│
└─ ③ finally 释放分布式锁（Lua 脚本保证只释放自己的锁）
```

> 借阅数上限 `max-count: 5` 和最大借阅天数 `max-days: 30` 来自 `application.yml` 的 `library.borrow.*` 自定义配置，通过 `@Value` 注入。

#### 流程 B：归还图书（`BorrowServiceImpl.returnBook`）

```
returnBook(recordId)
├─ 校验借阅记录存在
├─ 校验未归还（status != RETURNED）
├─ 计算逾期罚款：
│   if (今天 > dueDate) → fine = 0.50元/天 × 逾期天数
│   else → fine = 0
├─ 原子增加库存（increaseStock）
├─ 更新借阅记录（returnDate=今天, status=RETURNED, fine=计算值）
└─ 异步发送归还通知（含罚款金额）
```

> 每日罚款 `DAILY_FINE = new BigDecimal("0.50")` 是硬编码常量。用 `BigDecimal.valueOf(overdueDays)` 转成 BigDecimal 再相乘，避免精度问题。

#### 流程 C：新增图书（`BookServiceImpl.addBook`）

```
addBook(BookAddDTO)
├─ 校验 ISBN 唯一（count > 0 则抛异常）
├─ 校验分类存在（categoryId 不为 null 时）
├─ DTO → Entity（BeanUtils.copyProperties）
├─ 设置 totalStock = stock（初始总藏书量 = 库存）
├─ save(book)
└─ 返回 toVO(book)
```

### 3.6 `LambdaQueryWrapper` 动态条件构建

Service 层大量使用 `LambdaQueryWrapper<T>` 构建查询条件，这是 MyBatis-Plus 的条件构造器，**用方法引用代替字符串列名**，编译期就能检查字段是否存在：

```java
// BookServiceImpl.buildQueryWrapper 中的动态条件
LambdaQueryWrapper<Book> wrapper = new LambdaQueryWrapper<>();

if (StringUtils.hasText(queryDTO.getTitle())) {
    wrapper.like(Book::getTitle, queryDTO.getTitle());   // LIKE '%Java%'
}
if (queryDTO.getCategoryId() != null) {
    wrapper.eq(Book::getCategoryId, queryDTO.getCategoryId());  // WHERE category_id = ?
}
if (Boolean.TRUE.equals(queryDTO.getOnlyAvailable())) {
    wrapper.gt(Book::getStock, 0);  // WHERE stock > 0
}
wrapper.orderByDesc(Book::getCreateTime);  // ORDER BY create_time DESC
```

常用条件方法：

| 方法 | 对应 SQL |
|------|----------|
| `eq(列, 值)` | `WHERE 列 = 值` |
| `ne(列, 值)` | `WHERE 列 <> 值` |
| `like(列, 值)` | `WHERE 列 LIKE '%值%'` |
| `gt(列, 值)` | `WHERE 列 > 值` |
| `ge(列, 值)` | `WHERE 列 >= 值` |
| `in(列, 集合)` | `WHERE 列 IN (...)` |
| `orderByAsc/Desc(列)` | `ORDER BY 列 ASC/DESC` |

> ⚠️ **排序字段白名单**：`BookServiceImpl` 中 `ALLOWED_ORDER_FIELDS` 定义了允许排序的字段集合，用户传入的 `orderBy` 参数必须在白名单内才生效。这是为了**防止 SQL 注入**——如果直接把用户输入拼到 ORDER BY 后面，攻击者可以注入恶意 SQL。

### 3.7 循环依赖的规避

`BookCategoryServiceImpl` 中有一个值得注意的设计：

```java
// 直接注入 BookMapper 而不是 BookService，避免循环依赖
private final BookMapper bookMapper;
```

**为什么不注入 `BookService`？**
- `BookServiceImpl` 注入了 `BookCategoryService`（toVO 时查分类名）
- 如果 `BookCategoryServiceImpl` 再注入 `BookService`，就形成了 **循环依赖**（A→B→A）
- Spring Boot 2.6+ 默认禁止循环依赖启动
- 解决方案：`BookCategoryServiceImpl` 直接注入 `BookMapper`（只需要 `selectCount` 统计分类下图书数，用 Mapper 足够），打破循环

## 四、Controller 层 —— RESTful API 设计

### 4.1 Controller 的标准写法

所有 Controller 的共同模式：

```java
@Tag(name = "图书管理", description = "...")   // Knife4j 分组
@RestController                                 // = @Controller + @ResponseBody
@RequestMapping("/books")                       // 基础路径
@RequiredArgsConstructor                        // 构造器注入
public class BookController {

    private final BookService bookService;      // 依赖 Service 接口

    @Operation(summary = "分页查询图书")
    @GetMapping
    public Result<IPage<BookVO>> pageBooks(BookQueryDTO queryDTO) {
        IPage<BookVO> page = bookService.pageBooks(queryDTO);
        return Result.success(page);
    }
}
```

- `@RestController`：标记为 REST 控制器，返回值自动序列化为 JSON（不需要每个方法加 `@ResponseBody`）。
- `@RequestMapping("/books")`：类级别的基础路径，方法上的路径在此基础上拼接。
- 返回值统一用 `Result<T>` 包装，保证前后端交互格式一致。

### 4.2 五个 Controller 的接口清单

#### AuthController（`/auth`）—— 认证接口（JWT 白名单，无需登录）

#### BookController（`/books`）—— 图书管理

### 4.3 RESTful 设计要点

1. **URL 用名词，不用动词**：`/books`、`/borrows`、`/categories`，而不是 `/getBooks`、`/deleteBook`。
2. **HTTP 方法表达动作**：
   - `GET` = 查询（幂等，无副作用）
   - `POST` = 新增（非幂等）
   - `PUT` = 全量更新（幂等）
   - `DELETE` = 删除（幂等）
3. **路径参数用 `{}`**：`/books/{id}` 中的 `id` 用 `@PathVariable` 接收。
4. **查询参数用 Query String**：`GET /books?title=Java&pageNum=1`，用 `@RequestParam` 或直接用 DTO 对象接收（Spring 自动绑定）。
5. **请求体用 `@RequestBody`**：POST/PUT 的 JSON 数据用 `@RequestBody` 反序列化为 DTO。

### 4.4 常用参数绑定注解

| 注解 | 作用 | 本项目示例 |
|------|------|-----------|
| `@RequestBody` | 从 JSON 请求体绑定对象 | `login(@Valid @RequestBody LoginDTO loginDTO)` |
| `@PathVariable` | 从 URL 路径绑定变量 | `getBookById(@PathVariable Long id)` |
| `@RequestParam` | 从 Query String 绑定参数 | `getMyBorrowRecords(@RequestParam(required=false) String status)` |
| `@Valid` | 触发参数校验（配合 DTO 上的注解） | `addBook(@Valid @RequestBody BookAddDTO addDTO)` |

> `@RequestParam` 有几个实用属性：`required = false`（可选）、`defaultValue = "1"`（默认值）。`BorrowController.getMyBorrowRecords` 中 `pageNum` 默认 1、`pageSize` 默认 10。

### 4.5 统一响应封装 —— `Result<T>`

所有 Controller 方法的返回值都是 `Result<T>`，标准结构：

```json
{
  "code": 20000,
  "message": "操作成功",
  "data": { ... },
  "timestamp": 1693574400000
}
```

`Result.java` 提供了静态工厂方法：

| 方法 | 用途 |
|------|------|
| `Result.success()` | 成功，无数据 |
| `Result.success(data)` | 成功，带数据 |
| `Result.success(message, data)` | 成功，自定义消息 + 数据 |
| `Result.error()` | 失败，默认错误码 50000 |
| `Result.error(message)` | 失败，自定义消息 |
| `Result.error(ResultCode)` | 失败，用枚举指定错误码 |
| `Result.error(code, message)` | 失败，自定义码 + 消息 |

错误码由 `ResultCode` 枚举统一管理，分段设计：

| 码段 | 含义 | 示例 |
|------|------|------|
| 20000 | 成功 | `SUCCESS` |
| 40000-40099 | 参数错误 | `PARAM_ERROR`、`PARAM_NOT_NULL` |
| 40100-40199 | 认证错误 | `UNAUTHORIZED`、`TOKEN_INVALID` |
| 40300 | 权限不足 | `FORBIDDEN` |
| 40400 | 资源不存在 | `NOT_FOUND` |
| 40010-40099 | 业务错误 | `USERNAME_EXIST`、`BOOK_OUT_OF_STOCK`、`BORROW_LIMIT_EXCEEDED` |
| 50000+ | 服务端错误 | `ERROR`、`SERVICE_UNAVAILABLE` |

### 4.6 权限校验方式

本项目**没有使用 Spring Security**，而是采用**手动权限校验**的轻量方案：

```java
// BookController 中的管理员校验
private void checkAdmin() {
    if (!UserContext.isAdmin()) {
        throw new BusinessException(ResultCode.FORBIDDEN);
    }
}
```

- `UserContext` 从 `ThreadLocal` 中获取当前登录用户的角色（JWT 拦截器解析 Token 后设置）。
- 需要管理员权限的方法（新增/更新/删除图书、分类、查看所有借阅记录）调用 `checkAdmin()`。
- 普通用户只能操作自己的数据（借阅、查看自己的记录），`BorrowController.getBorrowRecordById` 中还有"普通用户只能查看自己的记录"的细粒度校验。

> 这种方式简单直接，适合中小型项目。大型项目通常用 Spring Security + `@PreAuthorize` 注解式权限控制。

## 五、重点：DTO → Entity → VO 数据转换流程

这是第二阶段的**核心理解点**。为什么一个简单的"新增图书"需要三个对象？因为它们分别面向不同的"受众"，字段和约束都不同。

### 5.1 DTO、Entity、VO 的定义与职责

| 对象 | 全称 | 面向 | 职责 | 本项目包 |
|------|------|------|------|----------|
| **DTO** | Data Transfer Object | 前端 → 后端（入站） | 接收请求参数，携带校验注解 | `dto/` |
| **Entity** | 实体 | 后端 ↔ 数据库 | 映射数据库表，持久化对象 | `entity/` |
| **VO** | View Object | 后端 → 前端（出站） | 返回给前端的视图数据，不含敏感字段，可含关联信息 | `vo/` |

一句话区分：
- **DTO 是"前端给我的"**：我要校验它合不合法。
- **Entity 是"数据库里的"**：我要把它存进去/取出来。
- **VO 是"我给前端的"**：我要挑该给的字段给，不该给的（如 password）不给。

### 5.2 本项目的 DTO 清单

| DTO | 使用场景 | 关键字段 | 校验注解 |
|-----|----------|----------|----------|
| `LoginDTO` | 登录请求 | username, password | `@NotBlank`、`@Size(3-50)`、`@Size(6-100)` |
| `RegisterDTO` | 注册请求 | username, password, nickname, email, phone | `@NotBlank`、`@Pattern`（字母数字下划线）、`@Email`、`@Pattern`（手机号正则） |
| `BookAddDTO` | 新增图书 | isbn, title, author, publisher, publishDate, categoryId, price, stock, description, coverUrl | `@NotBlank`（isbn/title/author/stock）、`@DecimalMin`、`@Digits`、`@Min` |
| `BookQueryDTO` | 图书查询条件 | title, author, isbn, categoryId, onlyAvailable, pageNum, pageSize, orderBy, orderDir | `@Min(1)`（pageNum）、`@Min(1)@Max(100)`（pageSize），有默认值 |
| `BookUpdateDTO` | 更新图书 | 同 BookAddDTO 但全部可选 | 只有 `@Size`/`@DecimalMin` 等格式校验，无 `@NotBlank`（部分更新） |

> `BookAddDTO` vs `BookUpdateDTO` 的区别：新增时 `isbn`/`title`/`stock` 等必填（`@NotBlank`/`@NotNull`），更新时全部可选（只传要改的字段），这就是"部分更新"语义。

### 5.3 本项目的 VO 清单

| VO | 使用场景 | 特殊字段（Entity 没有的） |
|----|----------|--------------------------|
| `LoginVO` | 登录响应 | token, tokenPrefix, expiresIn, user（嵌套 UserVO） |
| `UserVO` | 用户信息 | **无 password 字段**（敏感字段剔除） |
| `BookVO` | 图书信息 | categoryName（分类名，关联查询）、available（是否可借，计算字段） |
| `BorrowRecordVO` | 借阅记录 | username, nickname, bookTitle, bookAuthor（关联信息）、overdue（是否逾期，计算字段）、remainingDays（剩余天数，计算字段） |
| `CategoryVO` | 分类信息 | bookCount（分类下图书数，统计字段） |

> VO 的典型特征：**比 Entity 多了关联信息和计算字段，少了敏感字段和内部字段**。比如 `BorrowRecord` 实体只有 `userId` 和 `bookId`，但 `BorrowRecordVO` 补充了 `username`、`bookTitle` 等前端真正需要展示的信息。

### 5.4 转换工具：`BeanUtils.copyProperties`

本项目使用 Spring 提供的 `BeanUtils.copyProperties(source, target)` 进行对象拷贝，**按属性名自动匹配复制**：

```java
// UserServiceImpl.register：DTO → Entity
User user = new User();
BeanUtils.copyProperties(registerDTO, user);  // 同名字段自动复制

// UserServiceImpl.toVO：Entity → VO
UserVO vo = new UserVO();
BeanUtils.copyProperties(user, vo);  // password 不会被复制，因为 UserVO 没有 password 字段
```

**三参数重载**：`BeanUtils.copyProperties(source, target, "忽略字段")`，`BookServiceImpl.updateBook` 中用到了：

```java
// 更新时忽略 stock 字段（stock 需要特殊处理，不能直接覆盖）
BeanUtils.copyProperties(updateDTO, book, "stock");
```

> ⚠️ **`BeanUtils.copyProperties` 的坑**：
> 1. 按**属性名**匹配，类型不同或名称不同的字段不会被复制（如 Entity 的 `categoryId` 和 VO 的 `categoryName` 不会互拷）。
> 2. 源对象的 null 值会覆盖目标对象的非 null 值——所以更新操作要小心，本项目用三参数版本忽略特定字段。
> 3. 性能一般（反射实现），但对 CRUD 场景足够。大型项目可考虑 MapStruct（编译期生成代码，性能更好）。

### 5.7 为什么不能直接用 Entity 接收请求/返回响应？

这是初学者最常问的问题。本项目的设计给出了明确答案：

| 问题 | 如果直接用 Entity | 本项目的解法 |
|------|-------------------|-------------|
| **敏感字段泄露** | `User` 实体有 `password` 字段，直接返回会把 BCrypt 密文暴露给前端 | `UserVO` 没有 `password` 字段，`BeanUtils.copyProperties` 自动忽略 |
| **字段不匹配** | 前端要展示 `categoryName`，但 `Book` 实体只有 `categoryId` | `BookVO` 增加 `categoryName`，toVO 时关联查询补充 |
| **计算字段** | 前端要知道"是否可借"，但 `Book` 只有 `stock` 数字 | `BookVO.available = stock > 0`，toVO 时计算 |
| **入参校验** | Entity 字段上不能加 `@NotBlank`（数据库字段可能允许 null），且新增和更新的校验规则不同 | DTO 独立定义校验规则，`BookAddDTO` 必填、`BookUpdateDTO` 全可选 |
| **前后端解耦** | 数据库表结构变更（加字段/改字段名）会直接影响前端接口 | Entity 变了不影响 VO，转换层做隔离 |
| **部分更新** | 更新时只传部分字段，用 Entity 接收会把未传字段当成 null 覆盖数据库 | `BookUpdateDTO` 全字段可选，Service 层只更新非空字段 |

> **核心原则**：DTO、Entity、VO 是三个**独立演化**的模型，变化的原因和频率不同。把它们混在一起，任何一方的变更都会波及其他方——这就是"分层"在数据模型层面的体现。

## 六、横切关注点：异常处理与用户上下文

除了四层主体，本项目还有两个贯穿各层的横切组件，理解它们对掌握整体架构很重要。

### 6.1 业务异常体系 —— `BusinessException` + `ResultCode`

Service 层遇到业务错误时**不返回 null 或错误码**，而是直接抛异常：

```java
if (user == null) {
    throw new BusinessException(ResultCode.USERNAME_NOT_FOUND);
}
```

`BusinessException` 继承 `RuntimeException`（非受检异常，不需要方法声明 `throws`），携带错误码和消息：

```java
public class BusinessException extends RuntimeException {
    private final Integer code;

    public BusinessException(ResultCode resultCode) {
        super(resultCode.getMessage());
        this.code = resultCode.getCode();
    }
    // 还有自定义 code+message、仅 message 两个构造器
}
```

**为什么用异常而不是返回错误码？**
- 业务错误是"异常路径"，用异常可以中断正常流程，避免层层判断返回值。
- 异常可以携带丰富的上下文（错误码、消息），由统一的处理器集中处理。
- `@Transactional` 遇到异常自动回滚——如果用返回错误码的方式，事务不会回滚。

### 6.2 全局异常处理器 —— `GlobalExceptionHandler`

```java
@Slf4j
@RestControllerAdvice   // = @ControllerAdvice + @ResponseBody，拦截所有 Controller 的异常
public class GlobalExceptionHandler {

    @ExceptionHandler(BusinessException.class)
    public Result<Void> handleBusinessException(BusinessException e) {
        log.warn("业务异常: code={}, message={}", e.getCode(), e.getMessage());
        return Result.error(e.getCode(), e.getMessage());
    }

    @ExceptionHandler(MethodArgumentNotValidException.class)
    @ResponseStatus(HttpStatus.BAD_REQUEST)
    public Result<Void> handleMethodArgumentNotValidException(...) {
        // 收集所有字段校验错误，拼接成消息
        String message = e.getBindingResult().getFieldErrors().stream()
                .map(error -> error.getField() + ": " + error.getDefaultMessage())
                .collect(Collectors.joining("; "));
        return Result.error(ResultCode.PARAM_ERROR.getCode(), message);
    }

    @ExceptionHandler(Exception.class)   // 兜底：所有未捕获的异常
    @ResponseStatus(HttpStatus.INTERNAL_SERVER_ERROR)
    public Result<Void> handleException(Exception e) {
        log.error("系统内部错误", e);
        return Result.error(ResultCode.ERROR.getCode(), "系统内部错误，请联系管理员");
    }
}
```

`@RestControllerAdvice` + `@ExceptionHandler` 的组合实现了**异常统一处理**：
- Controller 和 Service 中抛出的任何异常都会被这里捕获，不会直接暴露给前端。
- 不同类型的异常有不同的处理方法（业务异常、参数校验异常、JSON 解析异常、系统异常）。
- 最终都返回统一的 `Result` 格式，前端只需判断 `code` 字段。

> 异常处理优先级：**具体异常 > 通用异常**。`BusinessException` 是 `Exception` 的子类，抛出 `BusinessException` 时会匹配到 `handleBusinessException` 而不是兜底的 `handleException`。

### 6.3 当前用户上下文 —— `UserContext`

```java
public class UserContext {
    private static final ThreadLocal<LoginUser> CURRENT_USER = new ThreadLocal<>();

    public static void setCurrentUser(LoginUser user) { CURRENT_USER.set(user); }
    public static Long getCurrentUserId() { ... }
    public static boolean isAdmin() { ... }
    public static void clear() { CURRENT_USER.remove(); }
}
```

- **ThreadLocal**：每个线程有独立的变量副本，HTTP 请求处理在一个线程内完成，所以可以安全地存储当前用户信息。
- **设置时机**：JWT 拦截器（`JwtInterceptor`）解析请求头中的 Token，取出 userId/username/role，封装成 `LoginUser` 调用 `setCurrentUser`。
- **使用时机**：Controller 中 `UserContext.getCurrentUserId()` 获取当前用户 ID（借阅时用）、`UserContext.isAdmin()` 判断管理员权限。
- **清除时机**：请求结束时拦截器调用 `clear()`，防止线程池复用导致用户信息串号（内存泄漏 + 数据安全问题）。

> 这是"请求级上下文"的标准实现。替代方案是 Spring Security 的 `SecurityContextHolder`，原理相同（也是 ThreadLocal）。

## 七、第二阶段小结

| 层 | 学到什么 |
|----|----------|
| **Entity** | `@TableName`/`@TableId`/`@TableField`/`@TableLogic` 注解；`MyMetaObjectHandler` 自动填充 createTime/updateTime；逻辑删除的实际行为；BigDecimal 处理金额 |
| **Mapper** | `BaseMapper<T>` 提供 17 个 CRUD 方法；`@Select`/`@Update` 自定义 SQL；原子操作防超卖（`WHERE stock >= count`）；分页插件 `PaginationInnerInterceptor`；自定义 SQL 需手动加 `deleted = 0` |
| **Service** | `IService`/`ServiceImpl` 接口+实现分离；`@Transactional(rollbackFor = Exception.class)` 声明式事务；`LambdaQueryWrapper` 动态条件构建；借阅流程融合分布式锁+原子操作+事务+MQ；循环依赖的规避（注入 Mapper 而非 Service） |
| **Controller** | `@RestController` + `@RequestMapping` RESTful 设计；HTTP 方法语义（GET/POST/PUT/DELETE）；`@RequestBody`/`@PathVariable`/`@RequestParam` 参数绑定；`@Valid` 参数校验；`Result<T>` 统一响应；手动权限校验（UserContext.isAdmin） |
| **DTO→Entity→VO** | 三者面向不同受众、独立演化；`BeanUtils.copyProperties` 按名拷贝；VO 补充关联信息（categoryName/username/bookTitle）和计算字段（available/overdue/remainingDays）；DTO 携带校验注解；Entity 不直接暴露给前端（防敏感字段泄露、解耦） |
| **横切组件** | `BusinessException` + `ResultCode` 错误码体系；`@RestControllerAdvice` 全局异常统一处理；`UserContext` ThreadLocal 请求级用户上下文 |

**第二阶段的核心认知**：分层架构不是"把代码分到不同包里"这么简单，而是**每一层有明确的输入输出契约**——Controller 收 DTO 返 VO，Service 做业务和转换，Mapper 管数据存取。DTO/Entity/VO 三种对象的分离，是"数据模型也分层"的体现，保证了前端接口、业务逻辑、数据库表结构三者可以独立演化。
