## 一、从项目代码开始

看 `BookController` 里的分页接口：

```java
@GetMapping
public Result<IPage<BookVO>> pageBooks(
        @RequestParam(defaultValue = "1") Integer pageNum,
        @RequestParam(defaultValue = "10") Integer pageSize,
        @RequestParam(required = false) String keyword,
        @RequestParam(required = false) Long categoryId) {
    IPage<BookVO> page = bookService.pageBooks(pageNum, pageSize, keyword, categoryId);
    return Result.success(page);
}
```

看 `BookServiceImpl` 里的分页实现：

```java
@Override
public IPage<BookVO> pageBooks(Integer pageNum, Integer pageSize, String keyword, Long categoryId) {
    // 1. 构建分页对象：当前页、每页条数
    Page<Book> page = new Page<>(pageNum, pageSize);

    // 2. 构建查询条件
    LambdaQueryWrapper<Book> wrapper = new LambdaQueryWrapper<>();
    wrapper.like(StringUtils.hasText(keyword), Book::getTitle, keyword)      // 书名模糊查询
           .or()
           .like(StringUtils.hasText(keyword), Book::getAuthor, keyword)     // 作者模糊查询
           .eq(categoryId != null, Book::getCategoryId, categoryId)          // 分类精确查询
           .eq(Book::getDeleted, 0)                                            // 未删除
           .orderByDesc(Book::getCreateTime);                                  // 按创建时间倒序

    // 3. 执行分页查询
    IPage<Book> bookPage = bookMapper.selectPage(page, wrapper);

    // 4. 转换为 VO（补充分类名称、是否可借等）
    List<BookVO> voList = bookPage.getRecords().stream()
            .map(this::toVO)
            .collect(Collectors.toList());

    // 5. 构建返回的分页对象
    Page<BookVO> resultPage = new Page<>();
    resultPage.setRecords(voList);
    resultPage.setTotal(bookPage.getTotal());
    resultPage.setCurrent(bookPage.getCurrent());
    resultPage.setSize(bookPage.getSize());
    resultPage.setPages(bookPage.getPages());

    return resultPage;
}
```

## 二、为什么需要分页？

### 不分页会怎样？

如果图书有 10000 本，不分页一次性查询：
1. **数据库压力大**：一次返回 10000 条数据，内存占用大，查询慢
2. **网络传输慢**：10000 条数据的 JSON 可能有几 MB，传输慢
3. **前端渲染卡**：浏览器渲染 10000 行表格，卡顿甚至崩溃
4. **用户体验差**：用户不需要一次看 10000 条，只需要看当前页

### 分页的作用

1. **减少数据量**：每次只查一页（如 10 条），查询快、传输快、渲染快
2. **提升用户体验**：用户可以翻页浏览，每页数据量适中
3. **保护数据库**：避免大查询拖垮数据库

## 三、MyBatis-Plus 分页插件配置

看 `MyBatisPlusConfig`：

```java
@Configuration
public class MyBatisPlusConfig {

    @Bean
    public MybatisPlusInterceptor mybatisPlusInterceptor() {
        MybatisPlusInterceptor interceptor = new MybatisPlusInterceptor();
        // 添加分页插件
        interceptor.addInnerInterceptor(new PaginationInnerInterceptor(DbType.MYSQL));
        return interceptor;
    }
}
```

### 分页插件的原理

`PaginationInnerInterceptor` 是 MyBatis-Plus 的分页拦截器，它的原理是：

1. 拦截 `selectPage` 方法的 SQL 执行
2. 先执行一条 **COUNT 查询**，获取总记录数
3. 再在原 SQL 后面拼接 **LIMIT 子句**，只查询当前页的数据
4. 把总记录数和当前页数据封装到 `IPage` 对象返回

比如原 SQL：
```sql
SELECT * FROM book WHERE deleted = 0 ORDER BY create_time DESC
```

分页插件会变成两条 SQL：
```sql
-- 1. 查总记录数
SELECT COUNT(*) FROM book WHERE deleted = 0

-- 2. 查当前页数据（第1页，每页10条）
SELECT * FROM book WHERE deleted = 0 ORDER BY create_time DESC LIMIT 0, 10
```

`LIMIT 0, 10` 表示从第 0 条开始（偏移量），取 10 条。第 2 页就是 `LIMIT 10, 10`，第 3 页就是 `LIMIT 20, 10`。

### 为什么需要配置分页插件？

MyBatis-Plus 的 `selectPage` 方法本身不会自动分页，如果不配置分页插件，它会执行普通查询返回所有数据（total 为 0）。配置了 `PaginationInnerInterceptor` 后，才会自动拼接 COUNT 和 LIMIT。

## 四、IPage 接口详解

`IPage` 是 MyBatis-Plus 分页的核心接口，`Page` 是它的实现类。

### IPage 的核心属性

| 属性 | 类型 | 说明 | 示例 |
|------|------|------|------|
| `records` | List<T> | 当前页的数据列表 | 10 本图书 |
| `total` | long | 总记录数 | 156（共156本） |
| `current` | long | 当前页码 | 1（第1页） |
| `size` | long | 每页条数 | 10（每页10条） |
| `pages` | long | 总页数 | 16（156/10=15.6，向上取整16页） |

### 前端收到的分页 JSON

```json
{
  "code": 20000,
  "message": "操作成功",
  "data": {
    "records": [
      { "id": 1, "title": "Java核心技术", "author": "Cay", ... },
      { "id": 2, "title": "深入理解Java虚拟机", "author": "周志明", ... }
    ],
    "total": 156,
    "current": 1,
    "size": 10,
    "pages": 16
  }
}
```

前端用 `res.data.records` 渲染表格，用 `res.data.total` 显示总条数和计算分页器。

### Page 类的常用方法

```java
// 构建分页对象
Page<Book> page = new Page<>(pageNum, pageSize);  // 当前页、每页条数

// 常用方法
page.getCurrent();   // 当前页
page.getSize();      // 每页条数
page.getTotal();     // 总记录数
page.getPages();     // 总页数
page.getRecords();   // 当前页数据

// 不查总记录数（优化性能，只需要列表不需要总数时用）
page.setSearchCount(false);
```

```
    ▼

    ▼

    │
    ▼
loadBooks() 拿到数据
    │  setBooks(res.data.records)  → 更新表格数据
    │  setTotal(res.data.total)     → 更新总条数
    ▼

```

## 六、自定义分页 SQL（带 JOIN 的复杂查询）

上面的分页查询是单表查询（book 表），用 `selectPage` 就行。但如果需要多表 JOIN 查询（比如借阅记录需要关联用户表和图书表），就需要自定义 SQL。

### 6.1 Mapper 接口定义

```java
public interface BorrowRecordMapper extends BaseMapper<BorrowRecord> {

    // 自定义分页查询：关联用户表和图书表
    IPage<BorrowRecordVO> selectBorrowRecordPage(
            Page<BorrowRecordVO> page,
            @Param("userId") Long userId,
            @Param("keyword") String keyword);
}
```

注意：
- 第一个参数必须是 `Page` 对象（分页插件会识别）
- 返回值是 `IPage<VO>`
- 其他参数用 `@Param` 标注

### 6.2 XML 写 SQL

```xml
<!-- BorrowRecordMapper.xml -->
<select id="selectBorrowRecordPage" resultType="com.example.library.vo.BorrowRecordVO">
    SELECT
        br.id,
        br.user_id,
        u.username,
        br.book_id,
        b.title AS book_title,
        b.author,
        br.borrow_date,
        br.due_date,
        br.return_date,
        br.status,
        br.fine
    FROM borrow_record br
    LEFT JOIN sys_user u ON br.user_id = u.id
    LEFT JOIN book b ON br.book_id = b.id
    <where>
        br.deleted = 0
        <if test="userId != null">
            AND br.user_id = #{userId}
        </if>
        <if test="keyword != null and keyword != ''">
            AND (b.title LIKE CONCAT('%', #{keyword}, '%') OR u.username LIKE CONCAT('%', #{keyword}, '%'))
        </if>
    </where>
    ORDER BY br.borrow_date DESC
</select>
```

分页插件会自动：
1. 先执行 COUNT：`SELECT COUNT(*) FROM (上面的SQL) tmp`（或智能优化 COUNT）
2. 再在 SQL 后面拼 `LIMIT offset, size`

### 6.3 Service 调用

```java
@Override
public IPage<BorrowRecordVO> pageBorrowRecords(Integer pageNum, Integer pageSize, Long userId, String keyword) {
    Page<BorrowRecordVO> page = new Page<>(pageNum, pageSize);
    return borrowRecordMapper.selectBorrowRecordPage(page, userId, keyword);
}
```

### 项目里的实际情况

项目里的借阅记录分页（AllBorrows / MyBorrows）应该用了自定义 SQL 关联查询。如果项目里目前是单表查询后在 Service 里补信息（循环查用户和图书），那是**N+1 查询问题**，应该优化成 JOIN 分页查询。

## 七、分页查询的性能问题

### 7.1 深分页问题

当页码很大时（如第 10000 页，每页 10 条），`LIMIT 99990, 10` 会很慢，因为 MySQL 需要扫描并跳过前 99990 条数据。

```sql
-- 深分页：慢
SELECT * FROM book WHERE deleted = 0 ORDER BY id LIMIT 99990, 10;
```

**优化方案：游标分页（基于上一页最后一条的 ID）**

```sql
-- 优化：用上一页最后一条的 id 作为条件，避免大偏移
SELECT * FROM book WHERE deleted = 0 AND id < 99991 ORDER BY id DESC LIMIT 10;
```

这种方式不需要跳过大量数据，利用主键索引，速度快。但缺点是不能跳页（只能上一页/下一页），适合信息流场景（如微博、朋友圈）。

项目里是后台管理系统，页码不会特别大，用普通分页即可。

### 7.2 COUNT 查询优化

分页插件会先执行 COUNT 查询，如果表数据量大，COUNT 可能慢。

优化方案：
1. **不需要总条数时关闭 COUNT**：`page.setSearchCount(false)`，只查当前页数据
2. **近似 COUNT**：用 `EXPLAIN` 里的 rows 估算，不精确但快
3. **缓存总条数**：总条数变化不频繁时，缓存到 Redis

项目里数据量小，COUNT 不是问题。

### 7.3 排序字段加索引

分页查询一般都有 ORDER BY，排序字段应该加索引，否则会出现 filesort（文件排序，慢）。

项目里按 `create_time DESC` 排序，可以给 `create_time` 加索引，或者用主键 id 排序（主键自带索引）。

## 八、前端分页配合

看项目里前端怎么处理分页：

### 8.1 状态管理

```tsx
const [pageNum, setPageNum] = useState(1)      // 当前页
const [pageSize, setPageSize] = useState(10)   // 每页条数
const [total, setTotal] = useState(0)           // 总记录数
const [books, setBooks] = useState<Book[]>([])  // 当前页数据
```

### 8.2 useEffect 监听翻页

```tsx
useEffect(() => {
  loadBooks()  // pageNum 或 pageSize 变化时重新加载
}, [pageNum, pageSize])
```

### 8.3 Table 分页配置

```tsx
<Table
  dataSource={books}
  columns={columns}
  rowKey="id"
  loading={loading}
  pagination={{
    current: pageNum,                          // 当前页
    pageSize,                                   // 每页条数
    total,                                      // 总记录数
    showSizeChanger: true,                      // 显示每页条数选择器
    pageSizeOptions: ['10', '20', '50', '100'], // 可选每页条数
    showTotal: (total) => `共 ${total} 条`,    // 显示总条数
    onChange: (page, size) => {
      setPageNum(page)   // 更新页码，触发 useEffect 重新加载
      setPageSize(size)  // 更新每页条数
    },
  }}
/>
```

### 8.4 搜索时重置页码

```tsx
const handleSearch = () => {
  setPageNum(1)  // 搜索时重置到第1页
  loadBooks()    // 手动加载（因为 keyword 不在 useEffect 依赖里）
}
```

注意：搜索条件（keyword、categoryId）变化时，需要重置到第1页并重新加载。项目里是手动调用 `loadBooks()`，而不是把 keyword 加到 useEffect 依赖里（因为输入时每次按键都会触发，不需要每次都搜索，只有点击搜索按钮才搜索）。

## 十一、自测题

### Q1：MyBatis-Plus 分页插件怎么配置？原理是什么？

<details>
<summary>点击查看答案</summary>

**配置**：
```java
@Configuration
public class MyBatisPlusConfig {
    @Bean
    public MybatisPlusInterceptor mybatisPlusInterceptor() {
        MybatisPlusInterceptor interceptor = new MybatisPlusInterceptor();
        interceptor.addInnerInterceptor(new PaginationInnerInterceptor(DbType.MYSQL));
        return interceptor;
    }
}
```
在 `MybatisPlusInterceptor` 里添加 `PaginationInnerInterceptor`，指定数据库类型为 MySQL。

**原理**：
`PaginationInnerInterceptor` 是一个 MyBatis 拦截器，拦截 `selectPage` 方法的 SQL 执行：
1. 先执行一条 COUNT 查询（`SELECT COUNT(*) FROM (原SQL)` 或智能优化），获取总记录数，设置到 page.total
2. 再在原 SQL 后面拼接 LIMIT 子句（MySQL 是 `LIMIT offset, size`），只查询当前页的数据
3. 把总记录数和当前页数据封装到 IPage 对象返回

如果不配置分页插件，`selectPage` 会执行普通查询返回所有数据（total 为 0），不会真正分页。

</details>

### Q2：IPage 接口有哪些核心属性？前端怎么使用？

<details>
<summary>点击查看答案</summary>

**IPage 核心属性**：
- `records`（List<T>）：当前页的数据列表
- `total`（long）：总记录数
- `current`（long）：当前页码
- `size`（long）：每页条数
- `pages`（long）：总页数（total / size 向上取整）

```tsx
setTotal(res.data.total)

// Table 组件分页配置

  dataSource={books}
  pagination={{
    current: pageNum,
    pageSize,
    total,
    onChange: (page, size) => { setPageNum(page); setPageSize(size) },
  }}
/>
```

前端用 `records` 渲染当前页数据，用 `total` 计算分页器显示（总条数、总页数、页码按钮）。翻页时更新 pageNum/pageSize，触发 useEffect 重新加载数据。

### Q3：单表分页和多表 JOIN 分页分别怎么实现？

<details>
<summary>点击查看答案</summary>

**单表分页**：用 MyBatis-Plus 内置的 `selectPage` 方法
```java
Page<Book> page = new Page<>(pageNum, pageSize);
LambdaQueryWrapper<Book> wrapper = new LambdaQueryWrapper<>();
wrapper.like(Book::getTitle, keyword).eq(Book::getDeleted, 0);
IPage<Book> result = bookMapper.selectPage(page, wrapper);
```
配合 QueryWrapper/LambdaQueryWrapper 构建查询条件，不需要写 XML。

**多表 JOIN 分页**：自定义 Mapper 方法 + XML 写 SQL
```java
// Mapper 接口：第一个参数必须是 Page
IPage<BorrowRecordVO> selectBorrowRecordPage(
    Page<BorrowRecordVO> page,
    @Param("userId") Long userId);
```
```xml
<!-- XML：写 JOIN 查询，分页插件自动加 COUNT 和 LIMIT -->
<select id="selectBorrowRecordPage" resultType="BorrowRecordVO">
  SELECT br.*, u.username, b.title
  FROM borrow_record br
  LEFT JOIN sys_user u ON br.user_id = u.id
  LEFT JOIN book b ON br.book_id = b.id
  WHERE br.deleted = 0
  <if test="userId != null">AND br.user_id = #{userId}</if>
  ORDER BY br.borrow_date DESC
</select>
```
分页插件会自动识别第一个 Page 参数，先执行 COUNT 再拼 LIMIT。

**关键区别**：单表用 selectPage + QueryWrapper（零 XML），多表用自定义方法 + XML（写 JOIN SQL）。两者都依赖分页插件。

</details>

### Q4：分页查询有什么性能问题？怎么优化？

<details>
<summary>点击查看答案</summary>

**1. 深分页问题**：页码很大时（如 LIMIT 99990, 10），MySQL 需要扫描并跳过前 99990 条，很慢。
- 优化：游标分页，用上一页最后一条的 ID 作为条件（`WHERE id < lastId ORDER BY id DESC LIMIT 10`），利用主键索引避免大偏移。缺点是不能跳页，适合信息流场景。

**2. COUNT 查询慢**：数据量大时 COUNT(*) 可能慢。
- 优化：①不需要总条数时 `page.setSearchCount(false)` 关闭 COUNT；②用近似 COUNT（EXPLAIN 的 rows）；③缓存总条数到 Redis。

**3. 排序无索引**：ORDER BY 的字段没有索引，会导致 filesort（文件排序），慢。
- 优化：给排序字段加索引，或用主键 id 排序（主键自带聚簇索引）。

**4. SELECT * 问题**：查询所有字段，浪费 IO 和内存。
- 优化：只查需要的字段，VO 里只包含页面需要的字段。

**5. 大 OFFSET + JOIN**：深分页 + 多表 JOIN 更慢。
- 优化：先分页查出主表 ID，再用 ID 关联查询其他表（延迟关联）。

项目里是后台管理系统，数据量小，普通分页即可。生产项目大表需要考虑这些优化。

</details>

### Q5：前端翻页时，数据是怎么加载的？搜索时为什么要重置页码？

<details>
<summary>点击查看答案</summary>

**前端翻页加载流程**：
1. 用户点击分页器的"第2页"
2. Table 组件的 onChange 回调触发，调用 `setPageNum(2)` 和 `setPageSize(10)`
3. pageNum 状态变化，触发组件重新渲染
4. useEffect 检测到依赖 `[pageNum, pageSize]` 变化，执行 `loadBooks()`
5. `loadBooks()` 调用 `pageBooks({ keyword, categoryId, pageNum: 2, pageSize: 10 })`
6. 后端返回第2页数据，`setBooks(res.data.records)` 更新表格数据，`setTotal(res.data.total)` 更新总条数
7. React 重新渲染，Table 显示第2页数据

**搜索时重置页码的原因**：
搜索条件变化后，符合条件的总记录数可能变少了。如果当前在第5页，搜索后符合条件的只有3页，第5页就没有数据了。所以搜索时必须重置到第1页，确保有数据显示。

项目里的实现：
```tsx
const handleSearch = () => {
  setPageNum(1)  // 重置到第1页
  loadBooks()    // 手动加载（keyword 不在 useEffect 依赖里，因为输入时不需要每次都搜索）
}
```

注意：keyword 没有加到 useEffect 依赖里，因为用户在输入框输入时每次按键都会改变 keyword，但不需要每次都发请求搜索，只有点击"搜索"按钮或按回车时才搜索。所以搜索是手动调用 loadBooks()，而不是通过 useEffect 自动触发。

</details>

## 十二、面试题

### 面试题1：MyBatis-Plus 分页怎么实现的？分页插件的原理是什么？

> **答题要点**：
> 1. **配置**：注册 `MybatisPlusInterceptor` Bean，添加 `PaginationInnerInterceptor(DbType.MYSQL)` 内部拦截器
> 2. **使用**：
>    - 单表：`mapper.selectPage(new Page<>(pageNum, pageSize), queryWrapper)`
>    - 多表：自定义 Mapper 方法，第一个参数为 Page，XML 写 JOIN SQL，分页插件自动处理
> 3. **原理**：PaginationInnerInterceptor 是 MyBatis 拦截器，拦截查询方法：
>    - 先执行 COUNT 查询（智能优化，如去掉 SELECT 字段改为 COUNT(*)，去掉 ORDER BY），获取总记录数
>    - 再在原 SQL 后拼接数据库方言的分页语句（MySQL 用 `LIMIT offset, size`，Oracle 用 ROWNUM，PostgreSQL 用 LIMIT/OFFSET）
>    - 把 total 和当前页数据封装到 IPage 返回
> 4. **IPage 属性**：records（当前页数据）、total（总记录数）、current（当前页）、size（每页条数）、pages（总页数）
> 5. **注意**：不配置分页插件的话 selectPage 不会真正分页，会返回所有数据且 total=0
> 6. **性能优化**：深分页用游标分页、不需要总数时 setSearchCount(false)、排序字段加索引、大表用延迟关联（先分页查ID再JOIN）

### 面试题2：深分页怎么优化？游标分页和普通分页的区别？

> **答题要点**：
> 1. **深分页问题**：`LIMIT 100000, 10` 时，MySQL 需要扫描并跳过前 100000 条记录，只返回 10 条，效率极低。原因是 LIMIT 的 offset 越大，需要扫描和丢弃的数据越多。
> 2. **游标分页优化**：利用上一页最后一条记录的位置（通常是主键 ID 或排序字段），作为下一页的查询条件，避免大偏移。
>    ```sql
>    -- 普通分页（慢）
>    SELECT * FROM book WHERE deleted=0 ORDER BY id LIMIT 100000, 10;
>    -- 游标分页（快）
>    SELECT * FROM book WHERE deleted=0 AND id < 100001 ORDER BY id DESC LIMIT 10;
>    ```
>    利用主键索引范围扫描，不需要跳过大量数据，性能稳定。
> 3. **区别**：
>    - 普通分页：支持跳页（可以直接跳到第N页），但深分页慢；需要 COUNT 查总数
>    - 游标分页：只能上一页/下一页（不能跳页），性能稳定不随页码增加而下降；不需要 COUNT（或用 hasMore 标记）
> 4. **适用场景**：
>    - 普通分页：后台管理系统、需要跳页、数据量小
>    - 游标分页：信息流（微博、朋友圈、商品列表）、无限滚动、数据量大
> 5. **其他优化**：
>    - 延迟关联：先分页查出主键 ID，再用 ID 关联查询其他表，减少 JOIN 时扫描的数据量
>    - 覆盖索引：查询字段都在索引里，避免回表
>    - 业务限制：限制最大页码（如最多查100页），防止恶意深分页
