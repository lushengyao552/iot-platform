# 第8课：统一返回结果 + 全局异常处理——`Result`、`@RestControllerAdvice`、`@ExceptionHandler`

> **本课目标**：理解项目为什么要统一返回格式和全局异常处理，掌握 `Result<T>`、`ResultCode`、`@RestControllerAdvice`、`@ExceptionHandler` 的用法和底层原理。学完这课，你应该能独立设计一套统一响应和异常处理体系。

---

## 一、从项目代码开始

看 `BookController` 的返回值：

```java
@GetMapping("/{id}")
public Result<BookVO> getBookById(@PathVariable Long id) {
    BookVO bookVO = bookService.getBookById(id);
    return Result.success(bookVO);   // ← 统一返回 Result
}
```

再看 `BookServiceImpl` 里抛异常：

```java
Book book = getById(id);
if (book == null) {
    throw new BusinessException(ResultCode.BOOK_NOT_FOUND);   // ← 抛业务异常
}
```

最后看 `GlobalExceptionHandler` 怎么处理：

```java
@Slf4j
@RestControllerAdvice   // ← 全局异常处理器
public class GlobalExceptionHandler {

    @ExceptionHandler(BusinessException.class)   // ← 处理业务异常
    public Result<Void> handleBusinessException(BusinessException e) {
        log.warn("业务异常: code={}, message={}", e.getCode(), e.getMessage());
        return Result.error(e.getCode(), e.getMessage());
    }

    @ExceptionHandler(Exception.class)   // ← 兜底处理所有异常
    @ResponseStatus(HttpStatus.INTERNAL_SERVER_ERROR)
    public Result<Void> handleException(Exception e) {
        log.error("系统内部错误", e);
        return Result.error(ResultCode.ERROR.getCode(), "系统内部错误，请联系管理员");
    }
}
```

三个组件配合：
1. **`Result<T>`**：统一返回格式，所有接口都返回它
2. **`BusinessException`**：业务异常，Service 层抛出
3. **`GlobalExceptionHandler`**：全局异常处理器，捕获异常并转换成统一的 `Result` 返回

## 二、为什么需要统一返回格式？

### 没有统一格式的混乱场景

如果每个 Controller 自己决定返回什么：

```java
// 接口1：返回对象
@GetMapping("/{id}")
public Book getBookById(@PathVariable Long id) {
    return bookService.getById(id);
}

// 接口2：返回字符串
@PostMapping("/login")
public String login(@RequestBody LoginDTO dto) {
    return "登录成功，token: xxx";
}

// 接口3：返回 Map
@GetMapping("/list")
public Map<String, Object> list() {
    Map<String, Object> map = new HashMap<>();
    map.put("data", bookService.list());
    map.put("total", 100);
    return map;
}

// 接口4：出错直接抛异常，返回 500 错误页
@DeleteMapping("/{id}")
public void delete(@PathVariable Long id) {
    bookService.removeById(id);
}
```

前端的噩梦：
- 每个接口返回格式不一样，要写不同的解析逻辑
- 成功和失败的判断方式不一样（有的看 HTTP 状态码，有的看返回字段）
- 错误信息格式不统一，有的是 HTML 错误页，有的是字符串
- 新增接口时，后端开发者各写各的，没有规范

### 统一格式后的好处

所有接口都返回：

```json
{
  "code": 20000,
  "message": "操作成功",
  "data": { ... },
  "timestamp": 1693574400000
}
```

前端只需要一套解析逻辑：
```javascript
if (res.code === 20000) {
    // 成功，用 res.data
} else {
    // 失败，显示 res.message
}
```

好处：
1. **前端统一处理**：一套逻辑处理所有接口的响应和错误
2. **后端规范统一**：所有开发者遵循同一套返回格式
3. **成功/失败明确**：通过 `code` 字段判断，不依赖 HTTP 状态码
4. **错误信息友好**：业务异常返回具体的错误信息（如"图书不存在"），而不是 500 错误页
5. **便于扩展**：可以在 `Result` 里加统一字段（如 `timestamp`、`traceId`）

## 三、`Result<T>`——统一响应封装

### 完整代码

```java
@Data
public class Result<T> implements Serializable {

    private Integer code;       // 状态码
    private String message;     // 提示信息
    private T data;             // 响应数据
    private Long timestamp;     // 时间戳

    private Result() {
        this.timestamp = System.currentTimeMillis();
    }

    private Result(Integer code, String message, T data) {
        this.code = code;
        this.message = message;
        this.data = data;
        this.timestamp = System.currentTimeMillis();
    }

    // 成功响应
    public static <T> Result<T> success() {
        return new Result<>(ResultCode.SUCCESS.getCode(), ResultCode.SUCCESS.getMessage(), null);
    }

    public static <T> Result<T> success(T data) {
        return new Result<>(ResultCode.SUCCESS.getCode(), ResultCode.SUCCESS.getMessage(), data);
    }

    // 失败响应
    public static <T> Result<T> error(String message) {
        return new Result<>(ResultCode.ERROR.getCode(), message, null);
    }

    public static <T> Result<T> error(ResultCode resultCode) {
        return new Result<>(resultCode.getCode(), resultCode.getMessage(), null);
    }

    public static <T> Result<T> error(Integer code, String message) {
        return new Result<>(code, message, null);
    }

    // 便捷判断
    public boolean isSuccess() {
        return ResultCode.SUCCESS.getCode().equals(this.code);
    }
}
```

### 设计要点

1. **泛型 `T`**：`data` 字段的类型由调用时决定，可以是 `BookVO`、`IPage<BookVO>`、`String`、`Void` 等
2. **构造器私有**：只能通过静态方法 `success()`、`error()` 创建，保证所有 `Result` 对象都有正确的 code 和 message
3. **静态工厂方法**：`success()`、`success(data)`、`error(message)`、`error(resultCode)` 等，语义清晰，调用简洁
4. **时间戳**：每个响应自动带上 `timestamp`，前端可以用来判断服务器时间或做缓存控制
5. **`isSuccess()` 便捷方法**：方便在代码里判断是否成功

### 项目里的用法

```java
// 成功，无数据（删除接口）
return Result.success();

// 成功，带数据（查询接口）
return Result.success(bookVO);

// 成功，自定义消息 + 数据
return Result.success("操作成功", bookVO);

// 失败，自定义消息
return Result.error("ISBN 已存在");

// 失败，使用枚举状态码
return Result.error(ResultCode.BOOK_NOT_FOUND);

// 失败，自定义状态码 + 消息
return Result.error(ResultCode.PARAM_ERROR.getCode(), "ISBN 已存在");
```

## 四、`ResultCode`——状态码枚举

### 为什么需要状态码枚举？

如果状态码直接写数字（`return Result.error(40001, "图书不存在")`），会有问题：
- 数字容易写错（40001 写成 40010）
- 同一个错误在不同地方写了不同的状态码
- 不知道某个状态码是什么意思，得查文档

用枚举统一管理：

```java
@Getter
@AllArgsConstructor
public enum ResultCode {

    // 通用状态码
    SUCCESS(20000, "操作成功"),
    ERROR(50000, "系统内部错误"),
    PARAM_ERROR(40000, "参数错误"),
    PARAM_NOT_NULL(40001, "参数不能为空"),
    PARAM_TYPE_ERROR(40002, "参数类型错误"),

    // 认证相关
    UNAUTHORIZED(40100, "未登录或登录已过期"),
    TOKEN_INVALID(40101, "Token 无效"),
    TOKEN_EXPIRED(40102, "Token 已过期"),
    FORBIDDEN(40300, "没有权限访问"),

    // 用户相关
    USERNAME_NOT_FOUND(41001, "用户不存在"),
    USERNAME_EXISTS(41002, "用户名已存在"),
    PASSWORD_ERROR(41003, "密码错误"),
    USER_DISABLED(41004, "账号已被禁用"),

    // 图书相关
    BOOK_NOT_FOUND(42001, "图书不存在"),
    BOOK_OUT_OF_STOCK(42002, "图书库存不足"),
    BOOK_ALREADY_BORROWED(42003, "您已借阅此书，尚未归还"),

    // 借阅相关
    BORROW_RECORD_NOT_FOUND(43001, "借阅记录不存在"),
    BORROW_ALREADY_RETURNED(43002, "该书已归还"),
    BORROW_LIMIT_EXCEEDED(43003, "借阅数量已达上限"),

    // 分类相关
    CATEGORY_NOT_FOUND(44001, "分类不存在");

    private final Integer code;
    private final String message;
}
```

### 状态码设计规范

| 段位 | 含义 | 例子 |
|------|------|------|
| 2xxxx | 成功 | 20000 操作成功 |
| 4xxxx | 客户端错误（参数、认证、权限、业务） | 40000 参数错误、40100 未登录、40300 无权限 |
| 5xxxx | 服务端错误 | 50000 系统内部错误 |

项目里的细分：
- 40xxx：通用参数错误
- 41xxx：用户相关
- 42xxx：图书相关
- 43xxx：借阅相关
- 44xxx：分类相关

这样设计的好处：看到状态码就知道是哪个模块的什么错误。

## 五、`BusinessException`——业务异常

### 是什么？

业务异常是 Service 层在业务逻辑不满足时抛出的异常，比如：
- 图书不存在
- 库存不足
- 用户已借阅此书
- 没有管理员权限

### 完整代码

```java
@Getter
public class BusinessException extends RuntimeException {

    private final Integer code;

    public BusinessException(ResultCode resultCode) {
        super(resultCode.getMessage());
        this.code = resultCode.getCode();
    }

    public BusinessException(Integer code, String message) {
        super(message);
        this.code = code;
    }
}
```

### 为什么继承 `RuntimeException`？

Java 异常体系：

```
Throwable
├── Error（系统错误，如 OutOfMemoryError）
└── Exception
    ├── RuntimeException（运行时异常，非受检）
    │   ├── NullPointerException
    │   ├── IllegalArgumentException
    │   └── BusinessException（项目自定义）
    └── 受检异常（Checked Exception）
        ├── IOException
        ├── SQLException
        └── ...
```

**受检异常**：必须在方法签名上声明 `throws`，或者 try-catch 捕获，否则编译不通过。

**运行时异常（非受检）**：不需要声明 `throws`，也不需要强制捕获，编译能通过，运行时才会抛出。

`BusinessException` 继承 `RuntimeException` 的原因：
1. **不需要到处声明 `throws`**：Service 层的每个方法都可能抛业务异常，如果是受检异常，每个方法都要写 `throws BusinessException`，很麻烦
2. **配合 Spring 事务回滚**：Spring `@Transactional` 默认只回滚 `RuntimeException` 和 `Error`。如果 `BusinessException` 是受检异常，默认不会触发事务回滚（除非配置了 `rollbackFor = Exception.class`）
3. **业务异常是"不可恢复"的**：业务异常（如"图书不存在"）通常不需要调用者捕获后恢复，而是直接返回错误信息给前端。运行时异常更适合这种场景

### 项目里的用法

```java
// Service 层抛出业务异常
Book book = getById(id);
if (book == null) {
    throw new BusinessException(ResultCode.BOOK_NOT_FOUND);
}

if (book.getStock() <= 0) {
    throw new BusinessException(ResultCode.BOOK_OUT_OF_STOCK);
}

// 自定义消息
throw new BusinessException(ResultCode.PARAM_ERROR.getCode(), "ISBN 已存在");
```

Service 层只负责抛异常，不负责处理异常。异常由 `GlobalExceptionHandler` 统一捕获并转换成 `Result` 返回。

## 六、`@RestControllerAdvice`——全局异常处理器

### 是什么？

`@RestControllerAdvice` 是 Spring MVC 提供的**全局异常处理注解**，加在类上，表示这个类是全局异常处理器。

它本质是 `@ControllerAdvice` + `@ResponseBody` 的组合：
- `@ControllerAdvice`：全局控制器增强，拦截所有 Controller 的异常
- `@ResponseBody`：返回值直接写入响应体（序列化成 JSON）

### 底层原理

`@RestControllerAdvice` 基于 Spring AOP 实现：
1. Spring 容器启动时，扫描所有 `@ControllerAdvice` 标记的类
2. 当 Controller 方法抛出异常时，`DispatcherServlet` 不直接返回 500 错误
3. 而是先找 `@ExceptionHandler` 标记的方法，看有没有匹配的异常类型
4. 找到匹配的方法就调用它，把返回值（`Result`）序列化成 JSON 返回
5. 找不到匹配的方法，就走默认的错误处理（500 错误页）

### 完整代码

```java
@Slf4j
@RestControllerAdvice
public class GlobalExceptionHandler {

    // ========== 业务异常 ==========
    @ExceptionHandler(BusinessException.class)
    public Result<Void> handleBusinessException(BusinessException e) {
        log.warn("业务异常: code={}, message={}", e.getCode(), e.getMessage());
        return Result.error(e.getCode(), e.getMessage());
    }

    // ========== 参数校验异常 ==========
    @ExceptionHandler(MethodArgumentNotValidException.class)
    @ResponseStatus(HttpStatus.BAD_REQUEST)
    public Result<Void> handleMethodArgumentNotValidException(MethodArgumentNotValidException e) {
        String message = e.getBindingResult().getFieldErrors().stream()
                .map(error -> error.getField() + ": " + error.getDefaultMessage())
                .collect(Collectors.joining("; "));
        log.warn("参数校验失败: {}", message);
        return Result.error(ResultCode.PARAM_ERROR.getCode(), message);
    }

    @ExceptionHandler(BindException.class)
    @ResponseStatus(HttpStatus.BAD_REQUEST)
    public Result<Void> handleBindException(BindException e) {
        String message = e.getBindingResult().getFieldErrors().stream()
                .map(FieldError::getDefaultMessage)
                .collect(Collectors.joining("; "));
        return Result.error(ResultCode.PARAM_ERROR.getCode(), message);
    }

    @ExceptionHandler(ConstraintViolationException.class)
    @ResponseStatus(HttpStatus.BAD_REQUEST)
    public Result<Void> handleConstraintViolationException(ConstraintViolationException e) {
        String message = e.getConstraintViolations().stream()
                .map(ConstraintViolation::getMessage)
                .collect(Collectors.joining("; "));
        return Result.error(ResultCode.PARAM_ERROR.getCode(), message);
    }

    @ExceptionHandler(MissingServletRequestParameterException.class)
    @ResponseStatus(HttpStatus.BAD_REQUEST)
    public Result<Void> handleMissingServletRequestParameterException(MissingServletRequestParameterException e) {
        String message = "缺少必填参数: " + e.getParameterName();
        return Result.error(ResultCode.PARAM_NOT_NULL.getCode(), message);
    }

    @ExceptionHandler(MethodArgumentTypeMismatchException.class)
    @ResponseStatus(HttpStatus.BAD_REQUEST)
    public Result<Void> handleMethodArgumentTypeMismatchException(MethodArgumentTypeMismatchException e) {
        String message = String.format("参数 [%s] 类型错误，期望类型: %s",
                e.getName(), e.getRequiredType() != null ? e.getRequiredType().getSimpleName() : "未知");
        return Result.error(ResultCode.PARAM_TYPE_ERROR.getCode(), message);
    }

    @ExceptionHandler(HttpMessageNotReadableException.class)
    @ResponseStatus(HttpStatus.BAD_REQUEST)
    public Result<Void> handleHttpMessageNotReadableException(HttpMessageNotReadableException e) {
        return Result.error(ResultCode.PARAM_ERROR.getCode(), "请求体格式错误，请检查 JSON 格式");
    }

    // ========== 系统异常（兜底） ==========
    @ExceptionHandler(Exception.class)
    @ResponseStatus(HttpStatus.INTERNAL_SERVER_ERROR)
    public Result<Void> handleException(Exception e) {
        log.error("系统内部错误", e);
        return Result.error(ResultCode.ERROR.getCode(), "系统内部错误，请联系管理员");
    }
}
```

## 七、`@ExceptionHandler`——异常匹配规则

### 匹配优先级

`@ExceptionHandler` 按**异常类型的精确程度**匹配：
1. 先找**完全匹配**的异常类型（如 `BusinessException`）
2. 找不到就找**父类**（如 `RuntimeException`）
3. 再找不到就找**更上层的父类**（如 `Exception`）
4. 都找不到就走默认错误处理

项目里的匹配顺序：
```
抛出 BusinessException
    → 匹配 @ExceptionHandler(BusinessException.class) ✓（最精确）

抛出 MethodArgumentNotValidException
    → 匹配 @ExceptionHandler(MethodArgumentNotValidException.class) ✓

抛出 NullPointerException（没有专门处理）
    → 不匹配 BusinessException
    → 不匹配各种参数异常
    → 匹配 @ExceptionHandler(Exception.class) ✓（兜底）
```

### `@ResponseStatus` 的作用

```java
@ExceptionHandler(BusinessException.class)
public Result<Void> handleBusinessException(BusinessException e) {
    return Result.error(e.getCode(), e.getMessage());
    // 没有 @ResponseStatus，HTTP 状态码是 200
}

@ExceptionHandler(Exception.class)
@ResponseStatus(HttpStatus.INTERNAL_SERVER_ERROR)  // HTTP 状态码 500
public Result<Void> handleException(Exception e) {
    return Result.error(ResultCode.ERROR.getCode(), "系统内部错误");
}
```

注意一个设计细节：
- **业务异常**：HTTP 状态码返回 200，通过 `Result.code` 字段区分成功/失败。这是前后端分离项目的常见做法——前端只看 `code` 字段，不看 HTTP 状态码
- **系统异常**：HTTP 状态码返回 500，表示服务器内部错误。这是给运维/监控看的，5xx 错误会触发告警

### 为什么业务异常返回 HTTP 200？

这是一个有争议的设计，两种观点：

| 观点 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| **业务码派**（项目采用） | 业务异常 HTTP 200，用 code 字段区分 | 前端统一处理，不依赖 HTTP 状态码；HTTP 状态码只表示传输层是否成功 | 监控系统无法通过 4xx/5xx 统计业务错误 |
| **HTTP 状态码派** | 业务异常用对应的 HTTP 状态码（400 参数错误、401 未登录、403 无权限、404 不存在） | 符合 RESTful 规范，监控系统能统计 | 前端要处理多种 HTTP 状态码，逻辑复杂 |

项目用的是**业务码派**，这是国内企业项目的常见做法。两种都可以，关键是团队统一。

## 八、全局异常处理和事务回滚的关系

这是一个重要的细节，很多人搞混。

### 异常被全局异常处理器捕获了，事务还会回滚吗？

**会的。** 全局异常处理器和事务回滚是两个独立的机制：

1. **事务回滚**：发生在 Service 层方法执行时。`@Transactional` 的 AOP 代理在方法抛出异常时，先判断是否需要回滚，然后执行回滚，**然后把异常继续往上抛**
2. **全局异常处理**：异常从 Service 层抛到 Controller 层，再被 `@RestControllerAdvice` 捕获，转换成 `Result` 返回

顺序：
```
Service 方法抛出 BusinessException
    │
    ▼
@Transactional AOP 代理捕获异常
    → 判断：BusinessException 是 RuntimeException，需要回滚
    → 执行 rollback
    → 把异常继续往上抛（不会吞掉异常）
    │
    ▼
Controller 方法收到异常（不 try-catch 的话继续往上抛）
    │
    ▼
DispatcherServlet 收到异常
    → 找 @ExceptionHandler(BusinessException.class)
    → 调用 handleBusinessException()
    → 返回 Result.error(code, message)
    │
    ▼
前端收到 HTTP 200 + JSON {code: 42001, message: "图书不存在"}
```

**关键点**：事务回滚发生在异常被全局异常处理器捕获**之前**。全局异常处理器只是把异常转换成友好的返回格式，不影响事务回滚。

### 如果异常被 catch 了会怎么样？

```java
@Transactional(rollbackFor = Exception.class)
public void addBook(BookAddDTO dto) {
    try {
        // 业务逻辑，抛出 BusinessException
    } catch (Exception e) {
        e.printStackTrace();  // 异常被吞了
    }
}
```

异常被 catch 了，`@Transactional` 的 AOP 代理**感知不到异常**（因为方法正常返回了），所以**事务不会回滚**！

这就是第5课讲的"事务失效场景"之一：异常被 catch 吞掉了。

**正确做法**：catch 后重新抛出，或者手动设置回滚：
```java
catch (Exception e) {
    throw new BusinessException(ResultCode.ERROR.getCode(), e.getMessage());  // 重新抛出
}
// 或者
catch (Exception e) {
    TransactionAspectSupport.currentTransactionStatus().setRollbackOnly();  // 手动回滚
}
```

## 九、项目里的异常处理体系总结

```
异常类型                        抛出位置            处理器                              返回 code
─────────────────────────────────────────────────────────────────────────────────────
BusinessException               Service 层        handleBusinessException            自定义（42001等）
MethodArgumentNotValidException Controller 参数校验  handleMethodArgumentNotValid  40000
BindException                   Controller 表单绑定  handleBindException              40000
ConstraintViolationException    @Validated 参数校验 handleConstraintViolation        40000
MissingServletRequestParameter   Spring MVC         handleMissingServletRequestParam  40001
MethodArgumentTypeMismatch       Spring MVC         handleMethodArgumentTypeMismatch  40002
HttpMessageNotReadable           Jackson 解析 JSON   handleHttpMessageNotReadable     40000
Exception（其他所有）             任何位置           handleException（兜底）            50000
```

### 设计优点

1. **分层处理**：具体异常有具体处理方法，兜底用 `Exception`
2. **信息详细**：参数校验异常返回具体的字段错误信息（如"title: 书名不能为空"）
3. **日志分级**：业务异常用 `log.warn`，系统异常用 `log.error`（带堆栈）
4. **安全**：系统异常不返回具体错误信息（只返回"系统内部错误"），避免泄露服务器内部细节
5. **统一格式**：所有异常都转换成 `Result` 返回，前端统一处理

## 十、本课必须记住的 7 件事

1. **统一返回格式 `Result<T>`**：所有接口返回 `{code, message, data, timestamp}`，前端通过 `code` 判断成功/失败，不依赖 HTTP 状态码
2. **状态码用枚举 `ResultCode` 管理**：2xxxx 成功、4xxxx 客户端错误、5xxxx 服务端错误，按模块细分（41xxx 用户、42xxx 图书、43xxx 借阅）
3. **业务异常 `BusinessException` 继承 `RuntimeException`**：不需要到处声明 throws，配合 Spring 事务默认回滚规则
4. **全局异常处理器 `@RestControllerAdvice` + `@ExceptionHandler`**：基于 AOP，拦截所有 Controller 抛出的异常，转换成统一的 `Result` 返回
5. **异常匹配按精确程度**：先匹配具体异常类型，再匹配父类，最后兜底 `Exception`
6. **事务回滚和全局异常处理是独立的**：事务回滚发生在 Service 层 AOP 代理，全局异常处理发生在 Controller 层，异常被 catch 吞掉会导致事务不回滚
7. **业务异常返回 HTTP 200 + code 字段**（项目做法），系统异常返回 HTTP 500，前端统一看 code 字段

```java
// 统一返回结果
@Data
public class Result<T> implements Serializable {
    private Integer code;
    private String message;
    private T data;
    private Long timestamp;

    public static <T> Result<T> success(T data) {
        return new Result<>(20000, "操作成功", data);
    }

    public static <T> Result<T> error(Integer code, String message) {
        return new Result<>(code, message, null);
    }
}

// 业务异常
@Getter
public class BusinessException extends RuntimeException {
    private final Integer code;
    public BusinessException(ResultCode resultCode) {
        super(resultCode.getMessage());
        this.code = resultCode.getCode();
    }
}

// Service 层：只抛异常，不处理
@Service
public class BookServiceImpl {
    public BookVO getBookById(Long id) {
        Book book = getById(id);
        if (book == null) {
            throw new BusinessException(ResultCode.BOOK_NOT_FOUND);  // 抛异常
        }
        return toVO(book);
    }
}

// 全局异常处理器：统一捕获，转换成 Result
@Slf4j
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(BusinessException.class)
    public Result<Void> handleBusinessException(BusinessException e) {
        log.warn("业务异常: code={}, message={}", e.getCode(), e.getMessage());
        return Result.error(e.getCode(), e.getMessage());
    }

    @ExceptionHandler(Exception.class)
    @ResponseStatus(HttpStatus.INTERNAL_SERVER_ERROR)
    public Result<Void> handleException(Exception e) {
        log.error("系统内部错误", e);
        return Result.error(50000, "系统内部错误，请联系管理员");
    }
}
```

## 十三、自测题

### Q1：为什么项目里所有接口都返回 `Result<T>`？统一返回格式有什么好处？

<details>
<summary>点击查看答案</summary>

如果不统一返回格式，每个接口返回不同的类型（对象、字符串、Map、异常错误页），前端需要写不同的解析逻辑，成功/失败判断方式不统一，错误信息格式混乱。

统一返回 `Result<T>`（包含 code、message、data、timestamp）的好处：
1. **前端统一处理**：一套逻辑解析所有接口的响应，通过 code 字段判断成功/失败
2. **后端规范统一**：所有开发者遵循同一套返回格式，不会各写各的
3. **成功/失败明确**：通过 code 字段区分，不依赖 HTTP 状态码
4. **错误信息友好**：业务异常返回具体错误信息（如"图书不存在"），而不是 500 错误页
5. **便于扩展**：可以在 Result 里加统一字段（timestamp、traceId 等）

</details>

### Q2：`BusinessException` 为什么继承 `RuntimeException` 而不是 `Exception`？

<details>
<summary>点击查看答案</summary>

1. **不需要到处声明 throws**：受检异常（Exception 的直接子类）必须在方法签名上声明 throws 或 try-catch，否则编译不通过。Service 层很多方法都可能抛业务异常，如果是受检异常，每个方法都要写 throws BusinessException，非常繁琐。RuntimeException 不需要强制声明或捕获。
2. **配合 Spring 事务回滚**：Spring `@Transactional` 默认只回滚 RuntimeException 和 Error。如果 BusinessException 是受检异常，默认不会触发事务回滚（除非配置 rollbackFor = Exception.class）。继承 RuntimeException 后，抛出业务异常自动触发事务回滚。
3. **业务异常是"不可恢复"的**：业务异常（如"图书不存在"、"库存不足"）通常不需要调用者捕获后恢复，而是直接返回错误信息给前端。运行时异常更适合这种"抛出后由全局处理器统一处理"的场景。

</details>

### Q3：`@RestControllerAdvice` 和 `@ExceptionHandler` 是怎么工作的？异常匹配的规则是什么？

<details>
<summary>点击查看答案</summary>

`@RestControllerAdvice` 是 `@ControllerAdvice` + `@ResponseBody` 的组合，标记一个类为全局异常处理器。基于 Spring AOP 实现：
1. Spring 启动时扫描所有 `@ControllerAdvice` 类
2. Controller 方法抛出异常时，DispatcherServlet 不直接返回 500，而是找 `@ExceptionHandler` 方法
3. 找到匹配的方法就调用它，把返回值（Result）序列化成 JSON 返回

异常匹配规则：按异常类型的**精确程度**匹配
1. 先找完全匹配的异常类型（如 BusinessException）
2. 找不到就找父类（如 RuntimeException）
3. 再找不到就找更上层的父类（如 Exception）
4. 都找不到就走默认错误处理（500 错误页）

项目里的 `@ExceptionHandler(Exception.class)` 是兜底，处理所有未被其他处理器捕获的异常。

</details>

### Q4：全局异常处理器捕获了异常，事务还会回滚吗？为什么？

<details>
<summary>点击查看答案</summary>

**会回滚。** 全局异常处理和事务回滚是两个独立的机制，发生在不同的层级：

1. **事务回滚发生在 Service 层**：`@Transactional` 的 AOP 代理在方法抛出异常时，先判断是否需要回滚（默认 RuntimeException 和 Error 回滚），然后执行 rollback，**然后把异常继续往上抛**（不会吞掉异常）
2. **全局异常处理发生在 Controller 层**：异常从 Service 层抛到 Controller 层，再被 `@RestControllerAdvice` 捕获，转换成 Result 返回

顺序：Service 抛异常 → 事务 AOP 代理捕获 → 回滚 → 继续抛异常 → Controller 收到 → 全局异常处理器捕获 → 返回 Result

所以事务回滚发生在异常被全局异常处理器捕获**之前**，全局异常处理器只是把异常转换成友好的返回格式，不影响事务回滚。

**但如果异常被 try-catch 吞掉了**（Service 方法里 catch 了异常但没有重新抛出），事务 AOP 代理感知不到异常，事务就不会回滚。这是常见的事务失效场景。

</details>

### Q5：项目里业务异常返回 HTTP 200，系统异常返回 HTTP 500，为什么这么设计？

<details>
<summary>点击查看答案</summary>

这是国内企业前后端分离项目的常见设计：

1. **业务异常返回 HTTP 200 + code 字段**：业务异常（如"图书不存在"、"库存不足"）是正常的业务流程分支，不是传输层错误。HTTP 状态码 200 表示请求成功到达服务器并被处理，业务成功/失败通过 Result.code 字段区分。这样前端只需要一套逻辑：判断 code === 20000 就是成功，其他都是失败，不需要处理各种 HTTP 状态码。
2. **系统异常返回 HTTP 500**：系统异常（如空指针、数据库连接失败）是服务器内部错误，是不应该发生的。返回 HTTP 500 是给运维/监控系统看的，5xx 错误会触发告警，便于及时发现和排查问题。同时系统异常不返回具体错误信息（只返回"系统内部错误"），避免泄露服务器内部细节。

这种设计叫"业务码派"，另一种是"HTTP 状态码派"（业务异常也用 4xx 状态码，符合 RESTful 规范）。两种都可以，关键是团队统一。项目用的是业务码派。

</details>

## 十四、面试题

### 面试题1：你们项目的统一返回格式和异常处理是怎么设计的？

> **答题要点**：
> 1. **统一返回格式 `Result<T>`**：包含 code（状态码）、message（提示信息）、data（响应数据）、timestamp（时间戳）。所有 Controller 接口都返回 Result，通过静态工厂方法 success()、error() 创建。前端通过 code 判断成功/失败。
> 2. **状态码枚举 `ResultCode`**：统一管理所有状态码，2xxxx 成功、4xxxx 客户端错误（按模块细分：41xxx 用户、42xxx 图书、43xxx 借阅）、5xxxx 服务端错误。避免硬编码数字。
> 3. **业务异常 `BusinessException`**：继承 RuntimeException，携带 code 和 message。Service 层在业务逻辑不满足时抛出（如图书不存在、库存不足），不需要 try-catch，不需要声明 throws。
> 4. **全局异常处理器 `@RestControllerAdvice` + `@ExceptionHandler`**：拦截所有 Controller 抛出的异常，转换成统一的 Result 返回。具体异常有具体处理方法（BusinessException、参数校验异常等），Exception 兜底。业务异常 HTTP 200，系统异常 HTTP 500。
> 5. **分层原则**：Service 层只抛异常不处理，Controller 层不 try-catch（除非特殊场景），全局异常处理器统一处理。日志分级：业务异常 warn，系统异常 error（带堆栈）。

### 面试题2：`@RestControllerAdvice` 的实现原理是什么？异常是怎么被捕获的？

> **答题要点**：
> 1. `@RestControllerAdvice` = `@ControllerAdvice` + `@ResponseBody`，基于 Spring AOP 实现
> 2. Spring 容器启动时，`ControllerAdviceBean` 扫描所有 `@ControllerAdvice` 标记的类，注册为全局控制器增强
> 3. 当 Controller 方法抛出异常时，`DispatcherServlet` 不直接返回 500 错误页，而是调用 `ExceptionHandlerExceptionResolver` 解析异常
> 4. `ExceptionHandlerExceptionResolver` 遍历所有 `@ControllerAdvice` 类中的 `@ExceptionHandler` 方法，按异常类型匹配（先精确匹配，再父类匹配）
> 5. 找到匹配的方法后，通过反射调用该方法，传入异常对象，方法返回 Result 对象
> 6. `@ResponseBody` 确保返回值被 Jackson 序列化成 JSON，写入 HTTP 响应体
> 7. 如果找不到匹配的 `@ExceptionHandler`，就走默认的异常处理（返回 500 错误页）
> 8. 注意：`@RestControllerAdvice` 只拦截 Controller 层抛出的异常，不拦截 Filter/Interceptor 里的异常（那些需要单独处理）

### 面试题3：业务异常为什么用 RuntimeException？受检异常和运行时异常有什么区别？

> **答题要点**：
> 1. **受检异常（Checked Exception）**：继承 Exception 但不继承 RuntimeException，编译器强制要求处理——要么在方法签名声明 throws，要么 try-catch 捕获。如 IOException、SQLException。
> 2. **运行时异常（Unchecked Exception）**：继承 RuntimeException，编译器不强制要求处理，可以不声明 throws、不捕获，运行时才抛出。如 NullPointerException、IllegalArgumentException、自定义 BusinessException。
> 3. **业务异常用 RuntimeException 的原因**：
>    - 不需要到处声明 throws：Service 层大量方法都可能抛业务异常，受检异常会导致每个方法都写 throws，代码冗余
>    - 配合 Spring 事务：`@Transactional` 默认只回滚 RuntimeException 和 Error，业务异常继承 RuntimeException 后自动触发回滚
>    - 业务异常不可恢复：业务异常（如"库存不足"）通常不需要调用者捕获后恢复，而是由全局异常处理器统一处理返回给前端，运行时异常更适合
> 4. **什么时候用受检异常**：可恢复的异常、需要调用者明确处理的异常（如文件不存在可以换个路径重试）。但现代 Java 开发（如 Spring 体系）倾向于用运行时异常，减少模板代码。
