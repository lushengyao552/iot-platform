## 1. 项目架构与分层设计

### 1.1 是什么

本项目采用经典的**三层架构**（Controller → Service → Mapper），配合 DTO/VO/Entity 三种数据对象进行数据隔离。

```
HTTP 请求
    ↓
Controller（控制层）：接收请求、参数校验、调用Service、返回Result
    ↓
Service（业务层）：业务逻辑、事务管理、调用Mapper
    ↓
Mapper（数据访问层）：SQL执行、数据库操作
    ↓
MySQL 数据库
```

数据对象：
- **Entity**：与数据库表一一对应，包含所有字段
- **DTO（Data Transfer Object）**：接收前端请求参数，包含校验注解
- **VO（View Object）**：返回给前端的数据，去除敏感字段，补充关联信息

### 1.2 原理

**分层架构的核心思想是"关注点分离"（Separation of Concerns）**：
- Controller 只关心 HTTP 协议层面的事情（请求/响应/状态码）
- Service 只关心业务逻辑（规则/流程/事务）
- Mapper 只关心数据持久化（SQL/数据库）

**为什么需要 DTO/VO/Entity 分离？**
- 安全性：Entity 中的 password 等敏感字段不会通过 VO 暴露给前端
- 解耦：数据库表结构变化不影响前端接口（通过 VO 隔离）
- 清晰：DTO 只包含请求需要的字段，VO 只包含响应需要的字段

### 1.3 为什么这么做

| 做法 | 原因 |
|------|------|
| Controller 不写业务逻辑 | 业务逻辑可复用、可测试，HTTP 层只做协议转换 |
| Service 接口与实现分离 | 面向接口编程，可切换实现（如本地实现→远程调用），便于 Mock 测试 |
| Mapper 继承 BaseMapper | MyBatis-Plus 提供通用 CRUD，减少重复代码 |
| DTO 接收请求 | 防止前端传入多余字段（如 id、status 等不应由前端控制的字段） |
| VO 返回响应 | 去除 password 等敏感字段，补充 categoryName 等关联数据 |
| 统一 Result 封装 | 前后端约定统一格式，前端处理逻辑简化 |

### 1.4 怎么修改调整

**场景1：新增一个业务模块（如"出版社管理"）**
```
1. entity/  创建 Publisher.java
2. mapper/  创建 PublisherMapper.java（继承 BaseMapper<Publisher>）
3. service/ 创建 PublisherService.java 接口
4. service/impl/ 创建 PublisherServiceImpl.java
5. controller/ 创建 PublisherController.java
6. dto/ 创建 PublisherAddDTO.java、PublisherQueryDTO.java
7. vo/ 创建 PublisherVO.java
8. 在 SQL 脚本中添加 publisher 表
```

**场景2：Controller 需要调用另一个 Service**
- 直接通过 `@RequiredArgsConstructor` 注入即可，如 `private final BookService bookService;`
- 注意：避免循环依赖（A 注入 B，B 注入 A），如果出现循环依赖，考虑抽取公共逻辑到第三个 Service

**场景3：Entity 字段变化但不想影响前端接口**
- 修改 Entity 和数据库表
- VO 保持不变，在 toVO() 方法中不映射新字段即可
- 或者在 VO 中添加新字段，前端逐步适配

## 2. Spring Boot 核心原理

### 2.1 自动配置（Auto-Configuration）

**是什么**：Spring Boot 根据 classpath 中的依赖自动配置 Spring 容器中的 Bean。

**原理**：
1. `@SpringBootApplication` 注解包含 `@EnableAutoConfiguration`
2. `@EnableAutoConfiguration` 通过 `@Import(AutoConfigurationImportSelector.class)` 导入自动配置类
3. `AutoConfigurationImportSelector` 读取 `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports` 文件
4. 该文件列出所有自动配置类的全限定名
5. 每个自动配置类使用 `@ConditionalOnXxx` 注解判断是否需要生效
   - `@ConditionalOnClass`：classpath 中存在指定类时生效
   - `@ConditionalOnMissingBean`：容器中不存在指定 Bean 时生效
   - `@ConditionalOnProperty`：配置文件中存在指定属性时生效

**举例**：当 classpath 中存在 `spring-boot-starter-web` 时，`ServletWebServerFactoryAutoConfiguration` 自动配置内嵌 Tomcat。

**怎么调整**：
- 排除自动配置：`@SpringBootApplication(exclude = {DataSourceAutoConfiguration.class})`
- 自定义配置覆盖：自己定义同类型的 Bean，Spring Boot 会通过 `@ConditionalOnMissingBean` 跳过默认配置
- 查看自动配置报告：启动时加 `--debug` 参数，控制台输出自动配置报告

### 2.2 依赖注入（DI）

**是什么**：对象的依赖由容器注入，而不是自己创建。

**本项目中的用法**：
```java
@Service
@RequiredArgsConstructor  // Lombok 注解，为 final 字段生成构造函数
public class BookServiceImpl {
    private final BookMapper bookMapper;      // 构造函数注入
    private final RedisService redisService;  // 构造函数注入
}
```

**为什么用构造函数注入而不是 @Autowired 字段注入？**
1. **不可变性**：final 字段，注入后不能修改
2. **依赖明确**：构造函数参数明确列出所有依赖，方便查看
3. **便于测试**：单元测试时可以直接 new 对象并传入 Mock 对象
4. **循环依赖检测**：构造函数注入会在启动时立即检测循环依赖，而字段注入可能在运行时才发现

**怎么调整**：
- 字段注入（不推荐）：`@Autowired private BookMapper bookMapper;`
- Setter 注入（可选依赖）：`@Autowired public void setBookMapper(BookMapper bookMapper) {...}`
- 构造函数注入（推荐）：使用 `@RequiredArgsConstructor` + final 字段

### 2.3 事务管理（@Transactional）

**是什么**：声明式事务，方法内的多个数据库操作要么全部成功，要么全部回滚。

**原理**：
1. Spring AOP 在方法执行前开启事务（`begin`）
2. 方法正常执行完成后提交事务（`commit`）
3. 方法抛出 `RuntimeException` 或 `Error` 时回滚事务（`rollback`）
4. 默认只回滚 `RuntimeException` 和 `Error`，`Exception` 不回滚

**本项目中的用法**：
```java
@Transactional(rollbackFor = Exception.class)  // 所有异常都回滚
public BorrowRecordVO borrowBook(Long userId, Long bookId) {
    bookMapper.decreaseStock(bookId, 1);  // 操作1：扣减库存
    borrowRecordMapper.insert(record);      // 操作2：创建借阅记录
    // 如果操作2失败，操作1会回滚，库存恢复
}
```

**为什么 rollbackFor = Exception.class？**
- 默认只回滚 `RuntimeException`，如果方法抛出 `IOException` 等受检异常，事务不会回滚
- 设置 `rollbackFor = Exception.class` 确保所有异常都回滚，更安全

**事务失效的常见场景（面试高频）**：
1. 方法不是 `public` 的（Spring AOP 只能拦截 public 方法）
2. 同类中方法调用（`this.method()` 不走代理，事务不生效）
3. 异常被 try-catch 捕获了，没有抛出
4. 抛出的异常不是 `RuntimeException` 且没有设置 `rollbackFor`
5. 数据库引擎不支持事务（如 MyISAM）
6. `@Transactional` 注解在接口上但使用 CGLIB 代理

**怎么调整**：
- 只读事务：`@Transactional(readOnly = true)`，查询方法使用，可提升性能
- 事务隔离级别：`@Transactional(isolation = Isolation.READ_COMMITTED)`
- 事务传播行为：`@Transactional(propagation = Propagation.REQUIRED)`
  - REQUIRED（默认）：有事务就加入，没有就新建
  - REQUIRES_NEW：总是新建事务，挂起当前事务
  - NESTED：嵌套事务（保存点）

## 3. MyBatis-Plus 深度解析

### 3.1 是什么

MyBatis-Plus（简称 MP）是 MyBatis 的增强工具，在 MyBatis 的基础上只做增强不做改变，为简化开发、提高效率而生。

**核心特性**：
- 通用 CRUD：继承 `BaseMapper<T>` 自动获得 17 个基础方法
- 条件构造器：`LambdaQueryWrapper` 类型安全的条件构建
- 分页插件：自动拦截分页 SQL，生成 count 查询
- 逻辑删除：`@TableLogic` 自动处理软删除
- 自动填充：`MetaObjectHandler` 自动填充 createTime/updateTime
- 主键策略：`@TableId(type = IdType.AUTO)` 多种主键生成策略

### 3.2 原理

**BaseMapper 通用 CRUD 原理**：
- MyBatis-Plus 在启动时扫描实体类的注解（`@TableName`、`@TableId`、`@TableField`）
- 根据实体类信息动态生成 SQL（如 `INSERT INTO book (title, author) VALUES (?, ?)`）
- 通过 MyBatis 的 `MappedStatement` 注册到 SqlSessionFactory 中
- 调用 `baseMapper.insert(entity)` 时，MyBatis 执行动态生成的 SQL

**分页插件原理**：
- `MybatisPlusInterceptor` 注册 `PaginationInnerInterceptor`
- 拦截 `Executor.query()` 方法
- 判断参数中是否有 `IPage` 对象
- 如果有，先执行 count 查询（`SELECT COUNT(*) FROM ...`）
- 再执行分页查询（`SELECT ... FROM ... LIMIT ?, ?`）
- 将结果封装到 `IPage` 对象中

**逻辑删除原理**：
- `@TableLogic` 标记逻辑删除字段
- 查询时自动添加 `WHERE deleted = 0`
- 删除时自动转换为 `UPDATE ... SET deleted = 1 WHERE id = ?`
- 对开发者透明，无需手动处理

### 3.3 为什么这么做

| 做法 | 原因 |
|------|------|
| 继承 BaseMapper | 避免每个 Mapper 都写重复的 CRUD SQL |
| LambdaQueryWrapper | 类型安全，字段名写错编译时就报错，而不是运行时 |
| 逻辑删除 | 数据不真正删除，可恢复，保留历史数据 |
| 自动填充 | createTime/updateTime 自动设置，业务代码不用关心 |
| 分页插件 | 自动生成 count SQL 和分页 SQL，不用手写 |

### 3.4 怎么修改调整

**场景1：自定义复杂查询（多表关联）**
- 在 Mapper 接口中定义方法：`List<BookVO> selectBookWithCategory(@Param("categoryId") Long categoryId);`
- 在 `resources/mapper/BookMapper.xml` 中编写 SQL
- 或者使用 `@Select` 注解直接写 SQL

**场景2：修改分页大小限制**
```java
PaginationInnerInterceptor paginationInterceptor = new PaginationInnerInterceptor(DbType.MYSQL);
paginationInterceptor.setMaxLimit(1000L);  // 修改最大分页条数
```

**场景3：不使用逻辑删除**
- 去掉实体类上的 `@TableLogic` 注解
- 去掉 `application.yml` 中的 `logic-delete-field` 配置
- 删除操作会变成真正的 `DELETE` 语句

**场景4：自定义主键生成策略**
```java
@TableId(type = IdType.ASSIGN_ID)  // 雪花算法生成分布式ID
private Long id;
```
可选策略：
- `AUTO`：数据库自增
- `NONE`：不设置（跟随全局）
- `INPUT`：用户输入
- `ASSIGN_ID`：雪花算法（分布式ID）
- `ASSIGN_UUID`：UUID

## 4. MySQL 数据库设计与优化

### 4.1 表设计原则

**本项目的表设计**：
- `sys_user`：用户表
- `book`：图书表
- `book_category`：图书分类表
- `borrow_record`：借阅记录表

**设计原则**：
1. **主键**：所有表使用 `BIGINT AUTO_INCREMENT` 自增主键
2. **必备字段**：`create_time`、`update_time`、`deleted`（逻辑删除）
3. **索引设计**：
   - 主键索引（自动）
   - 唯一索引：`uk_username`、`uk_isbn`、`uk_name`
   - 普通索引：`idx_title`、`idx_author`、`idx_user_id`、`idx_book_id`、`idx_status`
4. **字段类型**：
   - 字符串：`VARCHAR`，根据实际长度设置
   - 金额：`DECIMAL(10,2)`，避免浮点精度问题
   - 时间：`DATETIME`，范围大，无时区问题
   - 状态：`TINYINT`，占用空间小
5. **字符集**：`utf8mb4`，支持 emoji 和所有 Unicode 字符
6. **存储引擎**：`InnoDB`，支持事务和外键

### 4.2 索引原理

**是什么**：索引是一种数据结构，帮助快速定位数据，类似书的目录。

**InnoDB 索引结构**：B+ 树
- 非叶子节点存储索引键和子节点指针
- 叶子节点存储所有数据（聚簇索引）或主键值（二级索引）
- 叶子节点通过双向链表连接，便于范围查询

**聚簇索引 vs 二级索引**：
- **聚簇索引**：主键索引，叶子节点存储整行数据。一张表只有一个聚簇索引。
- **二级索引**：非主键索引，叶子节点存储主键值。查询时需要"回表"（先查二级索引得到主键，再查聚簇索引得到数据）。

**覆盖索引**：查询的字段都在索引中，不需要回表，性能更好。
```sql
-- 假设 idx_user_status 是 (user_id, status) 联合索引
SELECT user_id, status FROM borrow_record WHERE user_id = 1;  -- 覆盖索引，不需要回表
SELECT * FROM borrow_record WHERE user_id = 1;  -- 需要回表
```

**最左前缀原则**：联合索引 `(a, b, c)` 可以支持 `a`、`a,b`、`a,b,c` 的查询，但不支持 `b`、`c`、`b,c` 的查询。

### 4.3 为什么这么设计

| 设计 | 原因 |
|------|------|
| BIGINT 主键 | INT 最大值 21亿，大数据量可能不够；BIGINT 足够大 |
| 逻辑删除 | 数据可恢复，保留历史，关联数据不失效 |
| DECIMAL 存金额 | FLOAT/DOUBLE 有精度问题，金额计算必须精确 |
| utf8mb4 | utf8 最多3字节，不支持 emoji；utf8mb4 最多4字节 |
| InnoDB | 支持事务、行级锁、外键，MyISAM 不支持事务 |
| 适当索引 | 加速查询，但索引不是越多越好（占空间、降低写入性能） |

### 4.4 怎么修改调整

**场景1：添加索引**
```sql
ALTER TABLE book ADD INDEX idx_publisher (publisher);
```

**场景2：慢查询优化**
1. 开启慢查询日志：`SET GLOBAL slow_query_log = ON; SET GLOBAL long_query_time = 1;`
2. 用 `EXPLAIN` 分析查询：`EXPLAIN SELECT * FROM book WHERE title LIKE '%Java%';`
3. 关注 `type` 列（ALL 全表扫描需要优化）、`key` 列（使用的索引）、`rows` 列（扫描行数）
4. 添加合适的索引，或改写查询

**场景3：分库分表（数据量大时）**
- 垂直分库：按业务拆分（用户库、图书库、借阅库）
- 水平分表：按用户ID取模拆分借阅记录表
- 使用 ShardingSphere 等中间件

## 5. JWT 认证机制

### 5.1 是什么

JWT（JSON Web Token）是一种开放标准（RFC 7519），用于在各方之间安全地传输信息。信息被编码为 JSON 对象，通过数字签名验证完整性。

**JWT 结构**：三部分用 `.` 分隔
```
eyJhbGciOiJIUzI1NiJ9.eyJ1c2VySWQiOjEsInVzZXJuYW1lIjoiYWRtaW4ifQ.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c
└─────────────┬─────────────┘ └───────────────────────┬───────────────────────┘ └──────────────┬──────────────┘
           Header                          Payload                              Signature
```

- **Header（头部）**：`{"alg": "HS256", "typ": "JWT"}`，声明算法和类型
- **Payload（载荷）**：`{"userId": 1, "username": "admin", "role": "ADMIN", "exp": 1696000000}`，存放用户信息和过期时间
- **Signature（签名）**：`HMACSHA256(base64UrlEncode(header) + "." + base64UrlEncode(payload), secret)`，用于验证 Token 完整性

### 5.2 原理

**认证流程**：
```
1. 用户登录 → 验证用户名密码 → 生成 JWT Token → 返回给前端
2. 前端存储 Token（localStorage / cookie）
3. 后续请求在 Header 中携带：Authorization: Bearer <token>
4. 后端 JwtInterceptor 拦截请求 → 验证 Token 签名和有效期 → 解析用户信息 → 存入 UserContext
5. Controller/Service 通过 UserContext 获取当前用户
6. 请求结束后清除 UserContext（ThreadLocal.remove()）
```

**签名验证原理**：
- 服务器用密钥（secret）对 Header+Payload 重新计算签名
- 与 Token 中的签名对比，如果一致说明 Token 未被篡改
- 因为密钥只有服务器知道，攻击者无法伪造签名

**为什么是无状态的？**
- 服务器不存储 Session，所有用户信息都在 Token 中
- 验证只需要密钥，不需要查询数据库或 Session 存储
- 适合分布式部署，任意服务器都能验证

### 5.3 为什么这么做

| 做法 | 原因 |
|------|------|
| JWT 而非 Session | 无状态，适合分布式/微服务；不需要共享 Session 存储 |
| Token 放 Header | 符合 RESTful 规范，不依赖 Cookie（避免 CSRF） |
| 设置过期时间 | Token 泄露后有有效期限制，降低风险 |
| ThreadLocal 存用户 | 线程隔离，请求内任意位置可获取当前用户 |
| 请求结束清除 ThreadLocal | 防止内存泄漏（线程池复用线程，ThreadLocal 不会自动清除） |

### 5.4 怎么修改调整

**场景1：修改 Token 过期时间**
```yaml
library:
  jwt:
    expiration: 604800000  # 7天（毫秒）
```

**场景2：Token 续期（刷新 Token）**
- 方案1：双 Token（Access Token + Refresh Token），Access Token 短期，Refresh Token 长期用于刷新
- 方案2：每次请求检查剩余时间，小于阈值时返回新 Token
- 方案3：Redis 存储 Token 黑名单，实现主动失效

**场景3：修改密钥**
```yaml
library:
  jwt:
    secret: your-new-secret-key-at-least-256-bits
```
注意：修改密钥后所有旧 Token 失效，用户需要重新登录。生产环境密钥应通过环境变量注入，不要硬编码。

**场景4：添加自定义字段到 Token**
```java
// 在 JwtUtil.generateToken 中添加
claims.put("email", user.getEmail());
claims.put("department", user.getDepartment());

// 解析时获取
String email = claims.get("email", String.class);
```

## 6. Redis 缓存与分布式锁

### 6.1 Redis 基础

**是什么**：Redis（Remote Dictionary Server）是一个开源的内存数据库，数据存储在内存中，读写速度极快，支持多种数据结构。

**支持的数据结构**：
- String（字符串）：缓存对象、计数器、分布式锁
- Hash（哈希）：存储对象（多个字段）
- List（列表）：消息队列、最新列表
- Set（集合）：去重、交集并集差集
- ZSet（有序集合）：排行榜、带权重的队列

**为什么用 Redis 做缓存？**
- 内存读写速度：10万+ QPS，远快于 MySQL（几千 QPS）
- 减轻数据库压力：热点数据放 Redis，减少数据库查询
- 支持过期时间：自动删除过期数据

### 6.2 缓存原理

**本项目中的缓存用法**（图书详情缓存）：
```java
public BookVO getBookById(Long id) {
    String cacheKey = "library:book:" + id;
    // 1. 先查缓存
    BookVO cached = redisService.get(cacheKey, BookVO.class);
    if (cached != null) {
        return cached;  // 缓存命中，直接返回
    }
    // 2. 缓存未命中，查数据库
    Book book = getById(id);
    BookVO vo = toVO(book);
    // 3. 写入缓存（设置过期时间）
    redisService.set(cacheKey, vo, 30, TimeUnit.MINUTES);
    return vo;
}
```

**缓存模式**：Cache-Aside（旁路缓存）
- 读：先查缓存，命中返回；未命中查数据库，然后写入缓存
- 写：先更新数据库，然后删除缓存（而不是更新缓存）

**为什么删除缓存而不是更新缓存？**
- 并发场景下，更新缓存可能导致数据不一致（A 更新数据库→B 更新数据库→B 更新缓存→A 更新缓存，缓存是旧数据）
- 删除缓存更简单，下次查询时自动加载最新数据
- 缺点：删除后第一次查询会缓存未命中，但这是可接受的

**缓存三大问题（面试高频）**：

1. **缓存穿透**：查询不存在的数据，缓存永远不命中，请求都打到数据库
   - 解决方案：缓存空值（`redis.set(key, null, 5min)`）、布隆过滤器

2. **缓存击穿**：热点 key 过期瞬间，大量并发请求打到数据库
   - 解决方案：互斥锁（只让一个请求查数据库，其他等待）、逻辑过期（不设真正过期，异步更新）

3. **缓存雪崩**：大量 key 同时过期，或 Redis 宕机，请求全部打到数据库
   - 解决方案：过期时间加随机值、Redis 集群、服务降级/限流

### 6.3 分布式锁原理

**是什么**：在分布式系统中，多个实例同时操作共享资源时，通过锁保证同一时间只有一个实例执行。

**本项目中的用法**（防止重复借阅）：
```java
String lockKey = "library:lock:borrow:" + userId + ":" + bookId;
String lockValue = UUID.randomUUID().toString();
// 加锁：SET key value NX EX timeout（原子操作）
boolean locked = redisService.tryLock(lockKey, lockValue, 10, TimeUnit.SECONDS);
if (!locked) {
    throw new BusinessException("操作太频繁，请稍后再试");
}
try {
    // 执行业务逻辑
    return doBorrowBook(userId, bookId);
} finally {
    // 释放锁：Lua 脚本判断 value 匹配才删除（原子操作）
    redisService.unlock(lockKey, lockValue);
}
```

**加锁原理**：`SET key value NX EX 10`
- `NX`：key 不存在时才设置成功（Not eXists）
- `EX 10`：10秒后自动过期（防止死锁）
- 这是一个原子操作，要么成功要么失败，不会出现并发问题

**为什么 value 要用 UUID？**
- 防止误删别人的锁：A 获取锁→A 业务阻塞超过10秒→锁自动过期→B 获取锁→A 业务完成释放锁（删除了 B 的锁）
- 用 UUID 标识锁的持有者，释放时先判断 value 是否匹配，匹配才删除

**为什么释放锁要用 Lua 脚本？**
- 判断 value 和删除 key 是两个操作，如果不原子化：
  - A 判断 value 匹配→B 获取锁（A 的锁刚过期）→A 删除 key（删除了 B 的锁）
- Lua 脚本在 Redis 中原子执行，保证判断和删除不会被打断

**分布式锁的要求（面试高频）**：
1. 互斥性：同一时间只有一个客户端持有锁
2. 防死锁：锁有过期时间，即使客户端宕机也能自动释放
3. 解铃还须系铃人：只能释放自己的锁，不能释放别人的
4. 可重入性：同一个客户端可以多次获取同一把锁（可选）
5. 高可用：Redis 集群，单点故障不影响锁

### 6.4 怎么修改调整

**场景1：修改缓存过期时间**
```java

```

**场景2：清除所有缓存**
```java

redisTemplate.delete(keys);
```

**场景3：修改分布式锁超时时间**
```java

```

**场景4：使用 Redisson（更完善的分布式锁）**
- Redisson 提供了可重入锁、公平锁、读写锁、红锁等
- 自动续期（看门狗机制）：业务未执行完时自动延长锁过期时间
- 引入依赖：`redisson-spring-boot-starter`

## 7. RabbitMQ 消息队列

### 7.1 是什么

RabbitMQ 是一个开源的消息代理（Message Broker），实现了 AMQP（Advanced Message Queuing Protocol）协议，用于在分布式系统中存储和转发消息。

**核心概念**：
- **Producer（生产者）**：发送消息的应用
- **Consumer（消费者）**：接收消息的应用
- **Queue（队列）**：存储消息的缓冲区
- **Exchange（交换机）**：接收生产者的消息，根据路由规则转发到队列
- **Binding（绑定）**：定义 Exchange 和 Queue 之间的路由规则
- **Routing Key（路由键）**：消息的路由地址，Exchange 根据它决定转发到哪个队列
- **Virtual Host（虚拟主机）**：逻辑隔离，类似数据库的 schema

**Exchange 类型**：
1. **Direct**：精确匹配 routing key，消息只发到完全匹配的队列
2. **Topic**：通配符匹配，`*` 匹配一个词，`#` 匹配零个或多个词
3. **Fanout**：广播，消息发到所有绑定的队列（忽略 routing key）
4. **Headers**：根据消息头匹配（少用）

### 7.2 原理

**消息流转过程**：
```
Producer → Exchange → (根据 Binding 和 Routing Key 路由) → Queue → Consumer
```

**本项目中的架构**：
```
主应用（生产者）
    ↓ 发送消息
Exchange: library.exchange（Topic类型）
    ├── routing key: borrow.success → Queue: library.borrow.success.queue → 主应用消费者 + 通知微服务消费者
    ├── routing key: return.success → Queue: library.return.success.queue → 主应用消费者 + 通知微服务消费者
    ├── routing key: operation.log → Queue: library.operation.log.queue → 主应用消费者
    └── routing key: delay.borrow → Queue: library.delay.queue（延迟队列，TTL 60秒）
                                            ↓ 消息过期后转发到
                                    Exchange: library.dlx.exchange（死信交换机）
                                            ↓ routing key: dlx.borrow.remind
                                    Queue: library.dlx.queue → 到期提醒消费者
```

**消息可靠性保证**：

1. **生产者确认（Publisher Confirm）**：
   - 消息到达 Exchange 后，RabbitMQ 回调 `ConfirmCallback`
   - `ack=true` 表示成功到达，`ack=false` 表示失败（需要重发）

2. **消息返回（Publisher Return）**：
   - 消息到达 Exchange 但无法路由到任何 Queue 时，回调 `ReturnCallback`
   - 避免消息丢失

3. **消费者手动确认（Manual ACK）**：
   - 消费者处理完消息后调用 `channel.basicAck()` 确认
   - 处理失败调用 `channel.basicNack()`，可选择重新入队或丢弃
   - 防止消息处理失败导致丢失

4. **消息持久化**：
   - Exchange 持久化：`durable(true)`
   - Queue 持久化：`QueueBuilder.durable()`
   - 消息持久化：`deliveryMode=PERSISTENT`
   - RabbitMQ 重启后消息不丢失

**死信队列（DLX）原理**：
- 消息变成"死信"的情况：
  1. 消费者拒绝（`basicNack`/`basicReject`）且 `requeue=false`
  2. 消息 TTL 过期
  3. 队列达到最大长度
- 队列配置 `x-dead-letter-exchange` 和 `x-dead-letter-routing-key`
- 消息变成死信后，自动转发到配置的死信交换机
- 本项目用这个机制实现延迟消息：消息发到延迟队列→等待 TTL 过期→转发到死信交换机→死信队列→消费者消费

### 7.3 为什么这么做

| 做法 | 原因 |
|------|------|
| 消息队列异步通知 | 借阅/归还后发送通知不阻塞主流程，提升响应速度 |
| 服务解耦 | 主应用不需要知道通知服务的存在，通过消息队列通信 |
| 削峰填谷 | 高并发时消息先存队列，消费者按自己的速度处理 |
| Topic Exchange | 灵活路由，一个 Exchange 支持多种消息类型 |
| 手动 ACK | 确保消息被正确处理后才确认，防止消息丢失 |
| 死信队列实现延迟 | RabbitMQ 原生不支持延迟队列（需插件），用 TTL+DLX 实现 |
| 消息持久化 | RabbitMQ 重启后消息不丢失 |

### 7.4 怎么修改调整

**场景1：添加新的消息类型**
```java

// 3. 在 MessageConsumer 中添加消费方法
```

**场景2：修改延迟时间**

注意：修改队列参数需要删除旧队列重新创建（RabbitMQ 不允许修改已存在队列的参数）。

**场景3：消费者并发数**

**场景4：使用 RabbitMQ 延迟插件（更灵活）**

- 比 TTL+DLX 更灵活，支持每条消息不同延迟时间

## 8. 微服务架构

### 8.1 是什么

微服务架构是将一个大型应用拆分为多个小型、独立部署的服务，每个服务围绕特定业务能力构建，通过轻量级机制（通常是 HTTP REST 或消息队列）通信。

**本项目中的微服务**：
- **library-management（主应用）**：图书管理核心业务，作为消息生产者
- **notification-service（通知微服务）**：独立部署，消费 RabbitMQ 消息，处理通知发送

**微服务 vs 单体**：

| 维度 | 单体架构 | 微服务架构 |
|------|----------|------------|
| 部署 | 一个应用包 | 多个服务独立部署 |
| 扩展 | 整体扩展 | 按需扩展单个服务 |
| 技术栈 | 统一技术栈 | 各服务可使用不同技术 |
| 数据库 | 通常共享数据库 | 每个服务独立数据库 |
| 通信 | 方法调用 | 网络调用（HTTP/MQ） |
| 复杂度 | 低 | 高（服务发现、配置中心、链路追踪等） |
| 适合 | 小型项目、初创期 | 大型项目、团队协作、高并发 |

### 8.2 原理

**本项目的微服务通信方式**：异步消息（RabbitMQ）
```
主应用（生产者）→ RabbitMQ → 通知微服务（消费者）
```

**为什么用消息队列而不是 HTTP 调用？**
- 异步：主应用不需要等待通知服务响应
- 解耦：主应用不需要知道通知服务的地址
- 可靠：消息持久化，通知服务宕机后恢复时仍能消费
- 削峰：通知量大时先存队列，慢慢消费

**微服务核心组件（完整微服务架构需要）**：
1. **服务注册与发现**：Nacos、Eureka、Consul（服务启动时注册，调用时查询地址）
2. **配置中心**：Nacos Config、Spring Cloud Config（统一管理配置，动态刷新）
3. **服务网关**：Spring Cloud Gateway（统一入口、路由、鉴权、限流）
4. **负载均衡**：Spring Cloud LoadBalancer（客户端负载均衡）
5. **服务调用**：OpenFeign（声明式 HTTP 客户端）
6. **熔断降级**：Sentinel、Resilience4j（防止级联故障）
7. **分布式事务**：Seata（跨服务事务一致性）
8. **链路追踪**：Sleuth + Zipkin（追踪请求链路）
9. **消息队列**：RabbitMQ、Kafka（异步通信）

### 8.3 为什么这么做

| 做法 | 原因 |
|------|------|
| 通知服务独立部署 | 通知服务可以独立扩容、升级，不影响主业务 |
| 通过 MQ 通信 | 异步解耦，主应用响应更快，消息可靠 |
| 通知服务用内存存储 | 演示用，简单；实际项目应接数据库 |

## 9. 统一响应与全局异常处理

### 9.1 统一响应

**是什么**：所有接口返回统一的 JSON 格式，包含状态码、消息、数据。

**格式**：
```json
{
  "code": 20000,
  "message": "操作成功",
  "data": { ... },
  "timestamp": 1696000000000
}
```

**为什么需要统一响应？**
- 前端处理逻辑统一，不需要判断每个接口的返回格式
- 状态码和消息标准化，便于问题定位
- 前后端协作规范，减少沟通成本

**状态码设计**：
- 20000：成功
- 400xx：客户端错误（参数、认证、权限）
- 500xx：服务端错误

### 9.2 全局异常处理

**是什么**：使用 `@RestControllerAdvice` 拦截所有 Controller 抛出的异常，统一处理并返回标准格式。

**原理**：
- `@RestControllerAdvice` = `@ControllerAdvice` + `@ResponseBody`
- Spring MVC 在 Controller 方法抛出异常时，查找 `@ExceptionHandler` 注解的方法
- 找到匹配的异常类型，调用该方法处理
- 返回值序列化为 JSON 响应

**本项目中的异常分类**：
1. **BusinessException（业务异常）**：可预期的业务错误，如"用户不存在"、"库存不足"
2. **参数校验异常**：`MethodArgumentNotValidException`、`BindException` 等
3. **系统异常**：`Exception` 兜底，返回"系统内部错误"

**为什么用全局异常处理而不是 try-catch？**
- 统一处理，不需要每个方法都写 try-catch
- 异常处理逻辑集中，便于维护
- Controller 代码更简洁，只关注业务逻辑
- 避免异常信息直接暴露给前端（如堆栈信息）

### 9.3 怎么修改调整

**场景1：添加自定义异常**

## 10. 参数校验（JSR-380）

### 10.1 是什么

JSR-380（Bean Validation 2.0）是 Java EE 的参数校验规范，通过注解方式声明校验规则，Spring Boot 集成了 Hibernate Validator 作为实现。

**常用注解**：
- `@NotNull`：不能为 null
- `@NotBlank`：字符串不能为 null 且去除空格后长度 > 0
- `@NotEmpty`：集合/数组/字符串不能为 null 且长度 > 0
- `@Size(min, max)`：字符串/集合长度范围
- `@Min`/`@Max`：数字最小值/最大值
- `@Email`：邮箱格式
- `@Pattern`：正则表达式匹配
- `@Positive`/`@Negative`：正数/负数
- `@Past`/`@Future`：过去的日期/未来的日期
- `@Valid`：级联校验（校验嵌套对象）

### 10.2 原理

**校验流程**：
1. Controller 方法参数标注 `@Valid` 或 `@Validated`
2. Spring MVC 在参数绑定后、方法执行前触发校验
3. Hibernate Validator 根据注解检查字段
4. 校验失败抛出 `MethodArgumentNotValidException`（@RequestBody）或 `BindException`（表单参数）
5. 全局异常处理器捕获异常，返回错误信息

**为什么用注解校验而不是手动 if 判断？**
- 声明式，代码简洁
- 校验规则集中在 DTO 中，清晰可见
- 可复用，同一个 DTO 在多个接口使用
- 标准化，团队协作统一

### 10.3 怎么修改调整

**场景1：自定义校验注解**
```java
// 1. 定义注解
@Target({ElementType.FIELD})
@Retention(RetentionPolicy.RUNTIME)
@Constraint(validatedBy = PhoneValidator.class)
public @interface Phone {
    String message() default "手机号格式不正确";
    Class<?>[] groups() default {};
    Class<? extends Payload>[] payload() default {};
}

// 2. 实现校验器
public class PhoneValidator implements ConstraintValidator<Phone, String> {
    private static final Pattern PHONE_PATTERN = Pattern.compile("^1[3-9]\\d{9}$");
    @Override
    public boolean isValid(String value, ConstraintValidatorContext context) {
        if (value == null) return true;  // null 由 @NotNull 处理
        return PHONE_PATTERN.matcher(value).matches();
    }
}
```

## 11. 单元测试与 Mockito

### 11.1 是什么

**单元测试**：对最小可测试单元（通常是一个方法）进行验证，确保其在各种输入下行为正确。

**Mockito**：Java 最流行的 Mock 框架，用于模拟依赖对象，隔离测试目标。

**本项目中的测试结构**：
- `@ExtendWith(MockitoExtension.class)`：启用 Mockito
- `@Mock`：模拟依赖对象（如 UserMapper、JwtUtil）
- `@InjectMocks`：将 Mock 对象注入到被测对象中
- `@Test`：测试方法
- `when(...).thenReturn(...)`：定义 Mock 行为
- `assertThrows`：断言抛出异常
- `verify`：验证方法调用

### 11.2 原理

**Mock 原理**：
- Mockito 通过动态代理（CGLIB/ByteBuddy）创建 Mock 对象
- Mock 对象的方法默认返回空值（null、0、false、空集合）
- 通过 `when(...).thenReturn(...)` 定义特定方法调用时的返回值
- 被测对象调用 Mock 对象的方法时，返回预设值，不执行真实逻辑

**为什么需要 Mock？**
- 隔离测试：只测试目标方法的逻辑，不依赖数据库、网络等外部资源
- 可控：可以模拟各种场景（正常、异常、边界值）
- 快速：不需要启动 Spring 容器、连接数据库，毫秒级完成
- 可重复：每次运行结果一致，不受外部环境影响

**测试金字塔**：
```
    /\     E2E 测试（端到端，慢，少）
   /  \    集成测试（中等）
  /____\   单元测试（快，多，基础）
```
单元测试应该占大多数，运行快、覆盖细。

### 11.3 怎么修改调整

**场景1：测试 Service 层方法**
```java
@Test
void testMethod() {
    // 1. Given（准备）：定义 Mock 行为
    when(userMapper.selectById(1L)).thenReturn(testUser);

    // 2. When（执行）：调用被测方法
    UserVO result = userService.getUserById(1L);

    // 3. Then（验证）：断言结果
    assertNotNull(result);
    assertEquals("testuser", result.getUsername());

    // 验证 Mock 方法被调用
    verify(userMapper, times(1)).selectById(1L);
}
```

**场景2：测试异常场景**
```java
@Test
void testNotFound() {
    when(userMapper.selectById(99L)).thenReturn(null);

    BusinessException exception = assertThrows(BusinessException.class,
        () -> userService.getUserById(99L));
    assertEquals(ResultCode.USERNAME_NOT_FOUND.getCode(), exception.getCode());
}
```

**场景3：Mock 返回 void 的方法**
```java
// 不做任何事
doNothing().when(userMapper).deleteById(1L);

// 抛出异常
doThrow(new RuntimeException("DB error")).when(userMapper).deleteById(1L);
```

**场景4：集成测试（启动 Spring 容器）**
```java
@SpringBootTest
@AutoConfigureMockMvc

    @Autowired
    private MockMvc mockMvc;

    @Test

        mockMvc.perform(get("/api/books/1"))
                .andExpect(status().isOk())
                .andExpect(jsonPath("$.code").value(20000));
    }
```

## 12. Docker 容器化部署

### 12.1 是什么

Docker 是一个容器化平台，将应用及其依赖打包到一个轻量级、可移植的容器中，确保应用在任何环境中都能一致运行。

**核心概念**：
- **Image（镜像）**：应用的只读模板，包含代码、运行时、依赖
- **Container（容器）**：镜像的运行实例，隔离的进程
- **Dockerfile**：构建镜像的脚本
- **docker-compose.yml**：多容器编排配置

### 12.2 本项目的 Docker Compose

```yaml
services:
  mysql:      # MySQL 8.0 数据库
  redis:      # Redis 7 缓存
  rabbitmq:   # RabbitMQ 3.12 消息队列（带管理界面）
```

**为什么用 Docker Compose？**
- 一键启动所有依赖服务，不需要手动安装
- 环境一致，团队成员使用相同的配置
- 隔离性好，不污染本地环境
- 可版本控制，docker-compose.yml 提交到 Git

### 12.3 怎么修改调整

**场景1：应用也容器化**
```dockerfile
# Dockerfile
FROM eclipse-temurin:17-jre-alpine
WORKDIR /app
COPY target/library-management-1.0.0.jar app.jar
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "app.jar"]
```
```yaml
# docker-compose.yml 中添加
app:
  build: .
  ports:
    - "8080:8080"
  depends_on:
    - mysql
    - redis
    - rabbitmq
  environment:
    SPRING_DATASOURCE_URL: jdbc:mysql://mysql:3306/library_db
    SPRING_DATA_REDIS_HOST: redis
    SPRING_RABBITMQ_HOST: rabbitmq
```

**场景2：修改服务端口**
```yaml
mysql:
  ports:
    - "3307:3306"  # 宿主机3307映射到容器3306
```

**场景3：数据持久化**
- docker-compose.yml 中已配置 volumes（mysql_data、redis_data、rabbitmq_data）
- 容器删除后数据不丢失
- 查看数据卷：`docker volume ls`
