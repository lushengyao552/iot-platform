# Stage 01：数据库设计

## 阶段目标

只根据业务需求，自己设计出全部核心表，想清楚主键、类型、约束、索引、时间字段、状态字段、外键与冗余。本阶段**不写任何 Java 代码**，只交 SQL 建表脚本。

## 前置要求

- stage00 毕业
- MySQL 8 已能连接
- 会用 DDL：CREATE TABLE / ALTER / CREATE INDEX

## 业务需求（你要据此刻设计）

系统需要支持：

1. **用户**：用户名、密码（加密存储）、昵称、邮箱、手机号、角色（普通用户/管理员）、状态（正常/禁用）、创建时间、更新时间
2. **分类**：分类名、父分类 ID（支持两级分类即可）、排序、状态
3. **图书**：书名、作者、ISBN、出版社、分类 ID、总库存、可借库存、图书简介、封面 URL、状态（在架/下架）、创建时间、更新时间
4. **借阅记录**：借阅人 ID、图书 ID、借出时间、应还时间、实际归还时间、状态（借出中/已归还/逾期）、罚款金额

## 本阶段知识点

- 主键选型：自增 BIGINT vs UUID（为什么这里选 BIGINT）
- 字段类型：VARCHAR 长度怎么定、TEXT 什么时候用、DECIMAL vs DOUBLE
- NULL vs NOT NULL vs DEFAULT
- UNIQUE：用户名唯一、ISBN 唯一
- 索引：普通索引、联合索引、唯一索引
- 外键：业务库要不要物理外键（讨论题）
- 时间字段：DATETIME vs TIMESTAMP、创建/更新时间谁来填
- 逻辑删除：deleted 字段
- 范式：三范式 vs 反范式（冗余字段什么时候加）

### 【第 1-1 题：画 ER 图 + 设计用户表】

**业务背景**
系统先要有用户。一个用户能登录、能借书、有角色。

**我的任务**
1. 自己画一张草图（纸上 / draw.io / 文字描述都行），把 user / book / category / borrow 四张表之间的关系画出来
2. 写出 `user` 表的完整建表 SQL

**限制条件**
- 密码字段长度要够存加密后的哈希（想想 bcrypt 多长）
- 用户名要唯一
- 要有逻辑删除字段
- 要有创建时间、更新时间
- 表名、字段名用小写下划线风格
- 每个字段必须有 COMMENT

**验收标准**
- 表能在 MySQL 8 里直接执行成功
- 你能说出每个字段为什么选这个类型、这个长度
- 你能说出为什么密码不能存明文
- 你能说出为什么 user_name 要加唯一索引

**思考题**
1. 为什么主键用 BIGINT 自增，而不是用用户名当主键？
2. 角色字段用 ENUM 还是 VARCHAR 还是 TINYINT？各有什么问题？
3. 逻辑删除字段 deleted 用 TINYINT 还是 DATETIME？
4. 邮箱和手机号要不要都建唯一索引？
5. 创建时间和更新时间，数据库自动填还是 Java 填？两种方案利弊？

### 【第 1-3 题：图书表】

**业务背景**
这是系统的核心表。一本图书有基本信息、有库存。

**我的任务**
写出 `book` 表的建表 SQL。

**限制条件**
- ISBN 唯一
- 分类外键到 category.id（物理外键要不要建，自己决定并说明理由）
- 总库存 total_stock、可借库存 available_stock 两个字段都要有
- 价格用 DECIMAL
- 书名列要加索引（业务上要按书名模糊查）
- 要有逻辑删除、创建时间、更新时间、状态

**验收标准**
- 能插入一本书
- ISBN 重复时数据库会拒绝（唯一约束）
- 你能说清 total_stock 和 available_stock 的区别
- 你能说清为什么 book_name 用普通索引，而不是唯一索引

**思考题**
1. 书名要做模糊搜索（like '%java%'），普通 B+ 树索引能用吗？怎么优化？
2. 为什么 price 用 DECIMAL(10,2) 而不是 FLOAT / DOUBLE？
3. 封面 URL 是存字符串还是存文件？
4. 为什么需要 status 字段？直接逻辑删除不就行了吗？
5. 分类关联用 category_id 还是冗余 category_name？

### 【第 1-4 题：借阅记录表】

**业务背景**
用户借书要留痕。一本书被谁借了、什么时候借的、什么时候还的，都要能查。

**我的任务**
写出 `borrow_record` 表的建表 SQL。

**限制条件**
- 记录借书人 user_id、图书 book_id
- 借出时间 borrow_time、应还时间 due_time、实际归还时间 return_time
- 状态：BORROWED / RETURNED / OVERDUE
- 罚款金额 fine_amount 默认 0
- 要有索引：按用户查借阅记录、按图书查借阅记录、按状态查逾期

**验收标准**
- 能查"某用户当前未还的所有书"
- 能查"所有逾期未还的记录"
- 你能说出为什么 book_id 和 user_id 都要加索引
- 你能说出为什么归还前 return_time 应该是 NULL 而不是 0

**思考题**
1. 一本图书在"借出中"状态下，能不能再借一次？数据库层面怎么防止？
2. 借阅记录里要不要冗余 user_name / book_name？
3. 逾期状态是借书时算好的，还是查的时候现算？
4. 罚款金额谁来更新？什么时候更新？

### 【第 1-5 题：综合评审与调优】

**业务背景**
四张表都写完了，现在整体过一遍。

**我的任务**

## 常见坑（盯这些）

- 密码字段长度写短了，bcrypt 60 字符存不下
- 时间字段忘了加 DEFAULT CURRENT_TIMESTAMP / ON UPDATE
- 该建唯一索引的地方只建了普通索引
- 外键建了但业务里没用上，维护成本高
- 金额用了 DOUBLE
