## 题目

### 【第 16-1 题：找慢 SQL】

**业务背景**
借阅记录查询越来越慢。

**我的任务**
1. 造数据：往 borrow_record 插 10 万条
2. 用 EXPLAIN 分析"查某用户借阅记录"的 SQL
3. 看 type / key / rows / Extra
4. 发现没走索引 → 加索引 → 再看
5. 发现 like '%xx%' 导致索引失效 → 讨论方案

**限制条件**
- 必须真造数据，不能凭感觉
- EXPLAIN 结果要能讲清每个字段
- 至少修 3 个慢查询

**验收标准**
- 你能现场读 EXPLAIN 结果
- 你能列出至少 5 种索引失效场景
- 慢 SQL 改完后 type 至少到 ref / range

**思考题**
1. EXPLAIN 里 type 的 system/const/ref/range/index/all 顺序？
2. Using filesort / Using temporary 是什么意思？
3. 联合索引 (a,b,c)，where b=? 能走索引吗？
4. 覆盖索引是什么？

### 【第 16-2 题：消灭 N+1】

**业务背景**
借阅记录列表现在联表 book 没问题，但如果又联表 category，或者循环查，就 N+1 了。

**我的任务**
1. 故意写一段有 N+1 的代码：循环每条借阅记录，bookMapper.selectById(bookId)
2. 打开 SQL 日志，数 SQL 条数
3. 改成一次 in() 查所有 book，在内存组装
4. 对比 SQL 条数

**限制条件**
- 理解 N+1 的本质
- 不要为了消除 N+1 写一个 JOIN 十张表的大 SQL（走向另一个极端）

**验收标准**
- 100 条记录，SQL 从 101 条降到 2 条
- 你能说清 N+1 怎么发现、怎么修
- 你能说清 MyBatis-Plus 的 in() 和 selectBatchIds

**思考题**
1. 什么是 N+1？
2. MyBatis 的 association / collection 怎么解决 N+1？
3. 什么时候 N+1 反而可以接受？
4. JOIN 太多表会不会慢？

### 【第 16-3 题：深分页优化】

**业务背景**
图书分页查第 1000 页时很慢。

**我的任务**
1. 造 10 万本图书
2. 测 page=1 size=10 和 page=10000 size=10 的耗时
3. 用 EXPLAIN 看为什么慢
4. 用"游标分页"（where id > lastId limit 10）或"延迟关联"优化
5. 对比耗时

**限制条件**
- 理解 limit offset 的问题
- 两种优化方案都试
- 业务上能接受游标分页的话（滚动加载）优先用

**验收标准**
- 你能说清 limit 10000,10 为什么慢
- 优化后深分页耗时下降明显
- 你能说出游标分页的业务限制（不能跳页）

**思考题**
1. 为什么 limit offset 慢？
2. 游标分页为什么快？
3. 延迟关联是什么？
4. 搜索引擎那种"无限滚动"用什么方案？

### 【第 16-4 题：应用层优化盘点】

**业务背景**
SQL 优化完，应用层还有哪些可以做。

**我的任务**
不写代码，盘点清单：
1. 连接池大小 HikariCP 怎么配
2. 线程池 / 异步 @Async 用对了吗
3. 循环里有没有查库 / 远程调用
4. 大对象有没有及时释放
5. 日志级别生产是 info 还是 debug
6. Redis 缓存命中率多少

**限制条件**
- 每一项都要能说出"怎么观察、怎么改"
- 不要堆术语

**验收标准**
- 你能现场说出 5 个应用层常见性能问题
- 你能说出一个请求从浏览器到数据库的完整路径
- 你能说出哪一步最容易出性能问题

**思考题**
1. 连接池大小是不是越大越好？
2. @Async 线程池不配置会怎样？
3. 怎么看 JVM 线程数？
4. 什么时候该加机器，什么时候该优化代码？

## 常见坑

- 加了索引但 SQL 写法导致索引失效
- 一上来就加机器不查 SQL
- N+1 自己不知道
- 深分页用 limit offset
- 循环里远程调用
- 大事务长时间持锁
