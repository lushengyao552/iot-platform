## 1. Java 基础

### 1.1 == 和 equals 的区别？

**答案**：
- `==`：比较两个对象的引用地址（基本类型比较值，引用类型比较内存地址）
- `equals()`：Object 类的方法，默认实现和 `==` 一样（比较地址），但很多类重写了它（如 String、Integer），重写后比较内容

**举例**：
```java
String a = new String("hello");
String b = new String("hello");
a == b;      // false（不同对象，地址不同）
a.equals(b); // true（String 重写了 equals，比较内容）
```

**追问：为什么重写 equals 必须重写 hashCode？**
- hashCode 约定：两个对象 equals 相等，hashCode 必须相等
- 如果只重写 equals 不重写 hashCode，两个相等的对象可能有不同的 hashCode
- 在 HashMap 等集合中，先根据 hashCode 定位桶，再用 equals 比较，会导致相等的对象找不到

### 1.2 String、StringBuilder、StringBuffer 的区别？

**答案**：

| 特性 | String | StringBuilder | StringBuffer |
|------|--------|---------------|--------------|
| 可变性 | 不可变（final char[]） | 可变 | 可变 |
| 线程安全 | 安全（不可变） | 不安全 | 安全（synchronized） |
| 性能 | 拼接时创建新对象，性能差 | 快 | 较慢（有锁开销） |
| 适用场景 | 常量、少量拼接 | 单线程大量拼接 | 多线程大量拼接 |

**原理**：
- String 不可变：`private final char value[]`，每次拼接（+）都会创建新的 String 对象
- StringBuilder/StringBuffer：内部是可扩容的 char[]，append 时直接修改数组，数组不够时扩容（2倍+2）

**追问：String 不可变的好处？**
1. 线程安全：多线程下不需要同步
2. 可以缓存 hashCode：String 的 hashCode 只计算一次
3. 字符串常量池：可以复用，节省内存
4. 安全性：作为参数传递时不会被修改（如数据库连接 URL、文件名）

### 1.3 重载和重写的区别？

**答案**：

| 特性 | 重载（Overload） | 重写（Override） |
|------|------------------|------------------|
| 位置 | 同一个类中 | 子类中 |
| 方法名 | 相同 | 相同 |
| 参数列表 | 不同（个数/类型/顺序） | 相同 |
| 返回值 | 无关 | 相同（或协变） |
| 异常 | 无关 | 可以缩小，不能扩大 |
| 权限 | 无关 | 可以扩大，不能缩小 |
| 多态 | 编译时多态（静态分派） | 运行时多态（动态分派） |

---

### 1.4 接口和抽象类的区别？

**答案**：

| 特性 | 接口（interface） | 抽象类（abstract class） |
|------|-------------------|--------------------------|
| 构造方法 | 没有 | 有 |
| 成员变量 | 只能是 public static final | 可以是各种修饰符 |
| 方法实现 | Java 8 前只能抽象方法；Java 8 后可以有 default/static 方法 | 可以有抽象方法和具体方法 |
| 多继承 | 一个类可以实现多个接口 | 一个类只能继承一个抽象类 |
| 设计理念 | 定义行为规范（can-do） | 模板/基类（is-a） |

**追问：Java 8 接口的 default 方法有什么用？**
- 接口新增方法时，不需要所有实现类都实现（提供默认实现）
- 解决接口演化问题（如 Collection 接口新增 forEach 方法）

---

### 1.5 final、finally、finalize 的区别？

**答案**：
- `final`：修饰符
  - 修饰类：不能被继承
  - 修饰方法：不能被重写
  - 修饰变量：不能被重新赋值（基本类型值不变，引用类型地址不变）
- `finally`：异常处理的一部分，`try-catch-finally` 中的 finally 块，无论是否异常都会执行（除非 JVM 退出）
- `finalize()`：Object 类的方法，对象被垃圾回收前调用，已废弃（Java 9 标记为 deprecated），不推荐使用

## 2. JVM 虚拟机

### 2.1 JVM 内存区域划分？

**答案**：

```
JVM 运行时数据区
├── 线程共享
│   ├── 堆（Heap）：存放对象实例，GC 主要区域
│   │   ├── 新生代（Eden + Survivor0 + Survivor1）
│   │   └── 老年代
│   └── 方法区（Method Area）：类信息、常量、静态变量、JIT 编译后的代码
│       └── 运行时常量池
└── 线程私有
    ├── 虚拟机栈（VM Stack）：栈帧（局部变量表、操作数栈、动态链接、方法出口）
    ├── 本地方法栈（Native Method Stack）：native 方法
    └── 程序计数器（PC Register）：当前线程执行的字节码行号
```

**追问：哪些区域会发生 OOM？**
- 堆：`java.lang.OutOfMemoryError: Java heap space`（对象太多）
- 方法区/元空间：`java.lang.OutOfMemoryError: Metaspace`（类太多，如动态代理）
- 虚拟机栈：`java.lang.StackOverflowError`（递归太深）或 OOM（栈太多）
- 直接内存：`java.lang.OutOfMemoryError`（NIO 使用堆外内存）

---

### 2.2 垃圾回收算法有哪些？

**答案**：

1. **标记-清除（Mark-Sweep）**
   - 过程：标记所有需要回收的对象 → 统一清除
   - 优点：简单
   - 缺点：产生内存碎片，效率不高

2. **标记-复制（Mark-Copy）**
   - 过程：将内存分为两块，每次只用一块，回收时将存活对象复制到另一块，然后清空当前块
   - 优点：没有碎片，效率高
   - 缺点：内存利用率只有 50%
   - 应用：新生代（Eden:Survivor = 8:1，因为大部分对象朝生夕死）

3. **标记-整理（Mark-Compact）**
   - 过程：标记存活对象 → 将存活对象向一端移动 → 清除边界外的内存
   - 优点：没有碎片
   - 缺点：需要移动对象，效率较低
   - 应用：老年代

4. **分代收集（Generational Collection）**
   - 新生代：标记-复制（对象存活率低）
   - 老年代：标记-清除 或 标记-整理（对象存活率高）

---

### 2.3 垃圾回收器有哪些？

**答案**：

| 回收器 | 代 | 算法 | 线程 | 特点 |
|--------|-----|------|------|------|
| Serial | 新生代 | 复制 | 单线程 | 简单，Client 模式默认 |
| ParNew | 新生代 | 复制 | 多线程 | Serial 的多线程版本，配合 CMS |
| Parallel Scavenge | 新生代 | 复制 | 多线程 | 吞吐量优先，Server 模式默认 |
| Serial Old | 老年代 | 标记-整理 | 单线程 | Serial 的老年代版本 |
| Parallel Old | 老年代 | 标记-整理 | 多线程 | Parallel Scavenge 的老年代版本 |
| CMS | 老年代 | 标记-清除 | 多线程 | 低延迟，并发收集 |
| G1 | 全代 | 标记-整理+复制 | 多线程 | 区域化，可预测停顿，JDK 9+ 默认 |
| ZGC | 全代 | - | 并发 | 极低延迟（<10ms），JDK 15 正式 |

**CMS 收集过程（面试高频）**：
1. 初始标记（STW）：标记 GC Roots 直接关联的对象，很快
2. 并发标记：从 GC Roots 开始遍历，与用户线程并发
3. 重新标记（STW）：修正并发标记期间变化的对象
4. 并发清除：清除标记的对象，与用户线程并发

**G1 的特点**：
- 将堆分为多个大小相等的 Region
- 每个 Region 可以是 Eden、Survivor、Old、Humongous
- 可预测停顿时间：根据允许的停顿时间选择回收价值最高的 Region
- 整体是标记-整理，局部是复制，没有碎片

---

### 2.4 什么是 GC Roots？哪些对象可以作为 GC Roots？

**答案**：
GC Roots 是垃圾回收的根对象，从这些对象开始遍历，能到达的对象是存活的，不可达的对象可以被回收。

**可以作为 GC Roots 的对象**：
1. 虚拟机栈中引用的对象（局部变量）
2. 本地方法栈中 JNI 引用的对象
3. 方法区中静态变量引用的对象
4. 方法区中常量引用的对象（如字符串常量池）
5. 被 synchronized 持有的对象
6. JVM 内部引用（系统类加载器、异常对象等）

---

### 2.5 对象的创建过程？

**答案**：
1. **类加载检查**：检查 new 指令的参数是否能在常量池中定位到类的符号引用，检查类是否已加载、解析、初始化
2. **分配内存**：
   - 指针碰撞（Bump the Pointer）：堆内存规整，指针移动对象大小的距离
   - 空闲列表（Free List）：堆内存不规整，维护空闲块列表
   - 并发安全：TLAB（Thread Local Allocation Buffer），每个线程在 Eden 分配一小块，避免加锁
3. **初始化零值**：将分配的内存空间初始化为零值（保证对象字段不初始化也有默认值）
4. **设置对象头**：Mark Word（哈希码、GC 分代年龄、锁状态）、类型指针（指向类元数据）
5. **执行 <init> 方法**：调用构造函数，初始化对象

---

### 2.6 类加载过程？

**答案**：
类加载分为 7 个阶段：
1. **加载（Loading）**：通过类的全限定名获取二进制字节流，将静态存储结构转化为方法区的运行时数据结构，生成 Class 对象
2. **验证（Verification）**：确保字节流符合 JVM 规范（文件格式、元数据、字节码、符号引用验证）
3. **准备（Preparation）**：为类变量（static）分配内存并设置零值（final static 在编译时确定）
4. **解析（Resolution）**：将常量池中的符号引用替换为直接引用（类、字段、方法、接口）
5. **初始化（Initialization）**：执行 `<clinit>` 方法（静态变量赋值 + 静态代码块）
6. **使用（Using）**
7. **卸载（Unloading）**

**类加载器**：
- 启动类加载器（Bootstrap ClassLoader）：加载 JAVA_HOME/lib 下的核心类
- 扩展类加载器（Extension ClassLoader）：加载 JAVA_HOME/lib/ext 下的扩展类
- 应用程序类加载器（Application ClassLoader）：加载用户类路径下的类
- 自定义类加载器：继承 ClassLoader

**双亲委派模型**：
- 类加载时先委托父加载器加载，父加载器加载不了才自己加载
- 好处：避免类的重复加载，保证核心类的安全（如自己写的 java.lang.String 不会被加载）

## 3. 集合框架

### 3.1 ArrayList 和 LinkedList 的区别？

**答案**：

| 特性 | ArrayList | LinkedList |
|------|-----------|------------|
| 底层结构 | 动态数组 | 双向链表 |
| 随机访问 | O(1) | O(n) |
| 插入/删除（尾部） | O(1)（扩容时 O(n)） | O(1) |
| 插入/删除（中间） | O(n)（需要移动元素） | O(1)（找到位置后） |
| 内存占用 | 少（只存数据） | 多（每个节点存数据+前驱+后继指针） |
| 遍历方式 | fori 效率高 | 迭代器效率高 |

**追问：ArrayList 扩容机制？**
- 默认初始容量 10（第一次 add 时才初始化）
- 扩容时容量变为原来的 1.5 倍（`oldCapacity + (oldCapacity >> 1)`）
- 扩容时需要复制数组到新数组（`Arrays.copyOf`），开销大
- 建议预估容量，减少扩容次数

### 3.2 HashMap 的底层原理？

**答案**：

**JDK 1.8 之前**：数组 + 链表
**JDK 1.8 及以后**：数组 + 链表 + 红黑树

**核心参数**：
- 初始容量：16（必须是 2 的幂）
- 负载因子：0.75
- 扩容阈值：容量 × 负载因子（16 × 0.75 = 12）
- 链表转红黑树阈值：链表长度 ≥ 8 且数组长度 ≥ 64
- 红黑树转链表阈值：节点数 ≤ 6

**put 过程**：
1. 计算 key 的 hashCode，通过扰动函数（`(h = key.hashCode()) ^ (h >>> 16)`）得到 hash
2. 计算数组下标：`(n - 1) & hash`（n 是数组长度，2 的幂时等价于取模）
3. 如果该位置没有元素，直接插入
4. 如果有元素（哈希冲突）：
   - key 相同（equals），覆盖 value
   - 是链表节点，遍历链表，key 相同覆盖，不同则尾插
   - 是红黑树节点，按红黑树方式插入
5. 链表长度达到 8 且数组长度 ≥ 64，链表转红黑树
6. 插入后判断是否需要扩容（size > 阈值），扩容为原来的 2 倍

**扩容（resize）**：
- 容量变为 2 倍
- 重新计算每个元素的位置：因为容量是 2 的幂，扩容后元素要么在原位置，要么在原位置 + 旧容量
- 不需要重新计算 hashCode，只需要看 hash 的新增位是 0 还是 1

**为什么容量是 2 的幂？**
- 计算下标用 `(n - 1) & hash` 代替取模，位运算效率高
- 扩容时元素位置只有两种可能，便于 rehash

**为什么负载因子是 0.75？**
- 时间和空间的权衡：太小浪费空间，太大哈希冲突多
- 0.75 时，桶空的概率符合泊松分布，冲突概率较低

### 3.3 HashMap 是线程安全的吗？ConcurrentHashMap 原理？

**答案**：
HashMap 不是线程安全的，多线程下可能出现：
- 数据丢失
- 死循环（JDK 1.7 扩容时头插法导致链表环）
- size 不准确

**ConcurrentHashMap 线程安全原理**：

**JDK 1.7**：分段锁（Segment）
- 内部是 Segment 数组，每个 Segment 是一个小的 HashMap
- 每次操作只锁一个 Segment，不同 Segment 可以并发
- 并发度 = Segment 数量（默认 16）

**JDK 1.8**：CAS + synchronized
- 取消 Segment，改用 Node 数组 + 链表 + 红黑树
- 插入空桶时用 CAS（`tabAt`/`casTabAt`）
- 插入已有桶时用 synchronized 锁桶头节点（锁粒度更小）
- size 计算用 CounterCell 数组（类似 LongAdder，分散计数，减少竞争）
- 扩容时多线程并发迁移（每个线程领一批桶迁移）

### 3.4 HashSet 和 HashMap 的关系？

**答案**：
- HashSet 底层就是 HashMap，value 固定为一个静态 Object 对象（`PRESENT`）
- add 方法调用 map.put(e, PRESENT)
- 利用 HashMap key 的唯一性保证 Set 元素不重复

## 4. 多线程与并发

### 4.1 线程的创建方式？

**答案**：
1. 继承 Thread 类，重写 run() 方法
2. 实现 Runnable 接口，重写 run() 方法，作为 Thread 的 target
3. 实现 Callable 接口，重写 call() 方法，通过 FutureTask 包装，可以有返回值和抛出异常
4. 使用线程池（`ExecutorService`）

**追问：Runnable 和 Callable 的区别？**
- Runnable：run() 无返回值，不能抛出受检异常
- Callable：call() 有返回值（泛型），可以抛出 Exception
- Callable 配合 Future/FutureTask 获取结果

---

### 4.2 线程的生命周期？

**答案**：

```
新建（NEW）→ 就绪（RUNNABLE）→ 运行（RUNNING）→ 终止（TERMINATED）
                    ↑                    ↓
                    └── 阻塞（BLOCKED/WAITING/TIMED_WAITING）←┘
```

1. **NEW**：new Thread() 后，还未调用 start()
2. **RUNNABLE**：调用 start() 后，等待 CPU 调度（就绪 + 运行合称 RUNNABLE）
3. **BLOCKED**：等待获取 synchronized 锁
4. **WAITING**：无限期等待（Object.wait()、Thread.join()、LockSupport.park()）
5. **TIMED_WAITING**：限时等待（Thread.sleep()、Object.wait(timeout)、Thread.join(timeout)）
6. **TERMINATED**：run() 执行完毕或异常退出

---

### 4.3 synchronized 和 ReentrantLock 的区别？

**答案**：

| 特性 | synchronized | ReentrantLock |
|------|-------------|----------------|
| 实现层面 | JVM 关键字 | JDK 类（API 层面） |
| 锁释放 | 自动（退出同步块） | 手动（必须 unlock()，通常在 finally） |
| 锁获取 | 一直等待 | 可超时（tryLock(timeout)）、可中断（lockInterruptibly()） |
| 公平锁 | 非公平 | 可选择公平/非公平 |
| 条件变量 | 只有一个（wait/notify） | 可绑定多个 Condition |
| 可重入 | 支持 | 支持 |
| 性能 | 优化后性能好 | 类似 |

**追问：synchronized 的底层原理？**
- 基于对象头的 Mark Word 和监视器（Monitor）
- 锁升级过程：无锁 → 偏向锁 → 轻量级锁 → 重量级锁
  - 偏向锁：只有一个线程访问时，Mark Word 记录线程 ID，下次直接进入
  - 轻量级锁：多个线程交替访问，CAS 竞争 Mark Word，失败则自旋
  - 重量级锁：自旋超过次数或多个线程同时竞争，升级为 Monitor，阻塞线程

---

### 4.4 volatile 的作用和原理？

**答案**：
volatile 有两个作用：
1. **可见性**：一个线程修改 volatile 变量，其他线程立即可见
   - 原理：修改后立即刷新到主内存，读取时直接从主内存读（绕过工作内存）
   - 内存屏障：写操作后加 StoreLoad 屏障，读操作前加 LoadLoad 屏障
2. **禁止指令重排序**：编译器和 CPU 不会对 volatile 变量的操作进行重排序
   - 原理：内存屏障保证 volatile 写之前的操作不会重排到后面，读之后的操作不会重排到前面

**volatile 不能保证原子性**：如 `count++` 不是原子操作（读-改-写三步），多线程下仍会有问题。

**应用场景**：
- 状态标志（如 `volatile boolean running = true`）
- 双重检查锁定（DCL）单例模式中的 instance 变量
- happens-before 原则的实现

---

### 4.5 ThreadLocal 的原理和内存泄漏？

**答案**：
ThreadLocal 提供线程本地变量，每个线程有自己的副本，线程间隔离。

**原理**：
- 每个 Thread 对象有一个 `threadLocals` 字段（ThreadLocalMap 类型）
- ThreadLocalMap 是一个自定义的 Map，key 是 ThreadLocal 对象（弱引用），value 是线程本地变量值
- `threadLocal.set(value)`：获取当前线程的 ThreadLocalMap，以 threadLocal 为 key 存入 value
- `threadLocal.get()`：获取当前线程的 ThreadLocalMap，以 threadLocal 为 key 取出 value

**内存泄漏问题**：
- ThreadLocalMap 的 key 是弱引用（WeakReference），GC 时 key 会被回收
- 但 value 是强引用，线程不结束的话 value 不会被回收
- 如果 ThreadLocal 对象被回收了（key 变 null），但 value 还在，就无法访问也无法回收，造成内存泄漏
- 解决：使用完后调用 `threadLocal.remove()` 手动清除

**应用场景**：
- 数据库连接（每个线程一个连接）
- 用户上下文（如本项目的 UserContext，存当前登录用户）
- 日期格式化（SimpleDateFormat 非线程安全，每个线程一个）

---

### 4.6 线程池的核心参数和工作流程？

**答案**：

**ThreadPoolExecutor 核心参数**：
1. `corePoolSize`：核心线程数，即使空闲也保留（除非 allowCoreThreadTimeOut）
2. `maximumPoolSize`：最大线程数
3. `keepAliveTime`：非核心线程空闲超时时间
4. `unit`：时间单位
5. `workQueue`：任务队列（BlockingQueue）
6. `threadFactory`：线程工厂（创建线程，可设置线程名、守护状态等）
7. `handler`：拒绝策略（队列满且达到最大线程数时的处理策略）

**工作流程**：
```
任务提交
  ↓
当前线程数 < corePoolSize？→ 是 → 创建核心线程执行任务
  ↓ 否
队列未满？→ 是 → 加入队列等待
  ↓ 否
当前线程数 < maximumPoolSize？→ 是 → 创建非核心线程执行任务
  ↓ 否
执行拒绝策略
```

**拒绝策略**：
1. `AbortPolicy`（默认）：抛出 RejectedExecutionException
2. `CallerRunsPolicy`：由提交任务的线程执行
3. `DiscardPolicy`：直接丢弃任务
4. `DiscardOldestPolicy`：丢弃队列中最旧的任务，然后重新提交

**常见线程池（Executors 创建）**：
- `newFixedThreadPool`：固定线程数，无界队列（LinkedBlockingQueue）
- `newCachedThreadPool`：弹性线程数，60秒回收，同步队列（SynchronousQueue）
- `newSingleThreadExecutor`：单线程，保证顺序执行
- `newScheduledThreadPool`：定时/周期任务

**注意**：阿里开发规范不推荐用 Executors 创建线程池，因为无界队列可能 OOM，应该直接用 ThreadPoolExecutor 构造。

### 4.7 AQS 原理？

**答案**：
AQS（AbstractQueuedSynchronizer）是 JUC 包的核心，是构建锁和同步器的框架。

**核心思想**：
- 用一个 `volatile int state` 表示同步状态（如 ReentrantLock 中 state=0 表示无锁，state>0 表示重入次数）
- 用一个 CLH 队列（双向链表）存放等待线程
- 线程获取锁失败时，封装为 Node 加入队列，然后阻塞（LockSupport.park()）
- 锁释放时，唤醒队列头节点的后继线程（LockSupport.unpark()）

**两种模式**：
- 独占模式（Exclusive）：同一时间只有一个线程持有锁（如 ReentrantLock）
- 共享模式（Share）：多个线程可以同时持有锁（如 Semaphore、CountDownLatch）

**AQS 的子类**：
- ReentrantLock：独占锁
- Semaphore：信号量（共享）
- CountDownLatch：倒计时门闩（共享）
- CyclicBarrier：循环栅栏
- ReentrantReadWriteLock：读写锁（读共享，写独占）

## 5. Spring 框架

### 5.1 Spring IOC 原理？

**答案**：
IOC（Inversion of Control，控制反转）：对象的创建和依赖管理交给 Spring 容器，而不是自己 new。

**DI（Dependency Injection，依赖注入）**：IOC 的实现方式，容器将依赖对象注入到需要它的对象中。

**核心流程**：
1. **资源定位**：通过 `ResourceLoader` 加载配置文件（XML/注解）
2. **BeanDefinition 加载**：将配置解析为 `BeanDefinition`（Bean 的元数据，包含类名、作用域、依赖关系等）
3. **BeanDefinition 注册**：注册到 `BeanDefinitionRegistry`（DefaultListableBeanFactory 中的 beanDefinitionMap）
4. **Bean 实例化**：
   - 实例化：通过反射创建对象（`newInstance()` 或 CGLIB）
   - 属性填充：依赖注入（@Autowired 字段/setter 注入）
   - 初始化：执行 `@PostConstruct`、`InitializingBean.afterPropertiesSet()`、init-method
   - 放入单例池（`singletonObjects`）
5. **获取 Bean**：`getBean()` 从容器获取

**Bean 的生命周期（面试高频）**：
1. 实例化（构造函数）
2. 属性注入（@Autowired）
3. Aware 接口回调（BeanNameAware、BeanFactoryAware、ApplicationContextAware）
4. BeanPostProcessor.postProcessBeforeInitialization（初始化前处理）
5. 初始化：@PostConstruct → InitializingBean.afterPropertiesSet() → init-method
6. BeanPostProcessor.postProcessAfterInitialization（初始化后处理，AOP 代理在这里生成）
7. 使用
8. 销毁：@PreDestroy → DisposableBean.destroy() → destroy-method

---

### 5.2 Spring AOP 原理？

**答案**：
AOP（Aspect-Oriented Programming，面向切面编程）：将横切关注点（日志、事务、权限、监控）从业务代码中分离出来，通过动态代理在运行时织入。

**核心概念**：
- 切面（Aspect）：横切关注点的模块化（如日志切面）
- 连接点（JoinPoint）：程序执行的某个点（方法调用）
- 切入点（Pointcut）：匹配连接点的表达式（如 `execution(* com.example..*.*(..))`）
- 通知（Advice）：在连接点执行的动作
  - 前置通知（@Before）
  - 后置通知（@AfterReturning）
  - 异常通知（@AfterThrowing）
  - 最终通知（@After）
  - 环绕通知（@Around）
- 织入（Weaving）：将切面应用到目标对象的过程（编译期/类加载期/运行期）
- 目标对象（Target）：被代理的对象
- 代理对象（Proxy）：AOP 框架生成的对象

**动态代理实现**：
- **JDK 动态代理**：目标类实现接口时使用，基于接口生成代理类（`Proxy.newProxyInstance`）
- **CGLIB 动态代理**：目标类没有实现接口时使用，基于继承生成子类（`Enhancer.create`）
- Spring Boot 2.x 默认使用 CGLIB（`spring.aop.proxy-target-class=true`）

**本项目中的 AOP 应用**：
- `@Transactional`：事务管理（Spring AOP 实现）
- 全局异常处理（`@RestControllerAdvice`，本质也是 AOP）

---

### 5.3 Spring 事务传播行为？

**答案**：
事务传播行为定义了多个事务方法相互调用时，事务如何传播。

| 传播行为 | 说明 |
|----------|------|
| REQUIRED（默认） | 有事务就加入，没有就新建 |
| REQUIRES_NEW | 总是新建事务，挂起当前事务 |
| SUPPORTS | 有事务就加入，没有就非事务运行 |
| NOT_SUPPORTED | 非事务运行，挂起当前事务 |
| MANDATORY | 必须在事务中运行，没有则抛异常 |
| NEVER | 必须非事务运行，有事务则抛异常 |
| NESTED | 嵌套事务（保存点），外层回滚影响内层，内层回滚不影响外层 |

**追问：事务失效的场景？**
1. 方法不是 public
2. 同类中方法调用（this.method() 不走代理）
3. 异常被 try-catch 捕获
4. 抛出的异常不是 RuntimeException（没有设置 rollbackFor）
5. 数据库引擎不支持事务（MyISAM）
6. 多线程环境（事务和线程绑定，新线程不在事务中）
7. @Transactional 注解在接口上但用 CGLIB 代理

## 6. Spring Boot

### 6.1 Spring Boot 自动配置原理？

**答案**：
1. `@SpringBootApplication` 包含 `@EnableAutoConfiguration`
2. `@EnableAutoConfiguration` 通过 `@Import(AutoConfigurationImportSelector.class)` 导入自动配置类
3. `AutoConfigurationImportSelector` 读取 `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports` 文件
4. 该文件列出所有自动配置类的全限定名
5. 每个自动配置类使用 `@ConditionalOnXxx` 注解判断是否生效
   - `@ConditionalOnClass`：classpath 有指定类
   - `@ConditionalOnMissingBean`：容器中没有指定 Bean
   - `@ConditionalOnProperty`：配置文件有指定属性
6. 符合条件的自动配置类注册到容器，完成自动配置

**举例**：当 classpath 中有 `spring-boot-starter-web` 时，`ServletWebServerFactoryAutoConfiguration` 自动配置内嵌 Tomcat。

## 7. MyBatis

### 7.1 MyBatis 工作原理？

**答案**：
1. **读取配置**：`SqlSessionFactoryBuilder` 读取 mybatis-config.xml 和 Mapper XML，构建 `Configuration` 对象
2. **创建 SqlSessionFactory**：`new DefaultSqlSessionFactory(configuration)`
3. **创建 SqlSession**：`factory.openSession()`，创建 `DefaultSqlSession`（包含 Executor、Configuration）
4. **获取 Mapper 代理**：`sqlSession.getMapper(UserMapper.class)`，通过 JDK 动态代理生成 Mapper 代理对象（`MapperProxy`）
5. **执行 SQL**：
   - 调用 Mapper 接口方法 → MapperProxy.invoke() → MapperMethod.execute()
   - 根据 SQL 类型选择 Executor 的方法（select/insert/update/delete）
   - Executor 通过 StatementHandler 执行 SQL
   - ParameterHandler 设置参数，ResultSetHandler 处理结果集
6. **一级缓存/二级缓存**：
   - 一级缓存：SqlSession 级别，默认开启，同一个 SqlSession 内相同查询缓存
   - 二级缓存：Mapper（namespace）级别，需要配置开启，跨 SqlSession 共享

### 7.2 MyBatis #{} 和 ${} 的区别？

**答案**：
- `#{}`：预编译（PreparedStatement），参数用 `?` 占位，安全，防止 SQL 注入
- `${}`：字符串拼接，直接替换为参数值，不安全，有 SQL 注入风险

**使用场景**：
- `#{}`：绝大多数参数传递（如 WHERE id = #{id}）
- `${}`：需要动态拼接 SQL 结构时（如 ORDER BY ${sortField}、表名、列名）

**追问：MyBatis 如何防止 SQL 注入？**
- 使用 `#{}` 预编译参数
- `${}` 只用于表名、列名、排序字段等 SQL 结构，且需要白名单校验

### 7.3 MyBatis-Plus 和 MyBatis 的区别？

**增强点**：

**本项目使用 MyBatis-Plus 的原因**：
- 国内企业最常用

- 功能丰富，满足绝大多数业务需求

## 8. MySQL 数据库

### 8.1 MySQL 索引原理？

**答案**：
索引是帮助 MySQL 高效获取数据的数据结构。

**InnoDB 索引结构**：B+ 树
- 非叶子节点：存储索引键和子节点指针
- 叶子节点：存储所有数据（聚簇索引）或主键值（二级索引）
- 叶子节点通过双向链表连接，便于范围查询

**聚簇索引 vs 二级索引**：
- 聚簇索引：主键索引，叶子节点存储整行数据。一张表只有一个。
- 二级索引：非主键索引，叶子节点存储主键值。查询需要回表。

**回表**：通过二级索引找到主键，再通过聚簇索引找到完整数据。

**覆盖索引**：查询的字段都在索引中，不需要回表。

**最左前缀原则**：联合索引 (a,b,c) 支持 a、a,b、a,b,c 的查询。

**索引失效场景（面试高频）**：
1. 对索引列使用函数、运算（如 `WHERE YEAR(create_time) = 2024`）
2. 隐式类型转换（如字符串列用数字查询）
3. LIKE 以 % 开头（`LIKE '%abc'`）
4. OR 连接的条件中有非索引列
5. 联合索引不满足最左前缀
6. 使用 !=、NOT IN、NOT EXISTS（可能失效，优化器决定）
7. 数据量小，优化器认为全表扫描更快

---

### 8.2 MySQL 事务的 ACID？

**答案**：
- **A（Atomicity，原子性）**：事务是最小执行单元，要么全部成功，要么全部回滚。实现：undo log（回滚日志）
- **C（Consistency，一致性）**：事务执行前后，数据从一个一致状态变为另一个一致状态。实现：由其他三个特性保证 + 业务逻辑正确
- **I（Isolation，隔离性）**：多个事务并发执行时，互不干扰。实现：锁 + MVCC
- **D（Durability，持久性）**：事务提交后，数据永久保存，即使宕机也不丢失。实现：redo log（重做日志）

---

### 8.3 事务隔离级别？

**答案**：

| 隔离级别 | 脏读 | 不可重复读 | 幻读 |
|----------|------|-----------|------|
| 读未提交（Read Uncommitted） | 可能 | 可能 | 可能 |
| 读已提交（Read Committed） | 不可能 | 可能 | 可能 |
| 可重复读（Repeatable Read，MySQL 默认） | 不可能 | 不可能 | 可能（InnoDB 通过 MVCC+间隙锁解决） |
| 串行化（Serializable） | 不可能 | 不可能 | 不可能 |

- **脏读**：读到其他事务未提交的数据
- **不可重复读**：同一事务内两次读取同一行数据，结果不同（其他事务修改并提交）
- **幻读**：同一事务内两次范围查询，结果行数不同（其他事务插入/删除并提交）

**MVCC（多版本并发控制）原理**：
- 每行数据有隐藏字段：`trx_id`（最近修改事务ID）、`roll_pointer`（指向 undo log 版本链）
- 读操作时，根据事务的 ReadView 判断哪个版本可见
- ReadView 包含：m_ids（活跃事务ID列表）、min_trx_id、max_trx_id、creator_trx_id
- 可见性判断：trx_id < min_trx_id 可见；trx_id > max_trx_id 不可见；在 m_ids 中不可见，否则可见
- RC 级别：每次 SELECT 都生成新的 ReadView
- RR 级别：第一次 SELECT 生成 ReadView，后续复用

---

### 8.4 MySQL 锁？

**答案**：

**按粒度分**：
- 全局锁：锁定整个数据库（`FLUSH TABLES WITH READ LOCK`），用于全库备份
- 表级锁：锁定整张表（表锁、元数据锁 MDL、意向锁）
- 行级锁：锁定行（InnoDB 支持）

**InnoDB 行锁类型**：
- Record Lock：记录锁，锁定单行
- Gap Lock：间隙锁，锁定间隙（不包含记录本身），防止幻读
- Next-Key Lock：临键锁 = Record Lock + Gap Lock，锁定左开右闭区间，RR 级别默认

**加锁规则（RR 级别）**：
- 唯一索引等值查询：命中记录时退化为 Record Lock，未命中时退化为 Gap Lock
- 普通索引等值查询：Next-Key Lock + 向右遍历到不满足条件时加 Gap Lock
- 范围查询：Next-Key Lock
- 没有索引：全表扫描，所有行加 Record Lock，间隙加 Gap Lock（相当于锁表）

**乐观锁 vs 悲观锁**：
- 悲观锁：认为并发冲突多，操作前先加锁（`SELECT ... FOR UPDATE`）
- 乐观锁：认为并发冲突少，不加锁，更新时用版本号判断（`UPDATE ... SET version=version+1 WHERE id=? AND version=?`）

---

### 8.5 MySQL 主从复制原理？

**答案**：
1. **主库（Master）**：将数据变更写入 binlog（二进制日志）
2. **从库（Slave）**：IO 线程连接主库，请求 binlog，写入 relay log（中继日志）
3. **从库 SQL 线程**：读取 relay log，重放 SQL，实现数据同步

**binlog 格式**：
- STATEMENT：记录 SQL 语句（可能有数据不一致问题，如 now()）
- ROW：记录行数据变化（安全，日志量大）
- MIXED：混合模式，一般用 STATEMENT，特殊情况用 ROW

**主从延迟原因**：
- 从库性能差
- 大事务（主库执行时间长，从库重放也慢）
- 网络延迟
- 从库单线程重放（MySQL 5.7 后支持并行复制）

### 9.2 Redis 持久化？

**RDB（Redis Database）**：

- 触发：手动（save/bgsave）、自动（配置 save 规则）、主从复制、shutdown
- 优点：文件紧凑，恢复速度快，适合备份
- 缺点：可能丢失最后一次快照后的数据（fork 子进程，大数据时耗时）

**AOF（Append Only File）**：
- 原理：记录每个写命令，追加到 AOF 文件（appendonly.aof）
- 触发：always（每条命令都刷盘，最安全最慢）、everysec（每秒刷盘，默认，推荐）、no（操作系统决定）
- 重写：AOF 文件过大时，fork 子进程重写，只保留恢复数据的最小命令集
- 优点：数据安全性高，最多丢失1秒数据
- 缺点：文件大，恢复速度慢

**混合持久化（Redis 4.0+）**：
- AOF 重写时，前半部分是 RDB 格式的快照，后半部分是增量命令
- 兼顾恢复速度和数据安全

---

### 9.3 Redis 缓存三大问题？

**答案**：

**1. 缓存穿透**：查询不存在的数据，缓存永远不命中，请求都打到数据库
- 危害：数据库压力大，可能被恶意攻击
- 解决方案：
  - 缓存空值：`redis.set(key, null, 5min)`，短时间过期
  - 布隆过滤器：将所有可能存在的数据哈希到足够大的 bitmap，不存在的直接拦截

**2. 缓存击穿**：热点 key 过期瞬间，大量并发请求打到数据库
- 危害：数据库瞬时压力大
- 解决方案：
  - 互斥锁：只让一个请求查数据库，其他等待（本项目分布式锁的思路）
  - 逻辑过期：不设真正过期，数据中存逻辑过期时间，异步更新

**3. 缓存雪崩**：大量 key 同时过期，或 Redis 宕机，请求全部打到数据库
- 危害：数据库压力过大，可能宕机
- 解决方案：
  - 过期时间加随机值，避免同时过期
  - Redis 集群（主从、哨兵、Cluster），高可用
  - 服务降级/限流，保护数据库
  - 多级缓存（本地缓存 + Redis）

---

### 9.4 Redis 分布式锁？

**答案**：

**实现要求**：
1. 互斥性：同一时间只有一个客户端持有锁
2. 防死锁：锁有过期时间，客户端宕机也能自动释放
3. 解铃还须系铃人：只能释放自己的锁
4. 可重入性：同一客户端可多次获取（可选）
5. 高可用：Redis 集群

**本项目实现**：
- 加锁：`SET key value NX EX timeout`（原子操作）
- value：UUID（唯一标识锁的持有者）
- 释放锁：Lua 脚本（判断 value 匹配才删除，保证原子性）

**Redisson（更完善的分布式锁）**：
- 可重入锁：记录重入次数（Hash 结构）
- 看门狗：业务未执行完时自动续期（默认30秒，每10秒检查续期）
- 公平锁/非公平锁
- 读写锁
- 红锁（RedLock）：多节点部署，大多数节点获取成功才算成功

---

### 9.5 Redis 过期删除策略？

**答案**：
- **惰性删除**：访问 key 时才检查是否过期，过期则删除。对 CPU 友好，对内存不友好。
- **定期删除**：每隔一段时间随机抽取一些 key 检查，过期则删除。折中方案。
- Redis 同时使用这两种策略。

**内存淘汰策略（内存满时）**：
- noeviction（默认）：不淘汰，写操作报错
- allkeys-lru：所有 key 中淘汰最近最少使用的
- allkeys-lfu：所有 key 中淘汰最不经常使用的
- allkeys-random：所有 key 中随机淘汰
- volatile-lru：设置了过期时间的 key 中淘汰最近最少使用的
- volatile-lfu：设置了过期时间的 key 中淘汰最不经常使用的
- volatile-random：设置了过期时间的 key 中随机淘汰
- volatile-ttl：设置了过期时间的 key 中淘汰最早过期的

## 10. RabbitMQ

### 10.1 RabbitMQ 核心概念？

**答案**：
- Producer：生产者，发送消息
- Consumer：消费者，接收消息
- Queue：队列，存储消息
- Exchange：交换机，接收消息并路由到队列
- Binding：绑定，定义 Exchange 和 Queue 的路由规则
- Routing Key：路由键，Exchange 根据它路由
- Virtual Host：虚拟主机，逻辑隔离

**Exchange 类型**：
- Direct：精确匹配 routing key
- Topic：通配符匹配（* 匹配一个词，# 匹配零个或多个词）
- Fanout：广播到所有绑定队列
- Headers：根据消息头匹配

---

### 10.2 如何保证消息不丢失？

**答案**：

**1. 生产者端**：
- Publisher Confirm：消息到达 Exchange 后回调确认
- Publisher Return：消息无法路由到 Queue 时返回
- 失败重试 + 本地消息表（记录消息状态，定时补偿）

**2. RabbitMQ 端**：
- Exchange 持久化：`durable(true)`
- Queue 持久化：`QueueBuilder.durable()`
- 消息持久化：`deliveryMode=PERSISTENT`
- 镜像队列（高可用，多节点副本）

**3. 消费者端**：
- 手动 ACK：处理完才确认，失败则 NACK（可重新入队或进死信队列）
- 幂等性：防止重复消费（用 messageId 去重）
- 失败重试 + 死信队列（重试多次失败后进死信队列，人工处理）

---

### 10.3 如何保证消息顺序？

**答案**：
- 单队列 + 单消费者：严格保证顺序，但吞吐量低
- 按业务 ID 哈希到不同队列：同一业务 ID 的消息到同一队列，每个队列单消费者
- 本项目中，同一用户的借阅/归还消息可以按 userId 路由到同一队列

---

### 10.4 死信队列（DLX）？

**答案**：
消息变成死信的情况：
1. 消费者拒绝（basicNack/basicReject）且 requeue=false
2. 消息 TTL 过期
3. 队列达到最大长度

**原理**：
- 队列配置 `x-dead-letter-exchange` 和 `x-dead-letter-routing-key`
- 消息变成死信后，自动转发到死信交换机
- 死信交换机路由到死信队列
- 消费者从死信队列消费，处理失败消息或延迟消息

**本项目应用**：延迟消息（借阅到期提醒）
- 消息发到延迟队列 → 等待 TTL（60秒）过期 → 转发到死信交换机 → 死信队列 → 消费者消费

---

### 10.5 RabbitMQ 和 Kafka 的区别？

**答案**：

| 特性 | RabbitMQ | Kafka |
|------|----------|-------|
| 定位 | 消息代理（Message Broker） | 分布式流处理平台 |
| 协议 | AMQP | 自定义 TCP 协议 |
| 模型 | Exchange → Queue → Consumer | Topic → Partition → Consumer Group |
| 吞吐量 | 万级 | 百万级 |
| 延迟 | 微秒级 | 毫秒级 |
| 消息保留 | 消费后删除（可配置） | 按时间/大小保留，可重复消费 |
| 顺序保证 | 队列内有序 | 分区内有序 |
| 适用场景 | 业务消息、RPC、任务分发 | 日志、大数据、流处理、事件溯源 |

---

## 11. 微服务

### 11.1 微服务和单体的区别？

**答案**：

| 维度 | 单体 | 微服务 |
|------|------|--------|
| 部署 | 一个应用 | 多个服务独立部署 |
| 扩展 | 整体扩展 | 按需扩展 |
| 技术栈 | 统一 | 可异构 |
| 数据库 | 通常共享 | 每服务独立 |
| 通信 | 方法调用 | 网络调用 |
| 复杂度 | 低 | 高 |
| 数据一致性 | 本地事务 | 分布式事务 |
| 适合 | 小型项目 | 大型项目、团队协作 |

---

### 11.2 微服务核心组件？

**答案**：
1. **服务注册与发现**：Nacos、Eureka、Consul
   - 服务启动时注册地址，调用时查询地址
2. **配置中心**：Nacos Config、Spring Cloud Config
   - 统一管理配置，动态刷新
3. **服务网关**：Spring Cloud Gateway、Zuul
   - 统一入口、路由、鉴权、限流、日志
4. **负载均衡**：Spring Cloud LoadBalancer、Ribbon
   - 客户端负载均衡，选择服务实例
5. **服务调用**：OpenFeign
   - 声明式 HTTP 客户端，像调用本地方法一样调用远程服务
6. **熔断降级**：Sentinel、Resilience4j、Hystrix
   - 防止级联故障，服务不可用时返回降级结果
7. **分布式事务**：Seata
   - 跨服务事务一致性（AT/TCC/SAGA/XA 模式）
8. **链路追踪**：Sleuth + Zipkin、SkyWalking
   - 追踪请求在微服务间的调用链路
9. **消息队列**：RabbitMQ、Kafka
   - 异步通信、解耦、削峰

---

### 11.3 服务注册发现原理？

**答案**：
以 Nacos 为例：
1. **服务注册**：服务启动时，向 Nacos Server 注册自己的地址（IP+端口+服务名）
2. **服务发现**：服务消费者从 Nacos Server 获取服务提供者的地址列表
3. **心跳续约**：服务提供者定期（默认5秒）发送心跳，证明自己还活着
4. **服务剔除**：Nacos Server 15秒没收到心跳则标记不健康，30秒没收到则剔除
5. **本地缓存**：消费者本地缓存服务地址列表，定时更新，减少 Nacos 压力

---

### 11.4 分布式事务解决方案？

**答案**：

**1. 2PC（两阶段提交）**：
- 准备阶段：协调者通知所有参与者准备提交，参与者执行事务但不提交，返回是否可以提交
- 提交阶段：所有参与者都同意则提交，否则回滚
- 缺点：同步阻塞，单点故障，数据不一致风险

**2. TCC（Try-Confirm-Cancel）**：
- Try：预留资源（冻结金额、锁定库存）
- Confirm：确认提交（扣减冻结金额、扣减锁定库存）
- Cancel：取消提交（解冻金额、解锁库存）
- 优点：性能好，最终一致
- 缺点：业务侵入大，需要写三个方法

**3. SAGA**：
- 将长事务拆分为多个本地事务，每个事务有补偿操作
- 正向执行成功则继续，失败则反向执行补偿操作
- 适合长事务、参与者多的场景

**4. 本地消息表（本项目思路）**：
- 业务操作和消息记录在同一个本地事务中
- 定时任务扫描消息表，发送到 MQ
- 消费者消费消息，保证最终一致性

**5. 事务消息（RocketMQ）**：
- 发送半消息 → 执行本地事务 → 提交/回滚消息 → 消费者消费
- RocketMQ 原生支持，本项目用 RabbitMQ 可以用本地消息表替代

---

### 11.5 网关的作用？

**答案**：
- 统一入口：所有请求经过网关，后端服务对客户端透明
- 路由转发：根据路径/规则转发到对应服务
- 认证鉴权：统一登录校验、权限检查
- 限流熔断：保护后端服务，防止过载
- 日志监控：统一记录请求日志
- 缓存：缓存热点数据
- 跨域处理：统一处理 CORS

## 12. 设计模式

### 12.1 单例模式？

**答案**：
保证一个类只有一个实例，并提供全局访问点。

**实现方式**：
1. **饿汉式**：类加载时就创建实例
   - 优点：线程安全，简单
   - 缺点：不能延迟加载，浪费内存
2. **懒汉式**：第一次使用时创建
   - 优点：延迟加载
   - 缺点：需要加锁保证线程安全，性能差
3. **双重检查锁定（DCL）**：
   ```java
   public class Singleton {
       private static volatile Singleton instance;
       private Singleton() {}
       public static Singleton getInstance() {
           if (instance == null) {
               synchronized (Singleton.class) {
                   if (instance == null) {
                       instance = new Singleton();
                   }
               }
           }
           return instance;
       }
   }
   ```
   - volatile 防止指令重排序（new 对象分三步：分配内存、初始化、赋值，重排序可能导致其他线程拿到未初始化的对象）
4. **静态内部类**：
   ```java
   public class Singleton {
       private Singleton() {}
       private static class Holder {
           private static final Singleton INSTANCE = new Singleton();
       }
       public static Singleton getInstance() {
           return Holder.INSTANCE;
       }
   }
   ```
   - 利用类加载机制保证线程安全，延迟加载（Holder 类只在 getInstance 调用时加载）
5. **枚举**：
   ```java
   public enum Singleton {
       INSTANCE;
   }
   ```
   - 最简单，线程安全，防止反射和序列化破坏（《Effective Java》推荐）

**Spring 中的单例**：Spring Bean 默认 singleton 作用域，由 Spring 容器保证单例（不是单例模式，是容器管理的单例）。

---

### 12.2 工厂模式？

**答案**：
将对象的创建和使用分离，由工厂类负责创建对象。

**三种形式**：
1. **简单工厂**：一个工厂类根据参数创建不同产品（不符合开闭原则）
2. **工厂方法**：定义工厂接口，每个产品有对应的工厂实现（符合开闭原则，类多）
3. **抽象工厂**：创建一系列相关产品（产品族），如不同品牌的手机+电脑

**Spring 中的工厂模式**：
- `BeanFactory`：Spring 最核心的接口，负责创建和管理 Bean
- `FactoryBean`：自定义 Bean 的创建逻辑（复杂对象创建）
- `ObjectFactory`：延迟注入

---

### 12.3 代理模式？

**答案**：
为目标对象提供一个代理，控制对目标对象的访问。

**两种代理**：
1. **静态代理**：代理类和目标类实现同一接口，代理类持有目标类引用，编译时就确定
2. **动态代理**：运行时动态生成代理类
   - JDK 动态代理：基于接口，`Proxy.newProxyInstance`
   - CGLIB 动态代理：基于继承，`Enhancer.create`

**Spring AOP 就是动态代理的应用**：
- 目标类有接口时用 JDK 动态代理
- 没有接口时用 CGLIB 动态代理
- 在代理对象中织入切面逻辑（日志、事务、权限等）

---

### 12.4 策略模式？

**答案**：
定义一系列算法，将每个算法封装起来，使它们可以互相替换，算法变化不影响使用算法的客户端。

**结构**：
- Strategy（策略接口）：定义算法方法
- ConcreteStrategy（具体策略）：实现具体算法
- Context（上下文）：持有策略引用，客户端调用

**应用场景**：
- 支付方式（微信、支付宝、银行卡）
- 促销策略（满减、折扣、秒杀）
- 排序算法（冒泡、快排、归并）

**本项目可以扩展**：通知发送策略（站内信、邮件、短信），不同通知方式实现同一接口，运行时选择。

---

### 12.5 模板方法模式？

**答案**：
定义一个操作的算法骨架，将一些步骤延迟到子类中实现，子类不改变算法结构即可重定义某些步骤。

**结构**：
- AbstractClass（抽象类）：定义模板方法（final，不能重写）和抽象步骤
- ConcreteClass（具体类）：实现抽象步骤

**Spring 中的应用**：
- `JdbcTemplate`：数据库操作模板
- `RedisTemplate`：Redis 操作模板
- `RestTemplate`：HTTP 请求模板
- MyBatis-Plus 的 `ServiceImpl`：通用 Service 模板

### 13.2 项目中遇到的难点？怎么解决的？

**参考答案**：

**难点1：并发借阅导致超卖或重复借阅**
- 问题：多个请求同时借阅同一本书，可能库存扣减为负数，或同一用户重复借阅
- 解决：
  - 数据库层面：库存扣减用原子 SQL（`UPDATE book SET stock = stock - 1 WHERE id = ? AND stock >= 1`），返回0表示库存不足
  - 应用层面：Redis 分布式锁（key=lock:borrow:{userId}:{bookId}），同一用户同一本书只能有一个请求执行
  - 数据库唯一约束：可以加 (user_id, book_id, status) 唯一索引，数据库层面保证不重复

**难点2：缓存与数据库一致性**
- 问题：更新图书信息后，缓存还是旧数据
- 解决：采用 Cache-Aside 模式，更新数据库后删除缓存（而不是更新缓存），下次查询时自动加载最新数据。删除缓存比更新缓存更安全，因为并发场景下更新缓存可能导致数据不一致。

**难点3：消息可靠性**
- 问题：RabbitMQ 消息可能丢失（生产者发送失败、MQ 宕机、消费者处理失败）
- 解决：
  - 生产者：Publisher Confirm + Return 回调，失败时记录日志
  - MQ：Exchange/Queue/消息都持久化
  - 消费者：手动 ACK，处理失败 NACK 重新入队，通知服务用 messageId 做幂等性校验

- 所有表都有 create_time、update_time、deleted（逻辑删除）字段

### 13.4 为什么用 Redis？用在哪些场景？

**参考答案**：
Redis 主要用在两个场景：

1. **缓存**：图书详情查询用 Redis 缓存，减少数据库压力。采用 Cache-Aside 模式，先查缓存，未命中查数据库然后写缓存（30分钟过期），更新/删除图书时清除缓存。图书详情是读多写少的场景，非常适合缓存。

2. **分布式锁**：借阅操作加分布式锁，防止同一用户并发重复借阅同一本书。加锁用 `SET key value NX EX 10`（原子操作），value 用 UUID 标识持有者，释放锁用 Lua 脚本判断 value 匹配才删除（保证原子性，防止误删别人的锁）。

### 13.5 为什么用 RabbitMQ？怎么用的？

**参考答案**：
用 RabbitMQ 实现异步通知和服务解耦。

使用场景：
1. **借阅/归还通知**：用户借阅/归还成功后，主应用发送消息到 RabbitMQ，通知微服务消费消息并发送通知（站内信/邮件/短信）。这样主应用不需要等待通知发送完成，响应更快，而且通知服务可以独立部署和扩展。

2. **延迟到期提醒**：用 RabbitMQ 的 TTL + 死信队列实现延迟消息。借阅时发送消息到延迟队列（TTL 60秒，实际项目应设为到期前1天），消息过期后自动转发到死信交换机，死信队列的消费者消费消息，检查用户是否已归还，未归还则发送到期提醒。

消息可靠性保证：
- 生产者：Publisher Confirm + Return
- MQ：持久化
- 消费者：手动 ACK + 幂等性（messageId 去重）

### 13.6 项目的微服务是怎么拆分的？

**参考答案**：
目前拆分为两个服务：
1. **library-management（主应用）**：图书管理核心业务，作为消息生产者，端口 8080
2. **notification-service（通知微服务）**：独立部署，消费 RabbitMQ 消息，处理通知发送，端口 8081

通信方式：异步消息（RabbitMQ），而不是 HTTP 同步调用。
- 优点：异步解耦，主应用响应快，消息可靠，通知服务宕机不影响主业务
- 通知服务用内存存储通知记录（演示用），实际项目应接数据库

如果要进一步拆分，可以按业务领域拆分为：用户服务、图书服务、借阅服务、通知服务、搜索服务，每个服务独立数据库，通过 API 或 MQ 通信，使用 Nacos 做服务注册发现，Gateway 做统一网关。

### 13.7 项目的统一响应和异常处理？

**参考答案**：

**统一响应**：所有接口返回 `Result<T>`，包含 code（状态码）、message（消息）、data（数据）、timestamp（时间戳）。状态码分 20000（成功）、400xx（客户端错误）、500xx（服务端错误）。

**全局异常处理**：用 `@RestControllerAdvice` + `@ExceptionHandler` 拦截所有 Controller 异常：
- BusinessException（业务异常）：返回对应的业务状态码和消息
- 参数校验异常（MethodArgumentNotValidException 等）：返回 40000 + 具体字段错误
- Exception（兜底）：返回 50000 + "系统内部错误"，不暴露堆栈信息

这样 Controller 不需要写 try-catch，业务逻辑中直接 throw BusinessException，统一由全局异常处理器处理。

### 13.8 项目的 JWT 认证流程？

**参考答案**：
1. 用户登录 → 验证用户名密码（BCrypt 校验）→ 生成 JWT Token（包含 userId、username、role）→ 返回给前端
2. 前端存储 Token，后续请求在 Header 中携带 `Authorization: Bearer <token>`
3. JwtInterceptor 拦截所有请求（白名单除外：登录、注册、接口文档）→ 验证 Token 签名和有效期 → 解析用户信息 → 存入 ThreadLocal（UserContext）
4. Controller/Service 通过 UserContext 获取当前用户
5. 请求结束后在 afterCompletion 中清除 ThreadLocal，防止内存泄漏

为什么用 JWT 而不是 Session？
- 无状态，服务器不存储，适合分布式/微服务
- 不依赖 Cookie，避免 CSRF
- 跨语言，移动端友好

### 13.9 项目的分页查询怎么实现的？

**参考答案**：
用 MyBatis-Plus 的分页插件：
1. 配置 `PaginationInnerInterceptor`（指定数据库类型 MySQL）
2. Service 中创建 `Page<Book>(pageNum, pageSize)` 对象
3. 用 `LambdaQueryWrapper` 构建动态查询条件（书名模糊、作者模糊、分类精确、库存大于0等）
4. 调用 `page(page, wrapper)`，MyBatis-Plus 自动拦截，先执行 count 查询，再执行分页查询（LIMIT）
5. 返回 `IPage<BookVO>`，包含 records（数据列表）、total（总数）、pages（总页数）、current（当前页）、size（每页条数）

排序字段做了白名单校验，防止 SQL 注入。

### 13.10 项目的逾期罚款怎么计算的？

**参考答案**：
归还图书时：
1. 比较实际归还日期和应还日期
2. 如果归还日期 > 应还日期，计算逾期天数 = 归还日期 - 应还日期
3. 罚款 = 逾期天数 × 每日罚款（0.5元/天）
4. 更新借阅记录状态为 RETURNED，设置归还日期和罚款金额
5. 同时增加图书库存

罚款用 BigDecimal 计算，避免浮点精度问题。
